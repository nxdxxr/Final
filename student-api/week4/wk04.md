## 1. Middleware ใน Express

### 1.1 Middleware คืออะไร

Middleware คือฟังก์ชันที่ทำงานอยู่ระหว่างขั้นตอนที่ Express รับคำขอ (request) เข้ามาจนถึงขั้นตอนที่ส่งผลลัพธ์ (response) กลับไป แต่ละ middleware มีสิทธิ์เข้าถึงอ็อบเจกต์ `req`, `res` และฟังก์ชัน `next` ซึ่งใช้ส่งต่อการประมวลผลไปยัง middleware ตัวถัดไปในลำดับ (pipeline)

```javascript
function myMiddleware(req, res, next) {
  console.log(`ได้รับคำขอ: ${req.method} ${req.url}`);
  next(); // ส่งต่อไปยัง middleware หรือ route handler ตัวถัดไป
}

app.use(myMiddleware);
```

หากฟังก์ชัน middleware ไม่เรียก `next()` และไม่ส่ง response กลับ คำขอนั้นจะค้าง (hang) ไปตลอดจนกว่าจะ timeout ซึ่งเป็นข้อผิดพลาดที่พบบ่อยสำหรับผู้เริ่มต้น

### 1.2 ลำดับการประมวลผลของ Middleware (Middleware Pipeline)

Express ประมวลผล middleware ตามลำดับที่ประกาศไว้ในโค้ดจากบนลงล่าง (top-down) การเรียงลำดับจึงมีความสำคัญอย่างยิ่ง

```
Request เข้ามา
   │
   ▼
Middleware 1 (เช่น Logger)
   │  next()
   ▼
Middleware 2 (เช่น Helmet - Security Headers)
   │  next()
   ▼
Middleware 3 (เช่น CORS)
   │  next()
   ▼
Middleware 4 (เช่น express.json() - Body Parser)
   │  next()
   ▼
Route Handler (Business Logic)
   │
   ▼
Error-Handling Middleware (ถ้ามี error เกิดขึ้น)
   │
   ▼
Response ส่งกลับ
```

แผนภาพข้างต้นเป็นเพียง**ตัวอย่างหนึ่ง**ของการจัดลำดับที่เป็นไปได้ ไม่ใช่ลำดับที่ต้องเรียงตามอย่างเคร่งครัดเสมอไป โดยแยกเป็นกฎที่**บังคับ**กับส่วนที่**เลือกได้**ดังนี้

**กฎที่บังคับ (ละเมิดไม่ได้)**

1. **Error-Handling Middleware ต้องอยู่ท้ายสุดเสมอ** เนื่องจาก Express ค้นหา error handler จาก middleware ที่ยังไม่ได้ประมวลผลไปเท่านั้น หากวางไว้ก่อนหน้า route หรือ middleware อื่น จะไม่ถูกเรียกใช้เมื่อเกิด error
2. **Middleware ที่ route ต้องใช้ผลลัพธ์ ต้องอยู่ก่อน route นั้นเสมอ** เช่น `express.json()` ต้องอยู่ก่อน route ที่อ่าน `req.body` (ดูหัวข้อ 1.6) มิฉะนั้น `req.body` จะเป็น `undefined` หรือ middleware ตรวจสอบสิทธิ์ (authentication) ต้องอยู่ก่อน route ที่ต้องการจำกัดสิทธิ์การเข้าถึง

**ส่วนที่เลือกได้ (ไม่มีลำดับตายตัว)**

ลำดับระหว่าง Helmet, CORS และ Logger (morgan) สลับกันได้ ตราบใดที่ยังอยู่ก่อน route ทั้งหมดและเป็นไปตามกฎบังคับข้างต้น แนวทางที่พบบ่อยในทางปฏิบัติคือวาง Helmet และ CORS ไว้ต้นสุดของ pipeline เพื่อให้ Security Header ถูกตั้งค่าไว้เสมอ แม้คำขอจะถูกปฏิเสธในขั้นตอนถัดไปก็ตาม (ดูตัวอย่างจริงในหัวข้อ 5.3)

### 1.3 ประเภทของ Middleware

| ประเภท            | คำอธิบาย                                                         | ตัวอย่าง                             |
| ----------------- | ---------------------------------------------------------------- | ------------------------------------ |
| Application-level | ใช้กับทุก route หรือเฉพาะ path ที่กำหนด                          | `app.use(express.json())`            |
| Router-level      | ใช้กับ router เฉพาะกลุ่ม                                         | `router.use(authMiddleware)`         |
| Error-handling    | รับพารามิเตอร์ 4 ตัว `(err, req, res, next)` ใช้จัดการข้อผิดพลาด | ดูหัวข้อ 1.7                         |
| Built-in          | มาพร้อมกับ Express                                               | `express.json()`, `express.static()` |
| Third-party       | ติดตั้งเพิ่มเติมจาก npm                                          | `helmet`, `cors`, `morgan`           |

Router-level middleware เหมาะสำหรับกรณีที่ต้องการใช้ middleware เฉพาะบาง route เช่น ตรวจสอบสิทธิ์เฉพาะ route ที่ต้อง login ก่อน

```javascript
const express = require("express");
const router = express.Router();

function authMiddleware(req, res, next) {
  if (!req.headers.authorization) {
    return res.status(401).json({
      error: { code: "UNAUTHORIZED", message: "ต้องเข้าสู่ระบบก่อนใช้งาน" },
    });
  }
  next();
}

// authMiddleware มีผลเฉพาะ route ที่ประกาศผ่าน router ตัวนี้เท่านั้น
router.use(authMiddleware);

router.get("/profile", (req, res) => {
  res.json({ message: "ข้อมูลส่วนตัว" });
});

app.use("/api/v1", router);
```

### 1.4 ตัวอย่างการเขียน Custom Logger Middleware

```javascript
function requestLogger(req, res, next) {
  const timestamp = new Date().toISOString();
  console.log(`[${timestamp}] ${req.method} ${req.originalUrl}`);
  next();
}

app.use(requestLogger);
```

### 1.5 morgan: Logger สำเร็จรูป

การเขียน custom logger เองอย่างในหัวข้อ 1.4 เหมาะสำหรับทำความเข้าใจหลักการ แต่ในโปรเจกต์จริงมักใช้ไลบรารีสำเร็จรูปแทน เนื่องจากมีรูปแบบการบันทึก log ที่เป็นมาตรฐาน (เช่น สถานะ HTTP, เวลาในการประมวลผล) และรองรับการตั้งค่าเพิ่มเติม เช่น การบันทึกลงไฟล์

```bash
npm install morgan
```

```javascript
const morgan = require("morgan");

app.use(morgan("dev"));
```

รูปแบบ log ที่ได้จาก `morgan("dev")` จะมีลักษณะดังนี้

```
GET /api/v1/students 200 5.234 ms - 128
```

### 1.6 express.json(): Body Parser

เมื่อ client ส่งคำขอ `POST`, `PUT` หรือ `PATCH` พร้อมข้อมูลแบบ JSON มาใน body ของคำขอ Express จะไม่แปลงข้อมูลนั้นให้เป็น JavaScript object ให้อัตโนมัติ ต้องใช้ middleware ประเภท body parser ก่อนจึงจะอ่านค่าจาก `req.body` ได้ `express.json()` เป็น built-in middleware ของ Express ที่ทำหน้าที่นี้ ไม่ต้องติดตั้งไลบรารีเพิ่มเติม

**ตัวอย่างเมื่อไม่มี `express.json()`**

```javascript
app.post("/students", (req, res) => {
  res.json({ body: req.body, type: typeof req.body });
});
```

ผลลัพธ์เมื่อส่ง `POST` พร้อม `{"name": "test"}` ใน body

```json
{ "type": "undefined" }
```

`req.body` เป็น `undefined` เสมอ แม้ client จะส่งข้อมูลมาจริง เพราะยังไม่มี middleware แปลง raw body เป็น object

**ตัวอย่างเมื่อมี `express.json()`**

```javascript
app.use(express.json());

app.post("/students", (req, res) => {
  res.json({ body: req.body, type: typeof req.body });
});
```

ผลลัพธ์เมื่อส่ง `POST` พร้อม `{"name": "test"}` ใน body เดียวกัน

```json
{ "body": { "name": "test" }, "type": "object" }
```

**ข้อควรระวัง**: เช่นเดียวกับ middleware อื่น `app.use(express.json())` ต้องประกาศไว้ **ก่อน** route ที่ต้องอ่าน `req.body` เสมอ (ตามหลักการในหัวข้อ 1.2) และควรกำหนด `limit` เพื่อจำกัดขนาด body ที่รับได้ เช่น `express.json({ limit: "10kb" })` เพื่อป้องกัน payload ขนาดใหญ่ผิดปกติ ดังตัวอย่างในหัวข้อ 5.3

### 1.7 Error-Handling Middleware

Express กำหนดให้ middleware สำหรับจัดการข้อผิดพลาดต้องมีพารามิเตอร์ 4 ตัวเสมอ (`err, req, res, next`) และต้องถูกประกาศไว้เป็นลำดับสุดท้าย หลัง route ทั้งหมด

```javascript
// route ทั้งหมดต้องอยู่ก่อนหน้านี้

app.use((err, req, res, next) => {
  console.error(err.stack);
  // ใช้ err.status/err.statusCode หากมี (เช่น PayloadTooLargeError จาก express.json ที่ส่งมาเป็น 413)
  // เพื่อไม่ให้ error ที่มีรหัสสถานะของตัวเองถูกกลบด้วย 500 เสมอไป
  const statusCode = err.status || err.statusCode || 500;
  res.status(statusCode).json({
    error: {
      code: statusCode === 500 ? "INTERNAL_SERVER_ERROR" : err.type || "ERROR",
      message:
        statusCode === 500
          ? "เกิดข้อผิดพลาดที่ไม่คาดคิดภายในระบบ"
          : err.message,
    },
  });
});
```

การมี error-handling middleware แบบรวมศูนย์ช่วยให้ไม่ต้องเขียน `try-catch` ซ้ำซ้อนในทุก route และทำให้รูปแบบ error response เป็นมาตรฐานเดียวกันทั้งระบบ การอ่านค่า `err.status`/`err.statusCode` ก่อนเลือกใช้ 500 เป็นค่าสำรอง (fallback) ช่วยให้ error ที่มีรหัสสถานะเฉพาะของตัวเองอยู่แล้ว เช่น `PayloadTooLargeError` (413) จาก `express.json()` ยังคงรายงานรหัสสถานะที่ถูกต้องแก่ client แทนที่จะถูกแปลงเป็น 500 เสมอไป

## 2. Helmet: การป้องกันช่องโหว่พื้นฐานจาก HTTP Header

### 2.1 ความสำคัญของ HTTP Security Header

ค่าเริ่มต้นของ Express จะส่ง Header บางตัวที่เปิดเผยข้อมูลทางเทคนิคของเซิร์ฟเวอร์ เช่น `X-Powered-By: Express` ซึ่งอาจถูกผู้ไม่หวังดีใช้เป็นข้อมูลประกอบการโจมตี นอกจากนี้ยังมี Header ด้านความปลอดภัยอีกหลายตัวที่ควรตั้งค่าอย่างเหมาะสม แต่ Express ไม่ได้ตั้งค่าให้โดยอัตโนมัติ

### 2.2 การติดตั้งและใช้งาน Helmet

Helmet คือไลบรารีที่รวม middleware สำหรับตั้งค่า HTTP Security Header ที่จำเป็นไว้ในที่เดียว

```bash
npm install helmet
```

```javascript
const helmet = require("helmet");

app.use(helmet());
```

### 2.3 ตัวอย่าง Header ที่ Helmet ช่วยตั้งค่า

| Header                              | หน้าที่                                                                                                                                                                                                   |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X-DNS-Prefetch-Control`            | ควบคุมการทำ DNS prefetching ของเบราว์เซอร์                                                                                                                                                                |
| `X-Frame-Options`                   | ป้องกันการนำหน้าเว็บของแอปพลิเคชันไปฝังใน `<iframe>` ของเว็บอื่น (ป้องกัน Clickjacking)                                                                                                                            |
| `Strict-Transport-Security`         | บังคับให้เบราว์เซอร์เชื่อมต่อผ่าน HTTPS เท่านั้น                                                                                                                                                          |
| `X-Content-Type-Options`            | ป้องกันเบราว์เซอร์เดา (sniff) ประเภทไฟล์ผิดจากที่ระบุใน `Content-Type`                                                                                                                                    |
| `X-Download-Options`                | ป้องกันไฟล์ที่ดาวน์โหลดจากถูกเปิดโดยตรงในบริบทของเว็บไซต์ (ใช้กับ Internet Explorer)                                                                                                                      |
| `X-Permitted-Cross-Domain-Policies` | ป้องกันปลั๊กอินอย่าง Adobe Flash/PDF อ่านข้อมูลข้ามโดเมนผ่าน policy file                                                                                                                                  |
| `X-XSS-Protection`                  | ปิดกลไก XSS filter ในตัวเบราว์เซอร์รุ่นเก่าโดยตั้งใจ (ค่าเป็น `0`) เนื่องจากกลไกนี้มีช่องโหว่ในตัวเองและถูกยกเลิกในเบราว์เซอร์รุ่นใหม่ การป้องกัน XSS ที่แนะนำในปัจจุบันคือ `Content-Security-Policy` แทน |

Helmet เป็นเพียงจุดเริ่มต้นของการรักษาความปลอดภัย ไม่สามารถป้องกันช่องโหว่ทุกประเภทได้ การป้องกันที่ครอบคลุมยิ่งขึ้น เช่น Input Validation และ Rate Limiting จะกล่าวถึงในสัปดาห์ที่ 12

## 3. CORS (Cross-Origin Resource Sharing)

### 3.1 ปัญหา Same-Origin Policy

เบราว์เซอร์บังคับใช้นโยบาย Same-Origin Policy ซึ่งจำกัดไม่ให้หน้าเว็บจากโดเมนหนึ่งเรียกข้อมูลจากเซิร์ฟเวอร์ในอีกโดเมนหนึ่งได้โดยตรง เพื่อป้องกันการโจมตีข้ามเว็บไซต์ อย่างไรก็ตาม ในการพัฒนาจริง frontend และ backend มักถูก deploy อยู่คนละโดเมนหรือคนละพอร์ต จึงจำเป็นต้องมีกลไก CORS เพื่ออนุญาตการเข้าถึงข้ามโดเมนอย่างมีการควบคุม

### 3.2 การติดตั้งและใช้งาน CORS

```bash
npm install cors
```

```javascript
const cors = require("cors");

// อนุญาตทุกโดเมน (เหมาะสำหรับ API สาธารณะ หรือช่วงพัฒนาเท่านั้น)
app.use(cors());
```

### 3.3 การตั้งค่า CORS แบบจำกัดเฉพาะโดเมนที่เชื่อถือได้

ในสภาพแวดล้อมจริง (production) ไม่ควรอนุญาตทุกโดเมนอย่างไม่มีขอบเขต ควรระบุโดเมนที่อนุญาตอย่างชัดเจน

```javascript
const corsOptions = {
  origin: ["https://myapp.example.com", "http://localhost:3001"],
  methods: ["GET", "POST", "PUT", "PATCH", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization"],
};

app.use(cors(corsOptions));
```

การเผลอปล่อยให้ `cors()` เปิดทุกโดเมนตามหัวข้อ 3.2 หลุดไปถึงระบบจริง (production) โดยไม่ได้ตั้งค่าตามหัวข้อนี้ ถือเป็นตัวอย่างของความเสี่ยง Security Misconfiguration ตาม OWASP Top 10

### 3.4 กลไกเบื้องหลัง CORS: Preflight Request

สำหรับคำขอที่มีความซับซ้อน (เช่น ใช้ Method อื่นนอกจาก GET/POST หรือมี Header กำหนดเอง) เบราว์เซอร์จะส่งคำขอ `OPTIONS` ล่วงหน้าเรียกว่า preflight request เพื่อตรวจสอบก่อนว่าเซิร์ฟเวอร์อนุญาตให้ทำคำขอจริงหรือไม่ ไลบรารี `cors` จัดการขั้นตอนนี้ให้โดยอัตโนมัติเมื่อใช้งานเป็น middleware

## 4. Environment Variables

### 4.1 ปัญหาของการเขียนค่าคงที่ตายตัวในโค้ด (Hardcoding)

การเขียนข้อมูล เช่น รหัสผ่านฐานข้อมูล หรือ API Key ไว้ตรงในโค้ดโดยตรงเป็นความเสี่ยงด้านความปลอดภัยที่สำคัญ เนื่องจากหากโค้ดถูกเผยแพร่ขึ้น repository สาธารณะ ข้อมูลลับเหล่านั้นจะรั่วไหลทันที นอกจากนี้ค่าคงที่ เช่น พอร์ตหรือ URL ฐานข้อมูล มักเปลี่ยนแปลงไปตามสภาพแวดล้อม (development, staging, production)

### 4.2 การใช้งาน dotenv

```bash
npm install dotenv
```

สร้างไฟล์ `.env` ที่รากของโปรเจกต์ (และเพิ่มไฟล์นี้ใน `.gitignore` เพื่อไม่ให้ถูก commit ขึ้น repository)

```
PORT=3000
NODE_ENV=development
JWT_SECRET=this-is-a-secret-key-for-development-only
```

โหลดค่าตัวแปรในไฟล์ `index.js`

```javascript
require("dotenv").config();

const PORT = process.env.PORT || 3000;
const JWT_SECRET = process.env.JWT_SECRET;

app.listen(PORT, () => {
  console.log(`Server กำลังทำงานที่พอร์ต ${PORT} (${process.env.NODE_ENV})`);
});
```

### 4.3 แนวปฏิบัติที่ดีสำหรับ Environment Variables

1. ห้าม commit ไฟล์ `.env` ที่มีข้อมูลจริงขึ้น repository เด็ดขาด
2. จัดทำไฟล์ `.env.example` ที่มีรายชื่อตัวแปรทั้งหมดแต่ไม่มีค่าจริง เพื่อให้สมาชิกทีมทราบว่าต้องตั้งค่าตัวแปรใดบ้าง
3. ตรวจสอบว่าตัวแปรที่จำเป็นถูกตั้งค่าไว้ตั้งแต่เริ่มรันแอปพลิเคชัน หากขาดควรแจ้งข้อผิดพลาดทันทีแทนที่จะปล่อยให้ระบบทำงานผิดพลาดภายหลัง

```javascript
if (!process.env.JWT_SECRET) {
  throw new Error("ไม่พบ JWT_SECRET กรุณาตั้งค่าในไฟล์ .env");
}
```

## 5. ภาพรวมของ OWASP Top 10

### 5.1 OWASP คืออะไร

OWASP (Open Worldwide Application Security Project) เป็นองค์กรไม่แสวงหาผลกำไรที่เผยแพร่แนวทางปฏิบัติด้านความปลอดภัยของแอปพลิเคชันเว็บ โดย OWASP Top 10 คือรายการความเสี่ยงด้านความปลอดภัยที่พบบ่อยและมีผลกระทบสูงที่สุด 10 อันดับ ซึ่งได้รับการปรับปรุงเป็นระยะเพื่อสะท้อนภัยคุกคามที่เปลี่ยนแปลงไป (เนื้อหาในเอกสารนี้อ้างอิงเวอร์ชันล่าสุด OWASP Top 10:2025)

### 5.2 ภาพรวมความเสี่ยงที่เกี่ยวข้องกับการพัฒนา Node.js API

| ------ | -------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| A01    | Broken Access Control                  | ผู้ใช้เข้าถึงข้อมูลหรือฟังก์ชันที่ตนไม่มีสิทธิ์                 | ไม่ตรวจสอบว่า user เป็นเจ้าของข้อมูลก่อนแก้ไข                                          |

| A03    | Software Supply Chain Failures         | ใช้ไลบรารี เครื่องมือ หรือ pipeline ที่ถูกแทรกแซงหรือมีช่องโหว่ | ติดตั้ง dependency จาก npm ที่มีช่องโหว่หรือถูกแทรกโค้ดอันตราย โดยไม่ตรวจสอบแหล่งที่มา |

| Software or Data Integrity Failures    | ยังไม่ได้ป้องกันในสัปดาห์นี้ เป็นเรื่องของการดูแล dependency อย่างต่อเนื่องตลอดโครงการเช่นเดียวกับ Software Supply Chain Failures                               |

### 5.3 ตัวอย่างการป้องกันเบื้องต้นที่ทำได้ทันทีในสัปดาห์นี้

```javascript
const express = require("express");
const helmet = require("helmet");
const cors = require("cors");
const morgan = require("morgan");
require("dotenv").config();

const app = express();
const PORT = process.env.PORT || 3000;

// ป้องกัน Security Misconfiguration เบื้องต้น
// วาง Helmet และ CORS ก่อน Logger เพื่อให้ Security Header ถูกตั้งค่าไว้เสมอ
// แม้คำขอจะยังไม่ถึงขั้นตอน logger หรือเกิด error ก่อนหน้านั้น
app.use(helmet());
app.use(cors({ origin: process.env.ALLOWED_ORIGIN }));
app.use(morgan("dev"));
app.use(express.json({ limit: "10kb" })); // จำกัดขนาด body ป้องกัน payload ขนาดใหญ่ผิดปกติ

app.get("/api/v1/students", (req, res) => {
  res.json([{ id: 1, name: "สมชาย ใจดี" }]);
});

// 404: ไม่พบ route ที่ร้องขอ (ต้องอยู่หลัง route ทั้งหมด)
app.use((req, res) => {
  res.status(404).json({
    error: { code: "ROUTE_NOT_FOUND", message: "ไม่พบเส้นทางที่ร้องขอ" },
  });
});

// Error-Handling Middleware (ต้องอยู่ลำดับสุดท้ายเสมอ ดูหัวข้อ 1.7)
app.use((err, req, res, next) => {
  console.error(err.stack);
  const statusCode = err.status || err.statusCode || 500;
  res.status(statusCode).json({
    error: {
      code: statusCode === 500 ? "INTERNAL_SERVER_ERROR" : err.type || "ERROR",
      message:
        statusCode === 500
          ? "เกิดข้อผิดพลาดที่ไม่คาดคิดภายในระบบ"
          : err.message,
    },
  });
});

app.listen(PORT, () => {
  console.log(`Server กำลังทำงานที่พอร์ต ${PORT} (${process.env.NODE_ENV})`);
});
```

โค้ดข้างต้นเป็นแอปที่รันได้จริงครบทุกส่วน ไม่ใช่แค่การตั้งค่า middleware เพียงอย่างเดียว โดยต้องมีไฟล์ `.env` ประกอบในรูปแบบเดียวกับตัวอย่างในหัวข้อ 4.2 แต่เพิ่มตัวแปร `ALLOWED_ORIGIN` เข้าไปด้วย เช่น `ALLOWED_ORIGIN=http://localhost:3001` จึงจะรันได้สมบูรณ์

ลำดับข้างต้นต่างจากแผนภาพในหัวข้อ 1.2 เล็กน้อย (ซึ่งวาง Logger ไว้ก่อน Helmet) แผนภาพในหัวข้อ 1.2 เป็นเพียงตัวอย่างหนึ่งของการจัดลำดับที่เป็นไปได้ ส่วนในโค้ดจริงข้างต้นเลือกวาง Helmet และ CORS ไว้ก่อน เพื่อให้ Security Header ถูกตั้งค่าครบก่อนที่จะประมวลผลถึงขั้นตอนอื่น ไม่มีลำดับใดผิด ตราบใดที่ Error-Handling Middleware ยังคงอยู่ลำดับสุดท้ายเสมอ (`Helmet` ปิด `X-Powered-By` ให้โดยอัตโนมัติอยู่แล้ว จึงไม่จำเป็นต้องเรียก `app.disable("x-powered-by")` ซ้ำ)

การจำกัดขนาด body ด้วย `limit: "10kb"` เป็นตัวอย่างของการป้องกันเบื้องต้นที่ช่วยลดความเสี่ยงจากคำขอที่มีขนาดใหญ่ผิดปกติ ซึ่งเป็นส่วนหนึ่งของแนวคิด Security Misconfiguration หากไม่ได้จำกัดค่านี้ไว้

## สรุปเนื้อหาสำคัญ

1. Middleware คือฟังก์ชันที่ทำงานระหว่างการรับคำขอและการตอบกลับ ประมวลผลตามลำดับที่ประกาศไว้ และต้องเรียก `next()` เพื่อส่งต่อการทำงาน
2. Helmet ช่วยตั้งค่า HTTP Security Header ที่จำเป็นโดยอัตโนมัติ เพื่อป้องกันช่องโหว่พื้นฐาน เช่น Clickjacking
3. CORS ควบคุมว่าโดเมนใดสามารถเรียกใช้ API ข้ามโดเมนได้ และควรกำหนดขอบเขตให้ชัดเจนในสภาพแวดล้อมจริง ไม่ควรอนุญาตทุกโดเมน
4. Environment Variables ช่วยแยกค่าคงที่และข้อมูลลับออกจากโค้ด ทำให้ปรับเปลี่ยนตามสภาพแวดล้อมได้โดยไม่ต้องแก้โค้ด และลดความเสี่ยงข้อมูลรั่วไหล
5. OWASP Top 10 เป็นแนวทางมาตรฐานที่ช่วยให้นักพัฒนาตระหนักถึงความเสี่ยงด้านความปลอดภัยที่พบบ่อย ซึ่งบางส่วนจะถูกนำไปปฏิบัติจริงในสัปดาห์ถัดไปของรายวิชา

## คำถามท้ายบท

1. จงอธิบายว่าเหตุใด middleware ที่ไม่เรียก `next()` และไม่ส่ง response กลับ จึงทำให้คำขอค้าง พร้อมยกตัวอย่างโค้ดที่ผิดพลาดลักษณะนี้
2. Error-handling middleware ใน Express แตกต่างจาก middleware ทั่วไปอย่างไร และเพราะเหตุใดจึงต้องประกาศไว้เป็นลำดับสุดท้าย
3. Helmet ช่วยป้องกันความเสี่ยงประเภทใดบ้าง จงยกตัวอย่าง Header อย่างน้อย 2 ตัวพร้อมหน้าที่ของแต่ละ Header
4. เพราะเหตุใดการตั้งค่า `cors()` โดยไม่ระบุ `origin` จึงไม่เหมาะสมสำหรับระบบที่ใช้งานจริง (production)
5. จงอธิบายว่าเหตุใดจึงไม่ควร commit ไฟล์ `.env` ขึ้น repository และควรใช้ไฟล์ใดแทนเพื่อบอกสมาชิกทีมว่าต้องตั้งค่าตัวแปรใดบ้าง
6. จงจับคู่ความเสี่ยงตาม OWASP Top 10 ในตารางหัวข้อที่ 5.2 กับสัปดาห์ในแผนการสอนที่จะมีการนำไปปฏิบัติจริง
7. หากเซิร์ฟเวอร์ไม่จำกัดขนาดของ request body ไว้เลย จะเกิดความเสี่ยงใดตามมา และมีวิธีป้องกันเบื้องต้นอย่างไร
