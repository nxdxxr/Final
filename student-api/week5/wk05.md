## วัตถุประสงค์การเรียนรู้ประจำสัปดาห์

เมื่อเรียนจบเนื้อหาในสัปดาห์นี้ นิสิตจะสามารถ

1. อธิบายหลักการทำงานของ Connection Pool และเหตุผลที่ต้องใช้ในการเชื่อมต่อฐานข้อมูลสำหรับ API ได้
2. เชื่อมต่อ Node.js เข้ากับฐานข้อมูล MySQL และดำเนินการ CRUD พื้นฐานผ่านคำสั่ง SQL ได้

4. ป้องกันช่องโหว่ SQL Injection ด้วยการใช้ Parameterized Query ได้

## 1. จากข้อมูลจำลองสู่ฐานข้อมูลจริง

### 1.1 ข้อจำกัดของข้อมูลแบบ In-Memory

ตั้งแต่สัปดาห์ที่ 1 โปรเจกต์ `student-api` ใช้ตัวแปร `students` และ `courses` ที่เก็บอยู่ในหน่วยความจำ (in-memory array) ซึ่งมีข้อจำกัดสำคัญคือ

1. **ข้อมูลหายเมื่อรีสตาร์ตเซิร์ฟเวอร์** เนื่องจากไม่มีการบันทึกลงสื่อบันทึกถาวร (persistent storage)
2. **ไม่รองรับการทำงานพร้อมกันหลายอินสแตนซ์** หากรันเซิร์ฟเวอร์หลายตัวเพื่อรองรับผู้ใช้จำนวนมาก แต่ละอินสแตนซ์จะมีข้อมูลในหน่วยความจำแยกจากกัน ทำให้ข้อมูลไม่สอดคล้องกัน
3. **ไม่มีกลไกรับประกันความถูกต้องของข้อมูลเมื่อเกิดข้อผิดพลาดระหว่างการดำเนินการหลายขั้นตอน**

ฐานข้อมูลเชิงสัมพันธ์ (Relational Database) เช่น MySQL แก้ปัญหาเหล่านี้ได้ด้วยการจัดเก็บข้อมูลถาวร รองรับการเข้าถึงพร้อมกันจากหลายแหล่ง และมีกลไก Transaction ที่รับประกันความถูกต้องของข้อมูล

### 1.2 การติดตั้งไลบรารีเชื่อมต่อ MySQL

```bash
npm install mysql2
```

`mysql2` เป็นไลบรารีสำหรับเชื่อมต่อ Node.js กับ MySQL ที่พัฒนาต่อยอดจากไลบรารี `mysql` รุ่นเดิม โดยมีจุดต่างสำคัญคือ

1. **รองรับ Promise-based API โดยตรง** ผ่านการ `require("mysql2/promise")` ทำให้ใช้ `async/await` ได้ทันทีตามตัวอย่างในเอกสารนี้ทั้งหมด ขณะที่ไลบรารี `mysql` รุ่นเดิมใช้รูปแบบ callback เป็นหลัก ต้องครอบด้วย Promise เองหากต้องการใช้ `async/await`
2. **รองรับ Prepared Statement แบบ Binary Protocol** ของ MySQL ซึ่งเร็วกว่าการส่งคำสั่งแบบ text protocol ที่ไลบรารี `mysql` รุ่นเดิมใช้ โดยเฉพาะเมื่อเรียก query เดิมซ้ำหลายครั้งด้วยค่าพารามิเตอร์ต่างกัน
3. ยังคงใช้ชุดคำสั่ง (API) ที่คล้ายกับไลบรารี `mysql` รุ่นเดิมเป็นส่วนใหญ่ ทำให้ย้ายจากไลบรารีเดิมมาใช้ `mysql2` ได้โดยแก้โค้ดเพียงเล็กน้อย

## 2. Connection Pool

### 2.1 ปัญหาของการเปิดการเชื่อมต่อใหม่ทุกครั้ง

การเปิดการเชื่อมต่อ (connection) กับฐานข้อมูลมีค่าใช้จ่ายด้านเวลาและทรัพยากรค่อนข้างสูง หากเปิดการเชื่อมต่อใหม่ทุกครั้งที่มีคำขอเข้ามาและปิดทันทีหลังใช้งานเสร็จ จะทำให้ระบบทำงานช้าลงอย่างมากเมื่อมีผู้ใช้งานพร้อมกันจำนวนมาก

### 2.2 Connection Pool คืออะไร

Connection Pool คือกลไกที่สร้างการเชื่อมต่อกับฐานข้อมูลไว้ล่วงหน้าเป็นจำนวนหนึ่ง (pool) แล้วนำกลับมาใช้ซ้ำ (reuse) แทนการเปิด-ปิดการเชื่อมต่อใหม่ทุกครั้ง เมื่อคำขอหนึ่งต้องการติดต่อฐานข้อมูล ระบบจะ "ยืม" การเชื่อมต่อจาก pool มาใช้ และคืนกลับเข้า pool เมื่อใช้งานเสร็จ

```
Application
   │
   ▼
Connection Pool (เช่น มี 10 connections พร้อมใช้งาน)
   │  ┌── Connection 1 (กำลังใช้งาน)
   │  ├── Connection 2 (ว่าง)
   │  ├── Connection 3 (ว่าง)
   │  └── ... (Connection 4-10)
   ▼
MySQL Server
```

### 2.3 การสร้าง Connection Pool ด้วย mysql2

สร้างไฟล์ `db.js` แยกต่างหากเพื่อจัดการการเชื่อมต่อฐานข้อมูล

```javascript
const mysql = require("mysql2/promise");

const pool = mysql.createPool({
  host: process.env.DB_HOST || "localhost",
  user: process.env.DB_USER || "root",
  password: process.env.DB_PASSWORD || "",
  database: process.env.DB_NAME || "student_api",
  waitForConnections: true,
  connectionLimit: 10, // จำนวน connection สูงสุดใน pool
  queueLimit: 0,
});

module.exports = pool;
```

ค่าการเชื่อมต่อฐานข้อมูลทั้งหมดถูกอ่านจาก Environment Variables แทนการเขียนตายตัวในโค้ด เพิ่มค่าต่อไปนี้ในไฟล์ `.env`

```
DB_HOST=localhost
DB_USER=root
DB_PASSWORD=your_password
DB_NAME=student_api
```

### 2.4 เหตุใด Connection Limit จึงมีความสำคัญ

การกำหนด `connectionLimit` ที่เหมาะสมเป็นความสมดุลระหว่างประสิทธิภาพและการใช้ทรัพยากร หากตั้งค่าน้อยเกินไป คำขอจำนวนมากจะต้องรอคิว (queue) นานขึ้น แต่หากตั้งค่ามากเกินไป อาจทำให้เซิร์ฟเวอร์ฐานข้อมูลรับภาระเกินความสามารถ โดยทั่วไปค่านี้ควรกำหนดตามขนาดของทรัพยากรเซิร์ฟเวอร์และปริมาณผู้ใช้งานจริง

ค่าที่ตั้งไว้ในหัวข้อ 2.3 อีกสองตัวมีความหมายดังนี้

- **`waitForConnections: true`** กำหนดพฤติกรรมเมื่อ connection ใน pool ถูกใช้งานจนครบ `connectionLimit` แล้ว หากตั้งเป็น `true` คำขอใหม่ที่เข้ามาจะถูกเข้าคิวรอจนกว่าจะมี connection ว่าง แทนที่จะโยน error ทันที ซึ่งเหมาะกับ API ทั่วไปที่ยอมรับความหน่วงเล็กน้อยได้ดีกว่าคำขอล้มเหลว
- **`queueLimit: 0`** กำหนดจำนวนคำขอสูงสุดที่ยอมให้เข้าคิวรอพร้อมกัน ค่า `0` หมายถึง **ไม่จำกัดจำนวนคิว** (unlimited) ในระบบที่ต้องการป้องกันไม่ให้หน่วยความจำเซิร์ฟเวอร์บวมจากคิวที่ยาวเกินไปเมื่อมีผู้ใช้งานจำนวนมากพร้อมกัน ควรกำหนดค่าที่จำกัดไว้ (เช่น `queueLimit: 50`) เพื่อให้คำขอที่เกินโควตาได้รับ error ทันทีแทนการรอไม่มีกำหนด

> 💡 **Tip**: ไม่มีค่า `connectionLimit` ที่ถูกต้องตายตัวสำหรับทุกระบบ ค่าเริ่มต้นของ `mysql2` คือ `10` ซึ่งเหมาะสำหรับการพัฒนาและทดสอบ แต่ก่อน deploy ขึ้นระบบจริงควรตรวจสอบว่า MySQL Server ที่ใช้กำหนดค่า `max_connections` (จำนวน connection สูงสุดที่ MySQL Server รับได้ทั้งหมด) ไว้เท่าใด แล้วคำนวณ `connectionLimit` ของแต่ละอินสแตนซ์แอปพลิเคชันไม่ให้รวมกันเกินขีดจำกัดนั้น โดยเฉพาะเมื่อรันแอปพลิเคชันหลายอินสแตนซ์พร้อมกัน (ตามที่กล่าวถึงในหัวข้อ 1.1 เรื่องการรองรับหลายอินสแตนซ์)

## 3. การสร้างตารางและ CRUD พื้นฐาน

### 3.1 การออกแบบตาราง

สร้างฐานข้อมูลและตารางตามโครงสร้างข้อมูลที่ใช้มาตั้งแต่สัปดาห์ที่ 1

```sql
CREATE DATABASE IF NOT EXISTS student_api;
USE student_api;

CREATE TABLE students (
  id INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(100) NOT NULL,
  major VARCHAR(100) NOT NULL,
  email VARCHAR(100) NOT NULL UNIQUE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE courses (
  id INT AUTO_INCREMENT PRIMARY KEY,
  course_name VARCHAR(150) NOT NULL,
  credit INT NOT NULL
);

CREATE TABLE enrollments (
  id INT AUTO_INCREMENT PRIMARY KEY,
  student_id INT NOT NULL,
  course_id INT NOT NULL,
  FOREIGN KEY (student_id) REFERENCES students(id) ON DELETE CASCADE,
  FOREIGN KEY (course_id) REFERENCES courses(id) ON DELETE CASCADE,
  UNIQUE KEY unique_enrollment (student_id, course_id)
);
```

ข้อสังเกตสำคัญในการออกแบบตาราง

- คอลัมน์ `email` กำหนดเป็น `UNIQUE` เพื่อให้ฐานข้อมูลบังคับความถูกต้องของข้อมูล (data integrity) แทนที่จะพึ่งพาการตรวจสอบในโค้ดฝั่งแอปพลิเคชันเพียงอย่างเดียว
- ตาราง `enrollments` ใช้ Foreign Key เพื่อรักษาความสัมพันธ์ระหว่างตาราง และกำหนด `ON DELETE CASCADE` เพื่อให้ข้อมูลการลงทะเบียนถูกลบโดยอัตโนมัติเมื่อนิสิตหรือรายวิชาถูกลบ

> ⚠️ **ข้อควรระวัง**: `ON DELETE CASCADE` สะดวกแต่มีความเสี่ยง เพราะการลบระเบียนต้นทาง (เช่น ลบนิสิต 1 คน) จะลบข้อมูลที่เกี่ยวข้องทั้งหมดโดยอัตโนมัติแบบย้อนกลับไม่ได้ (irreversible) ไม่มีขั้นตอนยืนยันหรือแจ้งเตือนใด ๆ ก่อนลบ ในระบบที่ข้อมูลมีความสำคัญสูง (เช่น ประวัติการทำธุรกรรมทางการเงิน) ควรพิจารณาใช้ `ON DELETE RESTRICT` (ห้ามลบต้นทางถ้ายังมีข้อมูลลูกอ้างอิงอยู่) หรือแนวทาง Soft Delete (ทำเครื่องหมายว่าลบแล้วด้วยคอลัมน์ เช่น `deleted_at` แทนการ `DELETE` จริง) แทนการใช้ `CASCADE` โดยไม่พิจารณาผลกระทบ

### 3.2 การดำเนินการ SELECT (Read)

```javascript
const pool = require("./db");

app.get("/api/v1/students", async (req, res, next) => {
  try {
    const [rows] = await pool.query("SELECT * FROM students");
    res.status(200).json({ message: "สำเร็จ", data: rows });
  } catch (err) {
    next(err); // ส่งต่อไปยัง error-handling middleware
  }
});

app.get("/api/v1/students/:id", async (req, res, next) => {
  try {
    const [rows] = await pool.query("SELECT * FROM students WHERE id = ?", [
      req.params.id,
    ]);

    if (rows.length === 0) {
      return res.status(404).json({
        error: { code: "NOT_FOUND", message: "ไม่พบข้อมูลนิสิต" },
      });
    }

    res.status(200).json({ message: "สำเร็จ", data: rows[0] });
  } catch (err) {
    next(err);
  }
});
```

### 3.3 การดำเนินการ INSERT (Create)

```javascript
app.post("/api/v1/students", async (req, res, next) => {
  const { name, major, email } = req.body;

  if (!name || !major || !email) {
    return res.status(400).json({
      error: { code: "VALIDATION_ERROR", message: "กรุณาระบุข้อมูลให้ครบถ้วน" },
    });
  }

  try {
    const [result] = await pool.query(
      "INSERT INTO students (name, major, email) VALUES (?, ?, ?)",
      [name, major, email],
    );

    res.status(201).json({
      message: "เพิ่มข้อมูลสำเร็จ",
      data: { id: result.insertId, name, major, email },
    });
  } catch (err) {
    // รหัสข้อผิดพลาด ER_DUP_ENTRY เกิดขึ้นเมื่อข้อมูลซ้ำกับ UNIQUE constraint
    if (err.code === "ER_DUP_ENTRY") {
      return res.status(409).json({
        error: { code: "DUPLICATE_EMAIL", message: "อีเมลนี้มีอยู่ในระบบแล้ว" },
      });
    }
    next(err);
  }
});
```

### 3.4 การดำเนินการ UPDATE และ DELETE

```javascript
app.put("/api/v1/students/:id", async (req, res, next) => {
  const { name, major, email } = req.body;

  try {
    const [result] = await pool.query(
      "UPDATE students SET name = ?, major = ?, email = ? WHERE id = ?",
      [name, major, email, req.params.id],
    );

    if (result.affectedRows === 0) {
      return res.status(404).json({
        error: { code: "NOT_FOUND", message: "ไม่พบข้อมูลนิสิต" },
      });
    }

    res.status(200).json({ message: "แก้ไขข้อมูลสำเร็จ" });
  } catch (err) {
    next(err);
  }
});

app.delete("/api/v1/students/:id", async (req, res, next) => {
  try {
    const [result] = await pool.query("DELETE FROM students WHERE id = ?", [
      req.params.id,
    ]);

    if (result.affectedRows === 0) {
      return res.status(404).json({
        error: { code: "NOT_FOUND", message: "ไม่พบข้อมูลนิสิต" },
      });
    }

    res.status(200).json({ message: "ลบข้อมูลสำเร็จ" });
  } catch (err) {
    next(err);
  }
});
```

ทั้งสอง route ใช้ `result.affectedRows` ในการตรวจสอบว่ามีระเบียนถูกแก้ไขหรือลบจริงหรือไม่ ค่านี้เป็นตัวเลขจำนวนแถวที่คำสั่ง UPDATE หรือ DELETE ส่งผลกระทบ หาก `id` ที่ระบุใน `WHERE` ไม่ตรงกับระเบียนใดเลย MySQL จะไม่รายงาน error ใด ๆ กลับมา (เพราะไวยากรณ์คำสั่งถูกต้อง เพียงแต่ไม่มีแถวที่เข้าเงื่อนไข) ค่า `affectedRows` จะเป็น `0` ซึ่งเป็นวิธีเดียวที่ใช้แยกแยะระหว่าง "แก้ไขสำเร็จ" กับ "ไม่พบข้อมูลที่ต้องการแก้ไข" ได้

> ⚠️ **ข้อควรระวัง**: route `PUT` ด้านบนไม่ได้ตรวจสอบว่า `req.body` มีค่า `name`, `major`, `email` ครบถ้วนก่อนนำไป UPDATE (ต่างจาก route `POST` ในหัวข้อ 3.3 ที่ตรวจสอบก่อน) หากส่งค่าใดค่าหนึ่งเป็น `undefined` มาจาก client คอลัมน์นั้นในฐานข้อมูลจะถูกเขียนทับเป็น `NULL` ทันที ในการพัฒนาจริงควรเพิ่มการตรวจสอบ validation แบบเดียวกับ route `POST` ก่อนนำค่าไปใช้ใน query เสมอ

### 3.5 การดึงข้อมูลจากหลายตารางด้วย JOIN

สถานการณ์ที่พบบ่อยคือการดึงรายชื่อรายวิชาที่นิสิตคนหนึ่งลงทะเบียนไว้ ซึ่งข้อมูลกระจายอยู่ใน 2 ตาราง (`courses` และ `enrollments`) หากใช้ข้อมูลจำลองแบบเดิมต้อง query หรือวนลูปค้นหาแยกกันหลายครั้ง แต่เมื่อใช้ฐานข้อมูลเชิงสัมพันธ์ สามารถรวมข้อมูลจากหลายตารางได้ในคำสั่งเดียวด้วย `JOIN`

```javascript
app.get("/api/v1/students/:id/courses", async (req, res, next) => {
  try {
    const [rows] = await pool.query(
      `SELECT courses.id, courses.course_name, courses.credit
       FROM courses
       JOIN enrollments ON courses.id = enrollments.course_id
       WHERE enrollments.student_id = ?`,
      [req.params.id],
    );

    res.status(200).json({ message: "สำเร็จ", data: rows });
  } catch (err) {
    next(err);
  }
});
```

`JOIN` ในที่นี้จับคู่แถวของตาราง `courses` กับ `enrollments` โดยใช้เงื่อนไข `courses.id = enrollments.course_id` แล้วกรองด้วย `WHERE enrollments.student_id = ?` เหลือเฉพาะรายวิชาที่นิสิตคนที่ระบุลงทะเบียนไว้เท่านั้น ได้ผลลัพธ์เป็นรายชื่อรายวิชาโดยตรงในคำสั่งเดียว โดยไม่ต้อง query ตาราง `enrollments` แยกออกมาก่อนแล้วค่อยวนลูป query ตาราง `courses` ทีละรายวิชา

### 3.6 เหตุใดจึงต้องใช้ Parameterized Query

โค้ดทุกตัวอย่างข้างต้นใช้เครื่องหมาย `?` แทนที่จะนำค่าจาก `req.body` มาต่อสตริง SQL โดยตรง วิธีนี้เรียกว่า Parameterized Query (หรือ Prepared Statement) ป้องกันช่องโหว่ SQL Injection

```javascript
// อันตราย: เสี่ยงต่อ SQL Injection ห้ามใช้วิธีนี้
const query = `SELECT * FROM students WHERE email = '${req.query.email}'`;

// ปลอดภัย: ใช้ Parameterized Query
const [rows] = await pool.query("SELECT * FROM students WHERE email = ?", [
  req.query.email,
]);
```

หากใช้วิธีต่อสตริงโดยตรง ผู้ไม่หวังดีอาจส่งค่า เช่น `' OR '1'='1` เพื่อหลอกให้เงื่อนไข WHERE เป็นจริงเสมอ และดึงข้อมูลทั้งหมดออกมาได้โดยไม่ได้รับอนุญาต หรือส่งค่าที่รุนแรงกว่านั้น เช่น

```javascript
// ค่าที่ผู้ไม่หวังดีอาจส่งมาทาง req.query.email
// '; DROP TABLE students; --

// เมื่อต่อสตริงโดยตรง คำสั่ง SQL ที่รันจริงจะกลายเป็น
// SELECT * FROM students WHERE email = ''; DROP TABLE students; --'
```

เครื่องหมาย `;` ปิดคำสั่ง SELECT เดิม แล้วเปิดคำสั่ง `DROP TABLE students` ใหม่ที่ทำลายทั้งตารางทันที ส่วน `--` ทำให้ MySQL มองส่วนที่เหลือของสตริงเป็นคอมเมนต์ ไม่ก่อให้เกิด syntax error แม้ตัวอย่างนี้จะขึ้นอยู่กับสิทธิ์ของ database user ว่าอนุญาตให้รันหลายคำสั่งต่อกัน (multiple statements) หรือไม่ แต่ก็สะท้อนว่าผลกระทบของช่องโหว่นี้ไม่ได้จำกัดแค่การรั่วไหลข้อมูล (data leak) แต่รวมถึงการทำลายข้อมูลทั้งระบบได้ด้วย

**เหตุใด Parameterized Query จึงป้องกันได้**: เมื่อเรียก `pool.query(sql, values)` ไลบรารี `mysql2` จะนำค่าใน `values` มา **escape ตามกฎของ MySQL ให้ปลอดภัยก่อน แล้วจึงแทนที่ `?`** ด้วยค่าที่ escape แล้วนั้นในฝั่งไลบรารี (client-side escaping) กระบวนการ escape นี้แปลงอักขระพิเศษ เช่น `'`, `"`, `\` ให้กลายเป็นอักขระที่ MySQL ตีความว่าเป็น**ข้อมูล**เท่านั้น ไม่ใช่ส่วนหนึ่งของโครงสร้างคำสั่ง SQL ไม่ว่าค่านั้นจะมีเครื่องหมาย `'`, `;` หรือ `--` ปะปนอยู่ก็ตาม ต่างจากการต่อสตริงโดยตรงที่นำค่าดิบ (raw value) มาต่อเป็นส่วนหนึ่งของคำสั่ง SQL ทันทีโดยไม่ผ่านการ escape ทำให้เครื่องหมายพิเศษเหล่านี้มีผลเปลี่ยนโครงสร้างคำสั่งได้

> 💡 **Tip**: `mysql2` มีอีกเมธอดหนึ่งคือ `pool.execute(sql, values)` ซึ่งใช้ Prepared Statement แบบ Binary Protocol ของ MySQL จริง (ตามที่กล่าวถึงในหัวข้อ 1.2) คือส่งโครงสร้างคำสั่งกับค่าพารามิเตอร์แยกเป็นคนละส่วนไปยัง MySQL Server ให้ Server เป็นผู้ผูกค่าเอง ปลอดภัยจาก SQL Injection ด้วยกลไกเดียวกันแต่มาจากคนละขั้นตอน (server-side binding แทน client-side escaping) และมีข้อดีเพิ่มเติมด้านประสิทธิภาพเมื่อเรียก query เดิมซ้ำหลายครั้ง เอกสารนี้เลือกใช้ `pool.query()` เพราะอ่านง่ายกว่าสำหรับผู้เริ่มต้น แต่ทั้งสองเมธอดปลอดภัยจาก SQL Injection เท่ากันตราบใดที่ใช้เครื่องหมาย `?` แทนการต่อสตริง

## 4. Transaction

### 4.1 ปัญหาที่ Transaction แก้ไข

พิจารณาสถานการณ์การลงทะเบียนเรียน ซึ่งต้องดำเนินการ 2 ขั้นตอนที่เกี่ยวข้องกัน ได้แก่ (1) เพิ่มระเบียนในตาราง `enrollments` และ (2) ลดจำนวนที่นั่งว่างในตาราง `courses` หากขั้นตอนแรกสำเร็จแต่ขั้นตอนที่สองล้มเหลว (เช่น เกิดข้อผิดพลาดของระบบกะทันหัน) ข้อมูลจะไม่สอดคล้องกัน (data inconsistency) คือมีการลงทะเบียนเกิดขึ้นแต่จำนวนที่นั่งไม่ได้ถูกปรับปรุง

### 4.2 คุณสมบัติ ACID

Transaction ในฐานข้อมูลเชิงสัมพันธ์ยึดหลักคุณสมบัติ ACID

| คุณสมบัติ   | ความหมาย                                                                                        |
| ----------- | ----------------------------------------------------------------------------------------------- |
| Atomicity   | การดำเนินการทั้งหมดใน transaction ต้องสำเร็จทั้งหมดหรือย้อนกลับทั้งหมด ไม่มีสถานะครึ่งกลาง      |
| Consistency | ข้อมูลต้องอยู่ในสถานะที่ถูกต้องตามกฎเกณฑ์ (constraint) เสมอ ทั้งก่อนและหลัง transaction         |
| Isolation   | Transaction ที่ทำงานพร้อมกันต้องไม่ส่งผลกระทบต่อกันจนทำให้ข้อมูลผิดพลาด                         |
| Durability  | เมื่อ transaction สำเร็จ (commit) แล้ว ข้อมูลต้องถูกบันทึกถาวร แม้ระบบจะเกิดข้อผิดพลาดในภายหลัง |

ตัวอย่างสถานการณ์ที่คุณสมบัติแต่ละข้อมีความสำคัญ (อ้างอิงสถานการณ์การลงทะเบียนเรียนในหัวข้อ 4.1)

- **Atomicity**: หากระบบตัดไฟหรือแอปพลิเคชัน crash ระหว่างที่ INSERT เข้า `enrollments` สำเร็จแล้ว แต่ยังไม่ได้ UPDATE ลดที่นั่งใน `courses` transaction จะยังไม่ถูก commit เมื่อระบบกลับมาทำงานใหม่ การเปลี่ยนแปลงที่ค้างอยู่ (INSERT ที่ยังไม่ commit) จะไม่ปรากฏในฐานข้อมูล เสมือนไม่เคยเกิดขึ้นเลย
- **Consistency**: ตาราง `enrollments` กำหนด `FOREIGN KEY` และ `UNIQUE KEY unique_enrollment` ไว้ (หัวข้อ 3.1) หาก transaction ใดพยายาม INSERT ข้อมูลที่ละเมิด constraint เหล่านี้ (เช่น `course_id` ที่ไม่มีอยู่จริง หรือ `student_id`/`course_id` คู่ที่ซ้ำกับที่มีอยู่แล้ว) MySQL จะปฏิเสธคำสั่งนั้นทันที ทำให้ฐานข้อมูลไม่มีทางเข้าสู่สถานะที่ผิดกฎเกณฑ์ได้ไม่ว่า transaction จะ commit หรือ rollback
- **Isolation**: หากมีนิสิตสองคนกดลงทะเบียนรายวิชาเดียวกันที่เหลือที่นั่งสุดท้ายในเวลาเดียวกัน (concurrent request) กลไก Isolation ต้องรับประกันว่า transaction ทั้งสองจะไม่อ่านค่า `seat_available` เดิมพร้อมกันแล้วต่างฝ่ายต่างลดที่นั่งจนติดลบ (เช่น ที่นั่งเหลือ 1 แต่ลงทะเบียนสำเร็จทั้งคู่) คำสั่ง `SELECT ... FOR UPDATE` ที่ใช้ในหัวข้อ 4.5 ด้านล่างเป็นตัวอย่างของการล็อกแถวเพื่อรักษาคุณสมบัตินี้
- **Durability**: เมื่อ endpoint ลงทะเบียนเรียนตอบกลับ `201` และ `commit()` สำเร็จแล้ว ต่อให้ MySQL Server ปิดตัวกะทันหันในวินาทีถัดมา ข้อมูลการลงทะเบียนที่เพิ่ง commit ต้องยังอยู่ครบเมื่อเซิร์ฟเวอร์กลับมาทำงานใหม่ ผู้ใช้จึงวางใจได้ว่า response `201` ที่ได้รับมีความหมายจริง ไม่ใช่ข้อมูลที่อาจหายไปภายหลัง

### 4.3 ตัวอย่างการใช้ Transaction ด้วย mysql2

```javascript
app.post("/api/v1/students/:id/enrollments", async (req, res, next) => {
  const studentId = req.params.id;
  const { courseId } = req.body;

  const connection = await pool.getConnection();

  try {
    await connection.beginTransaction();

    // ขั้นตอนที่ 1: ตรวจสอบว่ารายวิชามีอยู่จริงก่อนดำเนินการต่อ
    const [courseRows] = await connection.query(
      "SELECT * FROM courses WHERE id = ?",
      [courseId],
    );

    if (courseRows.length === 0) {
      // หากไม่พบรายวิชา ให้ยกเลิก transaction ทันที ก่อนมีการเปลี่ยนแปลงข้อมูลใด ๆ
      await connection.rollback();
      return res.status(404).json({
        error: { code: "COURSE_NOT_FOUND", message: "ไม่พบรายวิชาที่ระบุ" },
      });
    }

    // ขั้นตอนที่ 2: รายวิชามีอยู่จริงแล้ว จึงเพิ่มระเบียนการลงทะเบียน
    await connection.query(
      "INSERT INTO enrollments (student_id, course_id) VALUES (?, ?)",
      [studentId, courseId],
    );

    // ทุกขั้นตอนสำเร็จ ยืนยันการเปลี่ยนแปลงถาวร
    await connection.commit();
    res.status(201).json({ message: "ลงทะเบียนสำเร็จ" });
  } catch (err) {
    await connection.rollback();
    next(err);
  } finally {
    connection.release(); // คืน connection กลับเข้า pool เสมอ ไม่ว่าจะสำเร็จหรือล้มเหลว
  }
});
```

### 4.4 ประเด็นสำคัญของการใช้ Transaction

1. ต้องเรียก `connection.release()` ใน block `finally` เสมอ เพื่อคืน connection กลับเข้า pool มิฉะนั้น pool จะเต็มและระบบไม่สามารถให้บริการคำขอใหม่ได้ (connection leak)
2. `rollback()` ใช้ยกเลิกการเปลี่ยนแปลงทั้งหมดที่เกิดขึ้นภายใน transaction นับตั้งแต่ `beginTransaction()` หากพบเงื่อนไขที่ไม่ควรดำเนินการต่อ
3. `commit()` ใช้ยืนยันว่าการเปลี่ยนแปลงทั้งหมดถูกต้องและบันทึกถาวร ควรเรียกเมื่อทุกขั้นตอนในกระบวนการเสร็จสมบูรณ์เท่านั้น
4. ทุก query ภายใน transaction เดียวกัน**ต้องเรียกผ่าน `connection` ที่ได้จาก `pool.getConnection()`** (เช่น `connection.query(...)`) ไม่ใช่ `pool.query(...)` โดยตรง เพราะ `pool.query()` แต่ละครั้งอาจสุ่มหยิบ connection คนละตัวจาก pool มาใช้ ทำให้คำสั่งแต่ละคำสั่งไม่ได้อยู่ใน transaction เดียวกันจริง และ `beginTransaction()`/`commit()`/`rollback()` จะไม่มีผลกับ query ที่หลุดออกไปใช้ connection อื่น
5. ควรจัดลำดับคำสั่งภายใน transaction ให้ขั้นตอนที่ตรวจสอบเงื่อนไข (เช่น ตรวจว่ารายวิชามีอยู่จริงหรือที่นั่งว่างเพียงพอ) อยู่**ก่อน**คำสั่งที่เปลี่ยนแปลงข้อมูล (INSERT/UPDATE/DELETE) เสมอ เพื่อลดจำนวนการเปลี่ยนแปลงที่ต้อง rollback และลดโอกาสชนกับ constraint ระดับฐานข้อมูลโดยไม่จำเป็น

### 4.5 ป้องกันการแย่งที่นั่งด้วย `SELECT ... FOR UPDATE`

โค้ดในหัวข้อ 4.3 ตรวจสอบแค่ว่ารายวิชามีอยู่จริงหรือไม่ ยังไม่ได้ตรวจสอบจำนวนที่นั่งว่าง เพิ่มคอลัมน์ `seat_available` เข้าไปในตาราง `courses` ก่อน

```sql
ALTER TABLE courses ADD COLUMN seat_available INT NOT NULL DEFAULT 30;
```

หากเขียนโค้ดตรวจสอบที่นั่งแบบตรงไปตรงมาโดยไม่ล็อกแถว จะเกิดปัญหา **Isolation** ตามที่อธิบายในหัวข้อ 4.2 หากมีคำขอสองคำขอเข้ามาพร้อมกันขณะที่นั่งเหลือ 1 ที่ ทั้งสอง transaction อาจ SELECT อ่านค่า `seat_available = 1` ได้พร้อมกันก่อนที่ฝ่ายใดจะ commit ทำให้ทั้งคู่ผ่านเงื่อนไข `> 0` และลงทะเบียนสำเร็จทั้งคู่ ทั้งที่มีที่นั่งจริงแค่ 1 ที่

> ⚠️ **ข้อควรระวัง**: MySQL (ใช้ storage engine InnoDB ตามค่าเริ่มต้น) กำหนดระดับ Isolation เริ่มต้นเป็น `REPEATABLE READ` ซึ่งป้องกันปัญหาบางอย่างได้เอง (เช่น non-repeatable read) แต่**ไม่ได้ป้องกัน race condition ในรูปแบบ "อ่านแล้วเขียน" (read-then-write)** อย่างสถานการณ์ที่นั่งด้านบน เพราะ SELECT ธรรมดาไม่ได้ล็อกแถวไว้ ต้องใช้ `FOR UPDATE` เพิ่มเพื่อล็อกแถวอย่างชัดเจน (explicit locking) จึงจะปิดช่องโหว่นี้ได้

คำสั่ง `FOR UPDATE` แก้ปัญหานี้โดยล็อกแถวที่ถูก SELECT ไว้จนกว่า transaction จะ `commit()` หรือ `rollback()` ทำให้ transaction ที่สองต้องรอจนกว่า transaction แรกจบก่อน จึงจะอ่านค่าที่นั่งล่าสุด (หลังถูกลดแล้ว) ได้

```javascript
app.post("/api/v1/courses/:id/enroll", async (req, res, next) => {
  const courseId = req.params.id;
  const { studentId } = req.body;

  const connection = await pool.getConnection();

  try {
    await connection.beginTransaction();

    // FOR UPDATE ล็อกแถวนี้ไว้ transaction อื่นที่พยายาม SELECT แถวเดียวกัน
    // ด้วย FOR UPDATE เช่นกัน จะต้องรอจนกว่า transaction นี้จะ commit/rollback ก่อน
    const [courseRows] = await connection.query(
      "SELECT * FROM courses WHERE id = ? FOR UPDATE",
      [courseId],
    );

    if (courseRows.length === 0) {
      await connection.rollback();
      return res.status(404).json({
        error: { code: "COURSE_NOT_FOUND", message: "ไม่พบรายวิชาที่ระบุ" },
      });
    }

    if (courseRows[0].seat_available <= 0) {
      await connection.rollback();
      return res.status(409).json({
        error: { code: "SEAT_FULL", message: "ที่นั่งเต็มแล้ว" },
      });
    }

    await connection.query(
      "INSERT INTO enrollments (student_id, course_id) VALUES (?, ?)",
      [studentId, courseId],
    );

    await connection.query(
      "UPDATE courses SET seat_available = seat_available - 1 WHERE id = ?",
      [courseId],
    );

    await connection.commit();
    res.status(201).json({ message: "ลงทะเบียนสำเร็จ" });
  } catch (err) {
    await connection.rollback();
    if (err.code === "ER_DUP_ENTRY") {
      return res.status(409).json({
        error: {
          code: "ALREADY_ENROLLED",
          message: "นิสิตลงทะเบียนรายวิชานี้ไปแล้ว",
        },
      });
    }
    next(err);
  } finally {
    connection.release();
  }
});
```

**ข้อสังเกต**: การ SELECT ตรวจสอบเงื่อนไขและ INSERT/UPDATE เปลี่ยนแปลงข้อมูลต้องอยู่ใน transaction เดียวกัน (ใช้ `connection` ตัวเดียวกันตลอด ตามข้อ 4 ในหัวข้อ 4.4) มิฉะนั้น `FOR UPDATE` จะไม่มีผลป้องกัน เพราะเป็นการล็อกที่ผูกกับ transaction ไม่ใช่ผูกกับ query เดี่ยว

### 4.6 พิสูจน์ผลของ Connection Pool และ Isolation ด้วยสคริปต์ทดสอบ

สร้างไฟล์ `test-concurrent.js` แยกต่างหาก (ไม่ต้องผ่าน HTTP endpoint) เพื่อส่ง query พร้อมกันหลายสิบครั้งไปยัง pool เดียวกัน และสังเกตผลจริงของค่า `connectionLimit`, `waitForConnections` ในหัวข้อ 2.4 และคุณสมบัติ Isolation ในหัวข้อ 4.2

```javascript
// test-concurrent.js
require("dotenv").config();
const pool = require("./db");

// จำลองเฉพาะขั้นตอนล็อกที่นั่งและลดจำนวนที่นั่ง (ไม่ INSERT enrollments จริง
// เพื่อไม่ให้ต้องสร้างนิสิต 20 คนตามใน seed data)
async function reserveSeatOnce(courseId, label) {
  const connection = await pool.getConnection();
  try {
    await connection.beginTransaction();

    const [rows] = await connection.query(
      "SELECT seat_available FROM courses WHERE id = ? FOR UPDATE",
      [courseId],
    );

    if (rows[0].seat_available <= 0) {
      await connection.rollback();
      console.log(`${label}: ที่นั่งเต็ม ไม่สามารถจองได้`);
      return;
    }

    await connection.query(
      "UPDATE courses SET seat_available = seat_available - 1 WHERE id = ?",
      [courseId],
    );
    await connection.commit();
    console.log(`${label}: จองที่นั่งสำเร็จ`);
  } catch (err) {
    await connection.rollback();
    console.log(`${label}: เกิดข้อผิดพลาด - ${err.message}`);
  } finally {
    connection.release();
  }
}

async function main() {
  // ก่อนรัน ให้ตั้งค่าที่นั่งของ courseId ที่ทดสอบเป็นจำนวนน้อย ๆ เช่น
  // UPDATE courses SET seat_available = 5 WHERE id = 1;
  const courseId = 1;

  const start = Date.now();

  // ส่ง 20 คำขอพร้อมกันไปยัง pool เดียวกัน (connectionLimit: 10 ตามหัวข้อ 2.3)
  const requests = Array.from({ length: 20 }, (_, i) =>
    reserveSeatOnce(courseId, `คำขอที่ ${i + 1}`),
  );

  await Promise.all(requests);

  console.log(`ใช้เวลารวม ${Date.now() - start} ms`);
  await pool.end();
}

main();
```

```bash
node test-concurrent.js
```

**ให้สังเกตผลลัพธ์สองอย่าง**

1. แม้ส่ง 20 คำขอพร้อมกัน แต่ `connectionLimit` มีเพียง 10 คำขอส่วนที่เกินจะไม่เกิด error ทันที (เพราะ `waitForConnections: true`) แต่จะรอคิวจนกว่าจะมี connection ว่าง สังเกตได้จากเวลารวมที่นานกว่าการส่ง 10 คำขอ
2. ตรวจสอบด้วย `SELECT seat_available FROM courses WHERE id = 1;` ผ่าน MySQL command line หลังสคริปต์ทำงานเสร็จ ค่า `seat_available` ต้องลดลงพอดีตามจำนวนคำขอที่ "จองที่นั่งสำเร็จ" เท่านั้น ไม่ลดลงเกินจำนวนที่นั่งเดิม แม้จะมีคำขอ 20 คำขอพยายามแย่งที่นั่งพร้อมกันก็ตาม (พิสูจน์ว่า `FOR UPDATE` รักษาคุณสมบัติ Isolation ได้จริง)

## สรุปเนื้อหาสำคัญ

1. Connection Pool ช่วยลดค่าใช้จ่ายในการเปิด-ปิดการเชื่อมต่อฐานข้อมูลซ้ำ ๆ โดยเตรียมการเชื่อมต่อไว้ล่วงหน้าและนำกลับมาใช้ซ้ำ
2. การดำเนินการ CRUD พื้นฐานกับ MySQL ใช้เมธอด `pool.query()` โดยควรใช้ Parameterized Query (`?`) เสมอเพื่อป้องกัน SQL Injection
3. ควรใช้ constraint ของฐานข้อมูล เช่น `UNIQUE` และ `FOREIGN KEY` เพื่อรักษาความถูกต้องของข้อมูล (data integrity) แทนที่จะพึ่งพาการตรวจสอบในโค้ดฝั่งแอปพลิเคชันเพียงอย่างเดียว
4. Transaction ยึดหลักคุณสมบัติ ACID และใช้เพื่อรับประกันว่าชุดการดำเนินการที่เกี่ยวข้องกันจะสำเร็จทั้งหมดหรือย้อนกลับทั้งหมด
5. ต้องคืน connection กลับเข้า pool ด้วย `release()` ใน block `finally` เสมอ เพื่อป้องกันปัญหา connection leak

## คำถามท้ายบท

1. จงอธิบายข้อจำกัดของการเก็บข้อมูลแบบ in-memory ที่ใช้มาตั้งแต่สัปดาห์ที่ 1 และเหตุใดจึงต้องเปลี่ยนมาใช้ฐานข้อมูลจริง
2. Connection Pool คืออะไร และเหตุใดการเปิดการเชื่อมต่อฐานข้อมูลใหม่ทุกครั้งที่มีคำขอจึงไม่เหมาะสม
3. จงอธิบายว่า Parameterized Query ป้องกัน SQL Injection ได้อย่างไร พร้อมยกตัวอย่างโค้ดที่ปลอดภัยและไม่ปลอดภัย
4. จงอธิบายคุณสมบัติ ACID ทั้ง 4 ประการ พร้อมยกตัวอย่างสถานการณ์ที่คุณสมบัติแต่ละข้อมีความสำคัญ
5. เพราะเหตุใดจึงต้องเรียก `connection.release()` ใน block `finally` เสมอ แม้ transaction จะสำเร็จหรือล้มเหลวก็ตาม
6. เพราะเหตุใดคำสั่ง `SELECT ... FOR UPDATE` ในหัวข้อ 4.5 จึงจำเป็นสำหรับการตรวจสอบที่นั่งว่างก่อนลงทะเบียน และหากตัด `FOR UPDATE` ออกจะเกิดปัญหาใดขึ้นได้เมื่อมีคำขอลงทะเบียนพร้อมกันหลายคำขอ
7. จงอธิบายว่าเหตุใดการกำหนด `UNIQUE` constraint ที่ระดับฐานข้อมูลจึงมีความน่าเชื่อถือมากกว่าการตรวจสอบข้อมูลซ้ำในโค้ดฝั่งแอปพลิเคชันเพียงอย่างเดียว
