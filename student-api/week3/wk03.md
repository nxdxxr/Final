## วัตถุประสงค์การเรียนรู้ประจำสัปดาห์

เมื่อเรียนจบเนื้อหาในสัปดาห์นี้ นิสิตจะสามารถ

1. ออกแบบ URI (Uniform Resource Identifier) สำหรับ resource ต่าง ๆ ตามหลักการตั้งชื่อที่เป็นมาตรฐานได้
2. เลือกใช้ HTTP Method ให้สอดคล้องกับการดำเนินการแต่ละประเภทได้อย่างถูกต้อง
3. เลือกใช้ HTTP Status Code ที่เหมาะสมกับผลลัพธ์ของแต่ละคำขอได้
4. อธิบายและประยุกต์ใช้หลักการ Content Negotiation ในการออกแบบ API ได้

หัวข้อนี้สอดคล้องกับ CLO3 และ CLO6

## 1. หลักการออกแบบ URI (Resource Naming)

### 1.1 แนวคิดพื้นฐาน: ทุกสิ่งคือ Resource

ตามหลักการ REST ที่กล่าวถึงในสัปดาห์ที่ 2 ทุกสิ่งในระบบถูกมองเป็น "resource" (ทรัพยากร) ซึ่งแทนด้วยคำนาม (noun) ไม่ใช่คำกริยา (verb) การออกแบบ URI ที่ดีจึงต้องสื่อถึง "สิ่งที่เข้าถึง" ไม่ใช่ "การกระทำที่จะทำ" เนื่องจากการกระทำนั้นถูกกำหนดโดย HTTP Method อยู่แล้ว

```
ไม่ควรใช้:  GET /getAllStudents
ควรใช้:     GET /students

ไม่ควรใช้:  POST /createNewStudent
ควรใช้:     POST /students

ไม่ควรใช้:  GET /deleteStudent/1
ควรใช้:     DELETE /students/1
```

### 1.2 กฎการตั้งชื่อ URI ที่เป็นมาตรฐาน

1. **ใช้คำนามพหูพจน์แทน resource collection** เช่น `/students` แทน `/student` เพื่อสื่อว่าเป็นกลุ่มของทรัพยากร
2. **ใช้ตัวพิมพ์เล็กทั้งหมด (lowercase)** และคั่นคำด้วยเครื่องหมายขีดกลาง (`-`) ไม่ใช้ underscore (`_`) หรือ camelCase

   ```
   ไม่ควรใช้:  /StudentCourses, /student_courses
   ควรใช้:     /student-courses
   ```

3. **แสดงลำดับชั้นของความสัมพันธ์ด้วยเส้นทางแบบซ้อน (nested path)** เมื่อ resource หนึ่งเป็นส่วนหนึ่งของอีก resource หนึ่ง

   ```
   GET /students/1/courses        → รายวิชาทั้งหมดของนิสิตรหัส 1
   GET /students/1/courses/101    → รายวิชารหัส 101 ของนิสิตรหัส 1
   ```

4. **ไม่ใส่นามสกุลไฟล์หรือคำกริยาใน URI** เช่น ไม่ใช้ `/students.json` หรือ `/students/search`
5. **ใช้ query string สำหรับการกรอง เรียงลำดับ หรือแบ่งหน้า** ไม่ใช่ path parameter (รายละเอียดเรื่อง pagination และ filtering จะกล่าวถึงในสัปดาห์ที่ 7)

   ```
   GET /students?major=วิทยาการคอมพิวเตอร์&sort=name
   ```

### 1.3 ตัวอย่างการออกแบบ URI สำหรับระบบจัดการนิสิต

| การดำเนินการ                 | Method | URI                             |
| ---------------------------- | ------ | ------------------------------- |
| ดึงรายชื่อนิสิตทั้งหมด       | GET    | `/api/v1/students`              |
| ดึงข้อมูลนิสิตรายบุคคล       | GET    | `/api/v1/students/{id}`         |
| เพิ่มนิสิตใหม่               | POST   | `/api/v1/students`              |
| แก้ไขข้อมูลนิสิตทั้งระเบียน  | PUT    | `/api/v1/students/{id}`         |
| แก้ไขข้อมูลนิสิตบางส่วน      | PATCH  | `/api/v1/students/{id}`         |
| ลบนิสิต                      | DELETE | `/api/v1/students/{id}`         |
| ดึงรายวิชาที่นิสิตลงทะเบียน  | GET    | `/api/v1/students/{id}/courses` |
| ลงทะเบียนรายวิชาใหม่ให้นิสิต | POST   | `/api/v1/students/{id}/courses` |

## 2. การเลือกใช้ HTTP Method อย่างถูกต้อง

### 2.1 คุณสมบัติ Safe และ Idempotent

การเลือก HTTP Method ที่ถูกต้องต้องพิจารณาคุณสมบัติ 2 ประการ

- **Safe** หมายถึง Method ที่ไม่ก่อให้เกิดการเปลี่ยนแปลงสถานะของข้อมูลบนเซิร์ฟเวอร์ (read-only)
- **Idempotent** หมายถึง ไม่ว่าจะเรียกคำขอเดิมซ้ำกี่ครั้ง ผลลัพธ์สุดท้ายของระบบจะเหมือนเดิมเสมอ

| Method | Safe   | Idempotent         | คำอธิบาย                                                                       |
| ------ | ------ | ------------------ | ------------------------------------------------------------------------------ |
| GET    | ใช่    | ใช่                | อ่านข้อมูลอย่างเดียว ไม่มีผลข้างเคียง                                          |
| POST   | ไม่ใช่ | ไม่ใช่             | สร้างข้อมูลใหม่ทุกครั้งที่เรียก เช่น เรียกซ้ำ 3 ครั้งจะได้ข้อมูลใหม่ 3 ระเบียน |
| PUT    | ไม่ใช่ | ใช่                | แทนที่ข้อมูลทั้งระเบียนด้วยค่าที่ส่งไป เรียกซ้ำผลลัพธ์เหมือนเดิม               |
| PATCH  | ไม่ใช่ | ไม่ใช่ (โดยทั่วไป) | แก้ไขข้อมูลบางส่วน ขึ้นอยู่กับการออกแบบว่าจะ idempotent หรือไม่                |
| DELETE | ไม่ใช่ | ใช่                | ลบข้อมูล เรียกซ้ำครั้งที่สองจะไม่มีผลเพิ่มเติม (ข้อมูลถูกลบไปแล้ว)             |

### 2.2 ตัวอย่างการเลือกใช้ Method ที่ถูกต้อง

```javascript
// ถูกต้อง: ใช้ PUT เพราะเป็นการแทนที่ข้อมูลทั้งระเบียน
app.put("/api/v1/students/:id", (req, res) => {
  const { name, major, email, phone } = req.body;
  // ต้องส่งข้อมูลครบทุกฟิลด์ มิฉะนั้นฟิลด์ที่ไม่ได้ส่งจะถูกลบ/รีเซ็ต
});

// ถูกต้อง: ใช้ PATCH เพราะเป็นการแก้ไขเฉพาะบางฟิลด์
app.patch("/api/v1/students/:id", (req, res) => {
  const { email } = req.body;
  // แก้ไขเฉพาะฟิลด์ email เท่านั้น ฟิลด์อื่นไม่เปลี่ยนแปลง
});
```

ข้อผิดพลาดที่พบบ่อยคือการใช้ GET เพื่อสร้างหรือลบข้อมูล เช่น `GET /students/delete/1` ซึ่งขัดกับคุณสมบัติ safe ของ GET และอาจก่อให้เกิดปัญหาด้านความปลอดภัย เนื่องจากคำขอ GET อาจถูกแคชหรือถูกเรียกซ้ำโดยไม่ตั้งใจจากเครื่องมือ เช่น web crawler

## 3. HTTP Status Code สำหรับการออกแบบ RESTful API

การเลือก Status Code ที่แม่นยำเป็นส่วนสำคัญของการออกแบบ URI Schema เนื่องจากช่วยให้ client จัดการผลลัพธ์ได้ถูกต้องโดยไม่ต้องแยกวิเคราะห์ข้อความใน body

### 3.1 Status Code ที่ควรใช้ตามสถานการณ์

| สถานการณ์                            | Status Code               | ตัวอย่าง                               |
| ------------------------------------ | ------------------------- | -------------------------------------- |
| ดึงข้อมูลสำเร็จ                      | 200 OK                    | `GET /students/1` สำเร็จ               |
| สร้างข้อมูลใหม่สำเร็จ                | 201 Created               | `POST /students` สำเร็จ                |
| ดำเนินการสำเร็จแต่ไม่มีข้อมูลส่งกลับ | 204 No Content            | `DELETE /students/1` สำเร็จ            |
| ข้อมูลที่ส่งมาไม่ถูกต้องตามรูปแบบ    | 400 Bad Request           | ส่ง `email` ที่ไม่ใช่รูปแบบอีเมล       |
| ไม่ได้ยืนยันตัวตน                    | 401 Unauthorized          | ไม่ได้แนบ token หรือ token ไม่ถูกต้อง  |
| ยืนยันตัวตนแล้วแต่ไม่มีสิทธิ์เข้าถึง | 403 Forbidden             | นิสิตพยายามเข้าถึงข้อมูลของผู้ดูแลระบบ |
| ไม่พบ resource ที่ร้องขอ             | 404 Not Found             | `GET /students/999` ที่ไม่มีในระบบ     |
| ข้อมูลขัดแย้งกับสถานะปัจจุบัน        | 409 Conflict              | สร้างนิสิตด้วยอีเมลที่มีอยู่แล้วในระบบ |
| ข้อผิดพลาดจากฝั่งเซิร์ฟเวอร์         | 500 Internal Server Error | เกิดข้อผิดพลาดที่ไม่คาดคิดขณะประมวลผล  |

### 3.2 ตัวอย่างการใช้ Status Code ในโค้ด

```javascript
app.post("/api/v1/students", (req, res) => {
  const { name, major, email } = req.body;

  // 400 Bad Request: ข้อมูลไม่ครบหรือไม่ถูกต้อง
  if (!name || !major || !email) {
    return res.status(400).json({
      message: "กรุณาระบุ name, major และ email ให้ครบถ้วน",
    });
  }

  // 409 Conflict: อีเมลซ้ำกับข้อมูลที่มีอยู่
  const duplicated = students.find((s) => s.email === email);
  if (duplicated) {
    return res.status(409).json({
      message: "อีเมลนี้มีอยู่ในระบบแล้ว",
    });
  }

  // 201 Created: สร้างข้อมูลสำเร็จ
  const newStudent = { id: nextId++, name, major, email };
  students.push(newStudent);
  res.status(201).json({ message: "เพิ่มข้อมูลสำเร็จ", data: newStudent });
});
```

### 3.3 รูปแบบมาตรฐานของ Error Response

เพื่อให้ client จัดการข้อผิดพลาดได้สม่ำเสมอ ควรกำหนดโครงสร้าง error response ให้เป็นรูปแบบเดียวกันทุก endpoint

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "กรุณาระบุ name, major และ email ให้ครบถ้วน",
    "fields": ["name", "major", "email"]
  }
}
```

การกำหนดรูปแบบ error ที่เป็นมาตรฐานเดียวกันทั้งระบบเป็นแนวปฏิบัติที่ดี ช่วยให้ client เขียนโค้ดจัดการ error ได้เพียงชุดเดียวโดยไม่ต้องแยกเงื่อนไขตาม endpoint

## 4. Content Negotiation

### 4.1 ความหมายของ Content Negotiation

Content Negotiation คือกลไกที่ client และ server ตกลงกันว่าจะแลกเปลี่ยนข้อมูลในรูปแบบใด (เช่น JSON, XML) และภาษาใด โดยอาศัย HTTP Header เป็นตัวกำหนด กลไกนี้ทำให้ API เดียวสามารถรองรับ client ที่หลากหลายได้โดยไม่ต้องสร้าง endpoint แยกสำหรับแต่ละรูปแบบข้อมูล

### 4.2 Header ที่เกี่ยวข้องกับ Content Negotiation

| Header            | ทิศทาง           | ความหมาย                                                         |
| ----------------- | ---------------- | ---------------------------------------------------------------- |
| `Accept`          | Request          | client ระบุรูปแบบข้อมูลที่ต้องการรับกลับ เช่น `application/json` |
| `Content-Type`    | Request/Response | ระบุรูปแบบของข้อมูลที่ส่งไปจริงใน body                           |
| `Accept-Language` | Request          | client ระบุภาษาที่ต้องการ เช่น `th-TH`, `en-US`                  |
| `Accept-Charset`  | Request          | client ระบุชุดตัวอักษรที่รองรับ เช่น `utf-8`                     |

### 4.3 ตัวอย่างการทำ Content Negotiation อย่างง่ายใน Express

```javascript
app.get("/api/v1/students/:id", (req, res) => {
  const id = Number(req.params.id);
  const student = students.find((s) => s.id === id);

  if (!student) {
    return res.status(404).json({ message: "ไม่พบข้อมูลนิสิต" });
  }

  // ตรวจสอบ Header Accept เพื่อเลือกรูปแบบข้อมูลที่ตอบกลับ
  res.format({
    "application/json": () => {
      res.status(200).json(student);
    },
    "text/xml": () => {
      res
        .status(200)
        .send(
          `<student><id>${student.id}</id><name>${student.name}</name></student>`,
        );
    },
    default: () => {
      res.status(406).json({ message: "รูปแบบข้อมูลที่ร้องขอไม่รองรับ" });
    },
  });
});
```

ในทางปฏิบัติสำหรับ API สมัยใหม่ นิยมใช้ JSON เป็นรูปแบบมาตรฐานเพียงรูปแบบเดียว เนื่องจากมีขนาดเล็ก อ่านง่าย และมีไลบรารีรองรับในทุกภาษาโปรแกรมมิ่ง แต่การเข้าใจหลักการ Content Negotiation ยังมีความสำคัญ โดยเฉพาะเมื่อต้องเชื่อมต่อกับระบบเดิม (legacy system) ที่ยังใช้ XML อยู่

### 4.4 Content Negotiation กับ Status Code 406

หาก client ร้องขอรูปแบบข้อมูลที่เซิร์ฟเวอร์ไม่รองรับผ่าน Header `Accept` เซิร์ฟเวอร์ควรตอบกลับด้วย Status Code `406 Not Acceptable` แทนที่จะพยายามส่งข้อมูลในรูปแบบอื่นที่ client ไม่ได้ร้องขอ เพื่อความชัดเจนและคาดเดาได้ของพฤติกรรม API

## 5. การรวมหลักการทั้งหมดเข้าด้วยกัน: ตัวอย่าง URI Schema ที่สมบูรณ์

ตารางต่อไปนี้แสดงตัวอย่าง URI Schema ของระบบจัดการนิสิตที่ประยุกต์ใช้หลักการทั้งหมดที่กล่าวถึงในสัปดาห์นี้ ได้แก่ resource naming, HTTP Method ที่ถูกต้อง และ Status Code ที่เหมาะสม

| Method | URI                             | คำอธิบาย                    | Status Code ที่เป็นไปได้ |
| ------ | ------------------------------- | --------------------------- | ------------------------ |
| GET    | `/api/v1/students`              | ดึงรายชื่อนิสิตทั้งหมด      | 200                      |
| GET    | `/api/v1/students/{id}`         | ดึงข้อมูลนิสิตรายบุคคล      | 200, 404                 |
| POST   | `/api/v1/students`              | เพิ่มนิสิตใหม่              | 201, 400, 409            |
| PUT    | `/api/v1/students/{id}`         | แก้ไขข้อมูลนิสิตทั้งระเบียน | 200, 400, 404            |
| PATCH  | `/api/v1/students/{id}`         | แก้ไขข้อมูลนิสิตบางส่วน     | 200, 400, 404            |
| DELETE | `/api/v1/students/{id}`         | ลบนิสิต                     | 204, 404                 |
| GET    | `/api/v1/students/{id}/courses` | ดึงรายวิชาที่นิสิตลงทะเบียน | 200, 404                 |
| POST   | `/api/v1/students/{id}/courses` | ลงทะเบียนรายวิชาใหม่        | 201, 400, 404, 409       |

การจัดทำตาราง URI Schema ในลักษณะนี้ก่อนเริ่มเขียนโค้ดจริง เป็นแนวปฏิบัติที่ดีที่ช่วยให้เห็นภาพรวมของ API ชัดเจนตั้งแต่ต้น และลดความขัดแย้งในการออกแบบภายหลังเมื่อต้องแก้ไขหรือเพิ่ม endpoint ใหม่

---

## สรุปเนื้อหาสำคัญ

1. URI ควรตั้งชื่อด้วยคำนามพหูพจน์ที่สื่อถึง resource ไม่ใช่คำกริยาที่สื่อถึงการกระทำ และควรแสดงความสัมพันธ์เชิงลำดับชั้นด้วย nested path
2. การเลือก HTTP Method ต้องพิจารณาคุณสมบัติ safe และ idempotent เพื่อให้ API มีพฤติกรรมที่คาดเดาได้
3. HTTP Status Code ที่ถูกต้องช่วยให้ client จัดการผลลัพธ์ได้อย่างเป็นระบบ โดยไม่ต้องพึ่งพาการวิเคราะห์ข้อความใน body เพียงอย่างเดียว
4. Content Negotiation เป็นกลไกที่ใช้ Header `Accept` และ `Content-Type` เพื่อให้ API รองรับรูปแบบข้อมูลที่หลากหลาย แม้ในทางปฏิบัติปัจจุบันจะนิยมใช้ JSON เป็นหลัก
5. การออกแบบ URI Schema ให้ครบถ้วนก่อนเริ่มพัฒนาจริง ช่วยลดความขัดแย้งในทีมและเป็นพื้นฐานของการจัดทำเอกสาร API ในลำดับถัดไป

## คำถามท้ายบท

1. จงอธิบายว่าเหตุใด URI เช่น `/getAllStudents` หรือ `/deleteStudent/1` จึงไม่สอดคล้องกับหลักการออกแบบ RESTful ที่ดี พร้อมเสนอ URI ที่ถูกต้องแทน
2. จงอธิบายความแตกต่างระหว่างคุณสมบัติ safe และ idempotent พร้อมระบุว่า POST และ PUT มีคุณสมบัติใดบ้าง
3. หากส่งคำขอ `POST /api/v1/students` ด้วยข้อมูลอีเมลที่มีอยู่แล้วในระบบ ควรตอบกลับด้วย Status Code ใด และเพราะเหตุใดจึงไม่ควรใช้ 400 Bad Request ในกรณีนี้
4. จงออกแบบ URI สำหรับดำเนินการต่อไปนี้: (ก) ดึงรายชื่ออาจารย์ผู้สอนทั้งหมด (ข) ดึงรายวิชาที่อาจารย์รหัส 5 เป็นผู้สอน (ค) ลบรายวิชารหัส 200 ออกจากอาจารย์รหัส 5
5. Content Negotiation คืออะไร และ Header ใดที่ client ใช้เพื่อระบุรูปแบบข้อมูลที่ต้องการรับกลับ
6. หากเซิร์ฟเวอร์ไม่สามารถให้ข้อมูลในรูปแบบที่ client ร้องขอผ่าน Header `Accept` ได้ ควรตอบกลับด้วย Status Code ใด
7. จงเขียนโครงสร้าง error response มาตรฐานสำหรับกรณีที่ผู้ใช้ส่งข้อมูลไม่ครบถ้วนในการสร้างรายวิชาใหม่ ซึ่งต้องมีฟิลด์ `courseCode`, `courseName` และ `credit`
