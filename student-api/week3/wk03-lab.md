# ปฏิบัติการสัปดาห์ที่ 3: ออกแบบและปรับปรุง URI Schema ให้ตรงมาตรฐาน RESTful

## วัตถุประสงค์ของปฏิบัติการ

เมื่อทำปฏิบัติการนี้เสร็จสิ้น นิสิตจะสามารถ

1. ตรวจสอบและปรับปรุง URI ของ endpoint ที่มีอยู่เดิมให้ตรงตามหลักการตั้งชื่อ RESTful ได้
2. ปรับปรุง HTTP Method และ Status Code ของ endpoint เดิมให้ถูกต้องตามสถานการณ์
3. จัดทำเอกสารตาราง URI Schema ที่สมบูรณ์สำหรับโปรเจกต์ของตนเอง
4. ตรวจสอบ (peer review) การออกแบบ URI Schema ของเพื่อนร่วมชั้นเรียน และให้ข้อเสนอแนะที่สร้างสรรค์ได้

ปฏิบัติการนี้ต่อยอดจากเนื้อหาบรรยายในเอกสาร `wk03.md` และปรับปรุงโปรเจกต์ `student-api` ที่สร้างต่อเนื่องมาจากปฏิบัติการสัปดาห์ที่ 1 และ 2 (`wk01-lab.md`, `wk02-lab.md`) เป็นพื้นฐานสำคัญของการประเมินผล CLO3 ซึ่งจัดสอบวัดผลออกแบบรวมอยู่ในคาบสอบปลายภาค สัปดาห์ที่ 16 (ดู `final-exam.md`) ตามที่กำหนดไว้ใน `course_plan.md`

## ส่วนที่ 2: กำหนด Schema ทุก Endpoint ให้ตรงมาตรฐาน (15-90 นาที)

### ขั้นตอนที่ 2.1 ตรวจสอบ Endpoint เดิมที่มีปัญหา

ก่อนแก้ไข ให้พิจารณา endpoint ที่มีอยู่แล้วในโปรเจกต์ `student-api` จากสัปดาห์ที่ 1 และระบุจุดที่ยังไม่ตรงตามมาตรฐาน RESTful โดยใช้ตารางต่อไปนี้เป็นแนวทางในการตรวจสอบ

| Endpoint เดิม                                   | ปัญหาที่พบ                                      | แนวทางแก้ไข                                                                     |
| ----------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------- |
| `GET /api/v1/students/1/full` (จาก wk02-lab)    | ชื่อ `full` เป็นคำที่ไม่สื่อถึง resource ชัดเจน | เปลี่ยนเป็นการฝัง query parameter เช่น `GET /api/v1/students/1?include=courses` |
| `POST /api/v1/students` เมื่อ email ซ้ำ ตอบ 400 | ใช้ Status Code ไม่ตรงสถานการณ์                 | เปลี่ยนเป็น 409 Conflict ตามที่กล่าวถึงใน `wk03.md`                             |
| ไม่มี endpoint สำหรับแก้ไขข้อมูลบางส่วน         | ขาด PATCH สำหรับกรณีแก้ไขทีละฟิลด์              | เพิ่ม `PATCH /api/v1/students/:id`                                              |

### ขั้นตอนที่ 2.2 ปรับปรุง Route เดิมให้ใช้ Status Code ถูกต้อง

แก้ไขไฟล์ `index.js` (หรือไฟล์ route ที่แยกไว้ หากทำแบบฝึกหัดต่อยอดของสัปดาห์ที่ 1) ในส่วน `POST /api/v1/students` ให้ตรวจสอบข้อมูลซ้ำก่อนสร้าง

```javascript
app.post("/api/v1/students", (req, res) => {
  const { name, major, email } = req.body;

  if (!name || !major || !email) {
    return res.status(400).json({
      error: {
        code: "VALIDATION_ERROR",
        message: "กรุณาระบุ name, major และ email ให้ครบถ้วน",
      },
    });
  }

  const duplicated = students.find((s) => s.email === email);
  if (duplicated) {
    return res.status(409).json({
      error: {
        code: "DUPLICATE_EMAIL",
        message: "อีเมลนี้มีอยู่ในระบบแล้ว",
      },
    });
  }

  const newStudent = { id: nextId++, name, major, email };
  students.push(newStudent);
  res.status(201).json({ message: "เพิ่มข้อมูลสำเร็จ", data: newStudent });
});
```

### ขั้นตอนที่ 2.3 เพิ่ม Route สำหรับ PATCH

เพิ่ม route ใหม่เพื่อรองรับการแก้ไขข้อมูลบางส่วน ซึ่งแตกต่างจาก PUT ที่ต้องส่งข้อมูลครบทุกฟิลด์

```javascript
app.patch("/api/v1/students/:id", (req, res) => {
  const id = Number(req.params.id);
  const student = students.find((s) => s.id === id);

  if (!student) {
    return res.status(404).json({
      error: { code: "NOT_FOUND", message: "ไม่พบข้อมูลนิสิต" },
    });
  }

  // อัปเดตเฉพาะฟิลด์ที่ส่งมา ฟิลด์อื่นคงค่าเดิมไว้
  const { name, major, email } = req.body;
  if (name !== undefined) student.name = name;
  if (major !== undefined) student.major = major;
  if (email !== undefined) student.email = email;

  res.status(200).json({ message: "แก้ไขข้อมูลสำเร็จ", data: student });
});
```

### ขั้นตอนที่ 2.4 ปรับปรุง Endpoint ที่มีชื่อไม่เป็นมาตรฐาน

แก้ไข endpoint `GET /api/v1/students/:id/full` จากสัปดาห์ที่ 2 ให้ใช้ query parameter แทนคำว่า `full` ซึ่งไม่ใช่คำนามที่สื่อถึง resource

```javascript
app.get("/api/v1/students/:id", (req, res) => {
  const id = Number(req.params.id);
  const student = students.find((s) => s.id === id);

  if (!student) {
    return res.status(404).json({
      error: { code: "NOT_FOUND", message: "ไม่พบข้อมูลนิสิต" },
    });
  }

  const shouldIncludeCourses = req.query.include === "courses";

  if (shouldIncludeCourses) {
    const studentCourses = courses.filter((c) =>
      student.courseIds.includes(c.id),
    );
    return res.status(200).json({
      message: "สำเร็จ",
      data: { ...student, courses: studentCourses },
    });
  }

  res.status(200).json({ message: "สำเร็จ", data: student });
});
```

ทดสอบทั้งสองกรณีด้วย Postman

```
GET /api/v1/students/1                  → ไม่มีข้อมูลรายวิชา
GET /api/v1/students/1?include=courses  → มีข้อมูลรายวิชาแนบมาด้วย
```

### ขั้นตอนที่ 2.5 จัดทำตาราง URI Schema ที่สมบูรณ์

จัดทำเอกสารตาราง URI Schema ของโปรเจกต์ `student-api` ทั้งหมด โดยใช้รูปแบบเดียวกับตัวอย่างในหัวข้อที่ 5 ของ `wk03.md` บันทึกเป็นไฟล์ `URI-SCHEMA.md` ในโฟลเดอร์โปรเจกต์

| Method | URI                     | คำอธิบาย                                           | Status Code ที่เป็นไปได้ |
| ------ | ----------------------- | -------------------------------------------------- | ------------------------ |
| GET    | `/api/v1/students`      | ดึงรายชื่อนิสิตทั้งหมด                             | 200                      |
| GET    | `/api/v1/students/{id}` | ดึงข้อมูลนิสิตรายบุคคล (รองรับ `?include=courses`) | 200, 404                 |
| POST   | `/api/v1/students`      | เพิ่มนิสิตใหม่                                     | 201, 400, 409            |
| PUT    | `/api/v1/students/{id}` | แก้ไขข้อมูลนิสิตทั้งระเบียน                        | 200, 400, 404            |
| PATCH  | `/api/v1/students/{id}` | แก้ไขข้อมูลนิสิตบางส่วน                            | 200, 404                 |
| DELETE | `/api/v1/students/{id}` | ลบนิสิต                                            | 200, 404                 |

### จุดตรวจสอบที่ 2

- ปรับปรุง endpoint `POST /api/v1/students` ให้ตอบ `409` เมื่ออีเมลซ้ำ และทดสอบผ่าน Postman ได้ผลลัพธ์ถูกต้อง
- เพิ่ม `PATCH /api/v1/students/:id` สำเร็จ และทดสอบว่าฟิลด์ที่ไม่ได้ส่งมายังคงค่าเดิม
- ปรับปรุง endpoint `full` เป็นการใช้ query parameter `include` เรียบร้อย
- มีไฟล์ `URI-SCHEMA.md` ที่บันทึกตาราง URI ทั้งหมดของโปรเจกต์

## ส่วนที่ 3: Peer Check และแก้ไขตามข้อเสนอแนะ (90-120 นาที)

### ขั้นตอนที่ 3.1 จับคู่ตรวจสอบงานกับเพื่อนร่วมชั้นเรียน

จับคู่กับเพื่อนในชั้นเรียน 1 คน และแลกเปลี่ยนไฟล์ `URI-SCHEMA.md` ของกันและกัน จากนั้นตรวจสอบตามหัวข้อในแบบฟอร์มต่อไปนี้

ชื่อ-นามสกุลผู้ตรวจสอบ (ผู้กรอกแบบฟอร์ม): ......................................................

| หัวข้อตรวจสอบ                                                       | ผ่าน / ไม่ผ่าน | ข้อเสนอแนะ |
| ------------------------------------------------------------------- | -------------- | ---------- |
| URI ใช้คำนามพหูพจน์ ไม่มีคำกริยาปน                                  |                |            |
| ใช้ตัวพิมพ์เล็กและขีดกลาง ไม่ใช้ camelCase หรือ underscore          |                |            |
| HTTP Method สอดคล้องกับการดำเนินการ (เช่น ไม่ใช้ GET เพื่อลบข้อมูล) |                |            |
| Status Code ครอบคลุมทั้งกรณีสำเร็จและกรณีผิดพลาด                    |                |            |
| ความสัมพันธ์ระหว่าง resource แสดงด้วย nested path อย่างเหมาะสม      |                |            |

### ขั้นตอนที่ 3.2 ทดสอบ Endpoint ของเพื่อนด้วย Postman

นำ URI Schema ของเพื่อนมาทดสอบจริงผ่าน Postman อย่างน้อย 3 endpoint โดยเน้นกรณีขอบเขต (edge case) เช่น

- เรียกข้อมูลด้วย `id` ที่ไม่มีอยู่จริง ควรได้ 404
- ส่งข้อมูลไม่ครบในการสร้างข้อมูลใหม่ ควรได้ 400
- สร้างข้อมูลซ้ำ (ถ้ามีเงื่อนไข unique) ควรได้ 409

บันทึกผลการทดสอบและข้อสังเกตเพื่อส่งกลับให้เพื่อนนำไปปรับปรุง

### ขั้นตอนที่ 3.3 แก้ไขโปรเจกต์ของตนเองตามข้อเสนอแนะที่ได้รับ

นำข้อเสนอแนะที่ได้รับจากเพื่อนกลับมาปรับปรุงโปรเจกต์ `student-api` ของตนเอง และอัปเดตไฟล์ `URI-SCHEMA.md` ให้ตรงกับโค้ดจริงหลังการแก้ไข

### จุดตรวจสอบที่ 3

- มีแบบฟอร์ม peer check ที่กรอกครบถ้วนสำหรับโปรเจกต์ของเพื่อน
- ทดสอบ edge case ทั้ง 3 กรณีข้างต้นกับ endpoint ของเพื่อน และบันทึกผลไว้
- ปรับปรุงโปรเจกต์ของตนเองตามข้อเสนอแนะอย่างน้อย 1 รายการ และปรับปรุงไฟล์ `URI-SCHEMA.md` ให้ตรงกับโค้ดล่าสุด

## ส่วนต่อยอด: แบบฝึกหัดเพิ่มเติมด้วยตนเอง

### แบบฝึกหัดที่ 1: ออกแบบ URI สำหรับ Resource ใหม่

ออกแบบและ implement URI Schema สำหรับ resource ใหม่ชื่อ `enrollments` (การลงทะเบียนเรียน) ที่แสดงความสัมพันธ์ระหว่างนิสิตและรายวิชา โดยต้องมี endpoint อย่างน้อยดังนี้

- `GET /api/v1/enrollments` — ดึงรายการลงทะเบียนทั้งหมด
- `POST /api/v1/students/{id}/enrollments` — ลงทะเบียนรายวิชาใหม่ให้นิสิต
- `DELETE /api/v1/students/{id}/enrollments/{courseId}` — ยกเลิกการลงทะเบียน

### แบบฝึกหัดที่ 2: จัดการ Error Response ให้เป็นมาตรฐานเดียวกันทั้งระบบ

สร้างฟังก์ชันช่วย (helper function) ชื่อ `sendError(res, statusCode, code, message)` เพื่อให้ทุก route ในโปรเจกต์ตอบกลับ error ด้วยโครงสร้างเดียวกัน แล้วแก้ไขทุก route ที่มีอยู่ให้เรียกใช้ฟังก์ชันนี้แทนการเขียน `res.status().json()` ซ้ำ ๆ

```javascript
function sendError(res, statusCode, code, message) {
  return res.status(statusCode).json({ error: { code, message } });
}
```

### แบบฝึกหัดที่ 3: ทดสอบคุณสมบัติ Idempotent ด้วยตนเอง

ใช้ Postman เรียก `PUT /api/v1/students/1` ด้วยข้อมูลเดิมซ้ำ 3 ครั้งติดต่อกัน แล้วตรวจสอบว่าผลลัพธ์ในระบบ (จำนวนข้อมูล ค่าของฟิลด์) เหมือนกันทุกครั้งหรือไม่ จากนั้นทำการทดลองเดียวกันกับ `POST /api/v1/students` และเปรียบเทียบผลลัพธ์ พร้อมอธิบายว่าเหตุใดผลลัพธ์จึงแตกต่างกัน

### เกณฑ์การประเมินแบบฝึกหัดต่อยอด (สำหรับนิสิตใช้ตรวจสอบตนเอง)

| รายการ         | ผ่านเกณฑ์เมื่อ                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------- |
| แบบฝึกหัดที่ 1 | ทดสอบ endpoint ของ `enrollments` ครบทั้ง 3 เส้นทางผ่าน Postman ได้ผลลัพธ์และ Status Code ถูกต้อง                  |
| แบบฝึกหัดที่ 2 | ทุก route ในโปรเจกต์เรียกใช้ `sendError` แทนการเขียน error response ซ้ำซ้อน และรูปแบบ error เหมือนกันทุก endpoint |
| แบบฝึกหัดที่ 3 | มีบันทึกผลการทดลองทั้ง PUT และ POST พร้อมคำอธิบายที่ถูกต้องเรื่อง idempotent                                      |

หมายเหตุ: แบบฝึกหัดต่อยอดนี้เป็นการเตรียมความพร้อมสำหรับเนื้อหาสัปดาห์ที่ 4 (Middleware, Basic Security & OWASP Top 10) ซึ่งจะนำ endpoint ที่ปรับปรุงในสัปดาห์นี้ไปเพิ่มชั้นการป้องกันความปลอดภัยเบื้องต้น เช่น Helmet, CORS และการจัดการ error แบบรวมศูนย์ด้วย middleware
