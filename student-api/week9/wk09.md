## วัตถุประสงค์การเรียนรู้ประจำสัปดาห์

เมื่อเรียนจบเนื้อหาในสัปดาห์นี้ นิสิตจะสามารถ

1. อธิบายความแตกต่างระหว่าง Unit Testing และ Integration Testing ได้
2. เขียนและรัน Test ด้วย Jest ตามโครงสร้าง Arrange-Act-Assert ได้
3. ใช้ Supertest ทดสอบ HTTP endpoint ของ Express API ได้โดยไม่ต้องเปิดพอร์ตจริง
4. ใช้ Mocking เพื่อแยกการทดสอบหน่วยโค้ดออกจาก dependency ภายนอก เช่น ฐานข้อมูล
5. อ่านและตีความรายงาน Test Coverage เพื่อประเมินความครอบคลุมของชุดทดสอบได้

ดูคู่มืออ้างอิงคำสั่ง Jest/Supertest ที่ใช้บ่อย (เปิดดูเวลาเขียนโค้ด ไม่ต้องไล่อ่านเนื้อหาเต็ม) ได้ที่ [ref-jest-supertest.md](ref-jest-supertest.md)

## 1. เหตุใดจึงต้องเขียนการทดสอบอัตโนมัติ

### 1.1 ปัญหาของการทดสอบด้วยมือ

การทดสอบ API ในรายวิชานี้ใช้ Postman เป็นหลักมาตลอด ซึ่งเหมาะกับการทดลองและตรวจสอบผลลัพธ์ระหว่างพัฒนา แต่มีข้อจำกัดเมื่อโปรเจกต์ใหญ่ขึ้น

| ปัญหาของการทดสอบด้วยมือ            | ผลกระทบ                                                             |
| ---------------------------------- | ------------------------------------------------------------------- |
| ต้องคลิกทดสอบซ้ำทุกครั้งที่แก้โค้ด | เสียเวลา และมักข้ามการทดสอบบาง endpoint ไปเมื่อมีเวลาจำกัด           |
| ไม่มีบันทึกว่าเคยทดสอบกรณีใดบ้าง   | ไม่ทราบว่าการแก้โค้ดครั้งใหม่ทำให้ฟีเจอร์เดิมเสียหายหรือไม่ (regression) |
| ผลการทดสอบขึ้นกับผู้ทดสอบ          | เสี่ยงต่อความคลาดเคลื่อนจากมนุษย์ (human error)                     |

Automated Testing คือการเขียนโค้ดขึ้นมาทดสอบโค้ดอีกชุดหนึ่งโดยอัตโนมัติ สามารถรันซ้ำได้ไม่จำกัดครั้งด้วยคำสั่งเดียว และให้ผลลัพธ์ที่แน่นอนตรงกันทุกครั้งที่รันด้วยเงื่อนไขเดียวกัน

### 1.2 ระดับของการทดสอบ (Testing Pyramid)

```
        /\
       /  \      E2E Testing (น้อยที่สุด, ช้าที่สุด, ครอบคลุมทั้งระบบ)
      /----\
     /      \    Integration Testing (ทดสอบหลายส่วนทำงานร่วมกัน)
    /--------\
   /          \  Unit Testing (มากที่สุด, เร็วที่สุด, ทดสอบหน่วยเล็กที่สุด)
  /------------\
```

| ระดับ                    | ทดสอบอะไร                                                | ความเร็ว  | ตัวอย่างในโปรเจกต์ `student-api`                                      |
| ------------------------ | -------------------------------------------------------- | --------- | --------------------------------------------------------------------- |
| Unit Testing             | ฟังก์ชันเดียวแบบแยกอิสระ                                 | เร็วมาก   | ทดสอบฟังก์ชัน `hashPassword` ใน `auth-helpers.js`                     |
| Integration Testing      | หลายโมดูลทำงานร่วมกัน เช่น route + middleware + database | ปานกลาง   | ทดสอบว่า `POST /api/v1/auth/login` คืน token เมื่อ credential ถูกต้อง |
| End-to-End (E2E) Testing | ทั้งระบบตั้งแต่ client ถึง database จริง                 | ช้าที่สุด | จำลองผู้ใช้เปิดเว็บ กรอกฟอร์ม แล้วตรวจสอบผลในฐานข้อมูล                |

รายวิชานี้เน้น Unit Testing และ Integration Testing เป็นหลัก เนื่องจากให้ผลตอบแทนสูงสุดเทียบกับความซับซ้อนในการติดตั้งสำหรับโปรเจกต์ขนาดเล็กถึงกลางอย่าง `student-api`

## 2. Jest พื้นฐาน

### 2.1 การติดตั้ง

```bash
npm install --save-dev jest
```

เพิ่ม script ใน `package.json`

```json
{
  "scripts": {
    "test": "jest",
    "test:watch": "jest --watch",
    "test:coverage": "jest --coverage"
  }
}
```

### 2.2 โครงสร้างไฟล์ทดสอบ

Jest จะค้นหาไฟล์ที่ลงท้ายด้วย `.test.js` หรืออยู่ในโฟลเดอร์ `__tests__` โดยอัตโนมัติ

```
student-api/
├── auth-helpers.js
├── auth-helpers.test.js
├── index.js
└── middlewares/
    └── auth.js
```

### 2.3 โครงสร้าง Arrange-Act-Assert

Test ที่ดีควรแบ่งเป็น 3 ขั้นตอนชัดเจน: **Arrange** (เตรียมข้อมูล), **Act** (เรียกใช้งานโค้ดที่ต้องการทดสอบ), **Assert** (ตรวจสอบผลลัพธ์)

```javascript
// auth-helpers.test.js
const { hashPassword, verifyPassword } = require("./auth-helpers");

describe("auth-helpers", () => {
  test("hashPassword ควรคืนค่าที่ไม่ตรงกับรหัสผ่านต้นฉบับ", async () => {
    // Arrange
    const plainPassword = "Passw0rd!";

    // Act
    const hashed = await hashPassword(plainPassword);

    // Assert
    expect(hashed).not.toBe(plainPassword);
    expect(hashed.length).toBeGreaterThan(0);
  });

  test("verifyPassword ควรคืนค่า true เมื่อรหัสผ่านถูกต้อง", async () => {
    const plainPassword = "Passw0rd!";
    const hashed = await hashPassword(plainPassword);

    const result = await verifyPassword(plainPassword, hashed);

    expect(result).toBe(true);
  });

  test("verifyPassword ควรคืนค่า false เมื่อรหัสผ่านไม่ถูกต้อง", async () => {
    const hashed = await hashPassword("Passw0rd!");

    const result = await verifyPassword("WrongPassword", hashed);

    expect(result).toBe(false);
  });
});
```

รันด้วยคำสั่ง

```bash
npm test
```

ผลลัพธ์ที่คาดหวัง

```
PASS  ./auth-helpers.test.js
  auth-helpers
    ✓ hashPassword ควรคืนค่าที่ไม่ตรงกับรหัสผ่านต้นฉบับ (65 ms)
    ✓ verifyPassword ควรคืนค่า true เมื่อรหัสผ่านถูกต้อง (58 ms)
    ✓ verifyPassword ควรคืนค่า false เมื่อรหัสผ่านไม่ถูกต้อง (60 ms)

Tests:       3 passed, 3 total
```

### 2.4 Matcher ที่ใช้บ่อย

| Matcher              | ความหมาย                                     | ตัวอย่าง                                         |
| -------------------- | -------------------------------------------- | ------------------------------------------------ |
| `toBe(value)`        | ค่าตรงกันแบบ `===` (primitive)               | `expect(status).toBe(200)`                       |
| `toEqual(value)`     | ค่าภายใน object/array ตรงกัน (deep equality) | `expect(body).toEqual({ id: 1, role: "admin" })` |
| `toBeNull()`         | ค่าเป็น `null`                               | `expect(err).toBeNull()`                         |
| `toBeGreaterThan(n)` | ค่ามากกว่าที่กำหนด                           | `expect(list.length).toBeGreaterThan(0)`         |
| `toContain(item)`    | array หรือ string มีค่านี้อยู่               | `expect(roles).toContain("admin")`               |
| `toThrow()`          | ฟังก์ชันโยน error เมื่อถูกเรียก              | `expect(() => parseToken(null)).toThrow()`       |
| `rejects.toThrow()`  | Promise ถูก reject พร้อม error               | `await expect(login()).rejects.toThrow()`        |

### 2.5 `beforeEach`/`afterEach` และ `beforeAll`/`afterAll`

Jest มี hook สำหรับเตรียมและล้างสถานะ 2 คู่ที่ความถี่ในการทำงานต่างกัน

| Hook                       | ทำงานเมื่อใด                                                        | เหมาะกับ                                                                                                        |
| -------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `beforeEach` / `afterEach` | ก่อน/หลัง **ทุก** test ใน `describe` นั้น                           | รีเซ็ตค่าที่แต่ละ test ต้องได้สถานะเริ่มต้นเหมือนกันเสมอ (test isolation) เช่นตัวอย่างด้านล่าง                  |
| `beforeAll` / `afterAll`   | ก่อน test แรกและหลัง test สุดท้าย**เพียงครั้งเดียว** ต่อ `describe` | งานที่มีต้นทุนสูงและใช้ร่วมกันได้ เช่น เปิด/ปิดการเชื่อมต่อฐานข้อมูลทดสอบ (ดูตัวอย่างการล้างข้อมูลในหัวข้อ 3.4) |

การเลือกใช้ผิดคู่ส่งผลต่างกันชัดเจน เช่น หากใช้ `beforeEach` เปิดการเชื่อมต่อฐานข้อมูลใหม่ทุก test จะทำให้ชุดทดสอบช้าลงมากโดยไม่จำเป็น ในทางกลับกันหากใช้ `beforeAll` รีเซ็ตค่าที่ควรสดใหม่ทุก test เช่นตัวแปร environment ในตัวอย่างถัดไป test ที่รันหลังอาจได้รับผลกระทบจาก test ก่อนหน้าโดยไม่ตั้งใจ

```javascript
describe("token generation", () => {
  let originalSecret;

  beforeEach(() => {
    originalSecret = process.env.JWT_SECRET;
    process.env.JWT_SECRET = "test-secret-key";
  });

  afterEach(() => {
    process.env.JWT_SECRET = originalSecret;
  });

  test("generateToken ควรสร้าง token ที่ verify กลับได้", () => {
    // ...
  });
});
```

## 3. Supertest: ทดสอบ HTTP Endpoint

### 3.1 เหตุใดจึงต้องใช้ Supertest

Jest ทดสอบฟังก์ชัน JavaScript ได้ดี แต่ endpoint ของ Express เกี่ยวข้องกับ HTTP request/response ทั้งกระบวนการ (headers, status code, body) Supertest คือไลบรารีที่ส่ง HTTP request เข้าไปยัง Express app โดยตรงในหน่วยความจำ **โดยไม่ต้องเปิดพอร์ตจริงด้วย `app.listen()`** ทำให้ทดสอบได้เร็วและไม่ชนพอร์ตกับเซิร์ฟเวอร์ที่กำลังรันอยู่

```bash
npm install --save-dev supertest
```

### 3.2 ข้อกำหนดเบื้องต้น: แยก `app` ออกจาก `app.listen()`

โครงสร้างเดิมของ `index.js` ตั้งแต่สัปดาห์ที่ 1 มักเรียก `app.listen()` ปนอยู่ในไฟล์เดียวกับการประกาศ route ทั้งหมด ซึ่งทำให้ Supertest import `app` มาทดสอบไม่ได้ (import ไฟล์แล้ว `app.listen()` จะถูกเรียกทันทีทุกครั้ง) จึงต้องแยกไฟล์ดังนี้

```javascript
// app.js — ประกาศ Express app และ route ทั้งหมด แต่ไม่เรียก listen()
const express = require("express");
const app = express();

app.use(express.json());
// ... middleware และ route ทั้งหมดจากสัปดาห์ที่ 1-7 ...

module.exports = app;
```

```javascript
// server.js — จุดเริ่มต้นจริงของแอปพลิเคชัน เรียก listen() ที่นี่เท่านั้น
const app = require("./app");
const PORT = process.env.PORT || 3000;

app.listen(PORT, () => {
  console.log(`เซิร์ฟเวอร์ทำงานที่พอร์ต ${PORT}`);
});
```

การแยกไฟล์นี้เป็นการปรับโครงสร้างเพียงครั้งเดียว ไม่กระทบ logic ของ route ใด ๆ ที่เขียนไว้ตั้งแต่สัปดาห์ก่อนหน้า

### 3.3 ตัวอย่างการทดสอบ Endpoint ด้วย Supertest

```javascript
// auth.test.js
const request = require("supertest");
const app = require("./app");

describe("POST /api/v1/auth/register", () => {
  test("ควรคืน 201 เมื่อข้อมูลถูกต้องและครบถ้วน", async () => {
    const response = await request(app)
      .post("/api/v1/auth/register")
      .send({ email: "newuser@example.com", password: "Passw0rd!" });

    expect(response.status).toBe(201);
    expect(response.body.data).toHaveProperty("id");
    expect(response.body.data.role).toBe("student");
  });

  test("ควรคืน 400 เมื่อไม่ระบุ password", async () => {
    const response = await request(app)
      .post("/api/v1/auth/register")
      .send({ email: "newuser2@example.com" });

    expect(response.status).toBe(400);
    expect(response.body.error.code).toBe("VALIDATION_ERROR");
  });
});

describe("GET /api/v1/auth/me", () => {
  test("ควรคืน 401 เมื่อไม่แนบ Authorization header", async () => {
    const response = await request(app).get("/api/v1/auth/me");

    expect(response.status).toBe(401);
    expect(response.body.error.code).toBe("NO_TOKEN");
  });
});
```

การเขียนเช่นนี้ทดสอบ endpoint ครบทั้งกระบวนการตั้งแต่ middleware (`express.json()`, `authenticateToken`) จนถึง route handler จริง จึงจัดเป็น Integration Testing

### 3.4 ปัญหาของการทดสอบชนฐานข้อมูลจริง

ตัวอย่างในหัวข้อ 3.3 เรียก route ที่เชื่อมต่อฐานข้อมูล MySQL จริง ซึ่งมีข้อควรระวัง

| ปัญหา                                         | ผลกระทบ                                                  |
| --------------------------------------------- | -------------------------------------------------------- |
| ข้อมูลทดสอบสะสมในฐานข้อมูลทุกครั้งที่รัน test | รันซ้ำแล้วชนกับ `UNIQUE` constraint ของ email เดิม       |
| Test พึ่งพาฐานข้อมูลต้องเปิดใช้งานอยู่เสมอ    | รัน test ในเครื่องอื่นหรือ CI/CD ไม่ได้หากไม่มีฐานข้อมูล |
| Test ทำงานช้าลง                               | ทุก test ต้อง round-trip ไปยังฐานข้อมูลจริง              |

มีสองแนวทางแก้ไข: (1) ใช้ฐานข้อมูลทดสอบแยกต่างหาก (เช่น `student_api_test`) ร่วมกับการล้างข้อมูลก่อน/หลังชุดทดสอบด้วย `beforeAll`/`afterAll` ดังตัวอย่างด้านล่าง หรือ (2) ใช้ Mocking ตามหัวข้อถัดไปเพื่อตัดการพึ่งพาฐานข้อมูลออกไปทั้งหมดสำหรับ Unit Test

```javascript
// __tests__/setup-test-db.js (ตัวอย่างแนวคิด ไม่ใช่โค้ดสมบูรณ์)
beforeAll(async () => {
  await pool.query("DELETE FROM users WHERE email LIKE '%@example.com'");
});

afterAll(async () => {
  await pool.query("DELETE FROM users WHERE email LIKE '%@example.com'");
  await pool.end();
});
```

## 4. Mocking

### 4.1 แนวคิดของ Mocking

Mocking คือการแทนที่ dependency จริง (เช่น การเชื่อมต่อฐานข้อมูล, การเรียก API ภายนอก) ด้วยวัตถุจำลองที่ควบคุมพฤติกรรมได้เอง เพื่อให้ Unit Test มุ่งทดสอบเฉพาะ logic ของโค้ดส่วนที่สนใจ โดยไม่ผูกกับความพร้อมใช้งานของระบบภายนอก

### 4.2 การ Mock ฟังก์ชันด้วย `jest.fn()`

```javascript
test("callback ควรถูกเรียกด้วยค่าที่ถูกต้อง", () => {
  const mockCallback = jest.fn();

  mockCallback("hello");

  expect(mockCallback).toHaveBeenCalledWith("hello");
  expect(mockCallback).toHaveBeenCalledTimes(1);
});
```

`jest.fn()` ยังกำหนดค่าที่ต้องการคืนได้ด้วย `mockReturnValue()` (ฟังก์ชัน sync) หรือ `mockResolvedValue()` (ฟังก์ชัน async ที่คืน Promise) โดยไม่ต้องมี dependency จริงมาเรียก ตัวอย่างการ mock middleware ที่ตรวจสอบสิทธิ์แล้วส่งต่อค่าไปยังฟังก์ชันถัดไป

```javascript
test("middleware ควรเรียก next() เมื่อ token ถูกต้อง", () => {
  const req = { headers: { authorization: "Bearer validtoken" } };
  const res = {
    status: jest.fn().mockReturnValue({ json: jest.fn() }),
  };
  const next = jest.fn();

  authenticateToken(req, res, next);

  expect(next).toHaveBeenCalledTimes(1);
  expect(res.status).not.toHaveBeenCalled();
});
```

ตัวอย่างนี้ mock ทั้ง `res.status` และ `next` เพราะ Express ส่งอาร์กิวเมนต์ทั้งสองมาให้ middleware เรียกใช้งาน การ mock ทำให้ทดสอบ `authenticateToken` แบบแยกอิสระได้โดยไม่ต้องสร้าง `res` ของจริงจาก Express

### 4.3 การ Mock Module ทั้งไฟล์ด้วย `jest.mock()`

ตัวอย่างการทดสอบ route `POST /api/v1/auth/login` โดย mock การเชื่อมต่อฐานข้อมูล (`pool`) เพื่อไม่ต้องพึ่งพาฐานข้อมูลจริง

```javascript
// db.js
const mysql = require("mysql2/promise");
const pool = mysql.createPool({
  /* ... การตั้งค่าจากสัปดาห์ที่ 5 ... */
});
module.exports = pool;
```

```javascript
// login.test.js
jest.mock("./db"); // แทนที่ module ./db ทั้งหมดด้วย mock อัตโนมัติ
const pool = require("./db");
const request = require("supertest");
const app = require("./app");
const { hashPassword } = require("./auth-helpers");

describe("POST /api/v1/auth/login (mocked database)", () => {
  test("ควรคืน token เมื่อ email และ password ถูกต้อง", async () => {
    const hashedPassword = await hashPassword("Passw0rd!");

    // Arrange: กำหนดให้ pool.query คืนค่าที่ต้องการโดยไม่เข้าถึงฐานข้อมูลจริง
    pool.query.mockResolvedValueOnce([
      [
        {
          id: 1,
          email: "test@example.com",
          password_hash: hashedPassword,
          role: "student",
        },
      ],
    ]);

    const response = await request(app)
      .post("/api/v1/auth/login")
      .send({ email: "test@example.com", password: "Passw0rd!" });

    expect(response.status).toBe(200);
    expect(response.body).toHaveProperty("token");
  });

  test("ควรคืน 401 เมื่อไม่พบผู้ใช้ในระบบ", async () => {
    pool.query.mockResolvedValueOnce([[]]); // ไม่พบแถวใด ๆ

    const response = await request(app)
      .post("/api/v1/auth/login")
      .send({ email: "notfound@example.com", password: "Passw0rd!" });

    expect(response.status).toBe(401);
    expect(response.body.error.code).toBe("INVALID_CREDENTIALS");
  });
});
```

> **ข้อควรระวัง**: `jest.mock("./db")` ต้องถูกเรียกที่ระดับบนสุดของไฟล์ (ไม่อยู่ใน `test()` หรือ `describe()`) เนื่องจาก Jest จะยก (hoist) คำสั่งนี้ขึ้นไปทำงานก่อนคำสั่ง `require`/`import` อื่นใดในไฟล์เสมอ

### 4.4 เมื่อใดควร Mock และเมื่อใดไม่ควร

| สถานการณ์                                                                     | คำแนะนำ                                                                                                                |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| ทดสอบ logic เพียงอย่างเดียวที่ไม่เกี่ยวกับ I/O เช่น การคำนวณ, การตรวจสอบเงื่อนไข | ไม่จำเป็นต้อง mock                                                                                                     |
| ทดสอบ route ที่เรียกฐานข้อมูล แต่ต้องการความเร็วสูงและรันได้โดยไม่มีฐานข้อมูล | ควร mock database layer                                                                                                |
| ทดสอบว่าระบบเชื่อมต่อฐานข้อมูลจริงได้ถูกต้องตาม schema                        | ไม่ควร mock (ต้องเป็น Integration Test กับฐานข้อมูลทดสอบจริงตามหัวข้อ 3.4)                                             |
| ทดสอบการเรียก External API เช่น Payment Gateway ระหว่างพัฒนา                  | ควร mock เพื่อไม่ให้ทดสอบไปเรียกระบบภายนอกจริงโดยไม่ตั้งใจ |

> เนื้อหาการเรียก External API และการจัดการความล้มเหลว (Retry, Timeout, Fallback) จะกล่าวถึงในรายละเอียดในสัปดาห์ถัดไป สัปดาห์นี้เน้นเพียงหลักการว่าควร mock เมื่อใด

## 5. Test Coverage

### 5.1 Coverage คืออะไร

Test Coverage คือสัดส่วนของโค้ดที่ถูกเรียกใช้งานระหว่างการรันชุดทดสอบทั้งหมด วัดได้หลายมิติ

| มิติ               | ความหมาย                                               |
| ------------------ | ------------------------------------------------------ |
| Statement Coverage | สัดส่วนคำสั่ง (statement) ที่ถูกรัน                    |
| Branch Coverage    | สัดส่วนเงื่อนไข (if/else, switch) ที่ถูกทดสอบครบทุกทาง |
| Function Coverage  | สัดส่วนฟังก์ชันที่ถูกเรียกอย่างน้อยหนึ่งครั้ง          |
| Line Coverage      | สัดส่วนบรรทัดโค้ดที่ถูกรัน                             |

### 5.2 การรันและอ่านรายงาน Coverage

```bash
npm run test:coverage
```

```
--------------------|---------|----------|---------|---------|-------------------
File                | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s
--------------------|---------|----------|---------|---------|-------------------
All files           |   72.5  |   58.3   |   80.0  |   72.5  |
 auth-helpers.js     |  100.0  |  100.0   |  100.0  |  100.0  |
 middlewares/auth.js |   65.0  |   50.0   |   66.7  |   65.0  | 25-31,45
--------------------|---------|----------|---------|---------|-------------------
```

คอลัมน์ `Uncovered Line #s` ระบุเลขบรรทัดที่ยังไม่มี test ใดครอบคลุมถึง ซึ่งเป็นจุดเริ่มต้นที่ดีในการเพิ่ม test case ใหม่

### 5.3 Coverage สูงไม่ได้แปลว่า Test ดี

**ข้อควรระวังสำคัญ**: ตัวเลข Coverage 100% บอกเพียงว่าโค้ดทุกบรรทัด**ถูกเรียกทำงาน**ระหว่าง test แต่ไม่ได้ยืนยันว่า test ได้ตรวจสอบ (assert) ผลลัพธ์อย่างถูกต้องครบถ้วน ตัวอย่างเช่น

```javascript
// test ที่ให้ coverage 100% แต่แทบไม่มีประโยชน์
test("authenticateToken ควรทำงานได้โดยไม่ error", () => {
  const req = { headers: { authorization: "Bearer sometoken" } };
  const res = {};
  const next = jest.fn();

  authenticateToken(req, res, next); // เรียกฟังก์ชัน แต่ไม่ตรวจสอบผลลัพธ์ใด ๆ
});
```

test ข้างต้นเรียกฟังก์ชันจริง (เพิ่ม coverage) แต่ไม่มีการ `expect()` ใด ๆ เลย จึงไม่สามารถตรวจจับได้ว่าฟังก์ชันทำงานถูกต้องหรือไม่ ดังนั้นเป้าหมายที่ถูกต้องของการเขียน test คือ**ครอบคลุมกรณีทางธุรกิจที่สำคัญให้ครบถ้วน** (เช่น กรณีสำเร็จ, กรณีข้อมูลผิดพลาด, กรณี edge case) มากกว่าการไล่ตัวเลข Coverage ให้สูงที่สุดเพียงอย่างเดียว

### 5.4 มุมมองที่เหมาะสมต่อเป้าหมาย Coverage

| แนวทาง                                                                             | คำแนะนำ                                                                 |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| ตั้งเป้า Coverage 100% ทุกไฟล์                                                     | ไม่แนะนำ อาจนำไปสู่การเขียน test ที่ไม่มีความหมายเพียงเพื่อให้ตัวเลขสูง |
| ไม่สนใจ Coverage เลย                                                               | ไม่แนะนำ เสี่ยงต่อการมี route หรือ branch สำคัญที่ไม่เคยถูกทดสอบเลย     |
| ใช้ Coverage เป็นตัวช่วยค้นหาจุดที่ขาดการทดสอบ แล้วพิจารณาความสำคัญทางธุรกิจประกอบ | แนะนำ — เป็นแนวทางที่ใช้ในแล็บสัปดาห์นี้                                |

## สรุปเนื้อหาสำคัญ

1. Automated Testing แก้ปัญหาความไม่สม่ำเสมอและความเสียเวลาของการทดสอบด้วยมือผ่าน Postman โดยแบ่งเป็น Unit, Integration และ E2E Testing ตามลำดับความครอบคลุมและความเร็ว
2. Jest ใช้โครงสร้าง Arrange-Act-Assert ในการเขียน test พร้อม matcher หลากหลายรูปแบบสำหรับตรวจสอบผลลัพธ์
3. Supertest ทดสอบ Express endpoint ได้โดยไม่ต้องเปิดพอร์ตจริง แต่ต้องแยก `app` (การประกาศ route) ออกจาก `server.js` (การเรียก `listen()`) ก่อนจึงจะ import มาทดสอบได้
4. Mocking ด้วย `jest.mock()` และ `jest.fn()` ช่วยแยก Unit Test ออกจาก dependency ภายนอกอย่างฐานข้อมูล ทำให้ test เร็วขึ้นและไม่ต้องพึ่งพาความพร้อมของระบบภายนอก
5. Test Coverage เป็นเครื่องมือช่วยค้นหาจุดที่ขาดการทดสอบ ไม่ใช่ตัวชี้วัดคุณภาพของ test โดยตรง ตัวเลข Coverage สูงไม่ได้รับประกันว่า test ได้ตรวจสอบผลลัพธ์อย่างถูกต้อง

## คำถามท้ายบท

1. จงอธิบายความแตกต่างระหว่าง Unit Testing, Integration Testing และ End-to-End Testing พร้อมยกตัวอย่างจากโปรเจกต์ `student-api`
2. เพราะเหตุใดจึงต้องแยกไฟล์ `app.js` ออกจาก `server.js` ก่อนจึงจะใช้ Supertest ทดสอบ Express endpoint ได้
3. จงอธิบายความหมายของโครงสร้าง Arrange-Act-Assert และยกตัวอย่างการเขียน test ที่ปฏิบัติตามโครงสร้างนี้
4. Mocking คืออะไร และเพราะเหตุใดการ mock การเชื่อมต่อฐานข้อมูลจึงช่วยให้ Unit Test มีประสิทธิภาพมากขึ้น
5. เพราะเหตุใด Test Coverage 100% จึงไม่ได้รับประกันว่าชุดทดสอบมีคุณภาพดี จงยกตัวอย่างประกอบ
6. จงเขียน test ด้วย Supertest สำหรับ endpoint `GET /api/v1/auth/me` เพื่อตรวจสอบว่าเมื่อแนบ token ที่ถูกต้อง ระบบคืน Status Code 200 พร้อมข้อมูลผู้ใช้
7. Statement Coverage, Branch Coverage และ Function Coverage แตกต่างกันอย่างไร
8. จงอธิบายว่าเหตุใดการทดสอบ route ที่เชื่อมต่อฐานข้อมูลจริงซ้ำหลายครั้งโดยไม่มีการล้างข้อมูล อาจทำให้ test ล้มเหลวในการรันครั้งถัดไป และมีวิธีแก้ไขอย่างไร
