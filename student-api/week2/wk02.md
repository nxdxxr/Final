## วัตถุประสงค์การเรียนรู้ประจำสัปดาห์

เมื่อเรียนจบเนื้อหาในสัปดาห์นี้ นิสิตจะสามารถ

1. อธิบายความหมายและวิวัฒนาการของมาตรฐานเว็บเซอร์วิสที่ใช้ในการพัฒนา Backend API ได้
2. เปรียบเทียบความแตกต่างระหว่าง SOAP, REST และ GraphQL ทั้งในเชิงโครงสร้าง หลักการทำงาน และข้อดีข้อเสียได้
3. วิเคราะห์และเลือกใช้มาตรฐานเว็บเซอร์วิสที่เหมาะสมกับสถานการณ์ (use case) ที่กำหนดให้ได้
4. เขียนตัวอย่าง Query และ Endpoint เบื้องต้นด้วย REST และ GraphQL ได้

หัวข้อนี้สอดคล้องกับ CLO1 และ CLO8

## 1. ความหมายของเว็บเซอร์วิส (Web Services)

เว็บเซอร์วิส (Web Service) คือระบบซอฟต์แวร์ที่ออกแบบมาเพื่อให้แอปพลิเคชันสองระบบขึ้นไปสามารถสื่อสารและแลกเปลี่ยนข้อมูลระหว่างกันผ่านเครือข่าย โดยไม่ขึ้นกับภาษาโปรแกรมมิ่งหรือแพลตฟอร์มที่ใช้พัฒนา ตัวอย่างเช่น ระบบที่พัฒนาด้วยภาษา Java สามารถเรียกใช้บริการจากระบบที่พัฒนาด้วยภาษา Python ได้ ตราบใดที่ทั้งสองฝั่งสื่อสารกันตามมาตรฐานเดียวกัน

เว็บเซอร์วิสมีความสำคัญต่อสถาปัตยกรรมซอฟต์แวร์สมัยใหม่ เนื่องจากช่วยให้ระบบสามารถแบ่งเป็นส่วนย่อย (services) ที่ทำงานร่วมกันได้ ซึ่งเป็นรากฐานของแนวคิดสถาปัตยกรรมไมโครเซอร์วิส (Microservices Architecture) ที่จะกล่าวถึงโดยละเอียดในสัปดาห์ที่ 13

มาตรฐานเว็บเซอร์วิสที่สำคัญและใช้งานแพร่หลายในปัจจุบันมี 3 รูปแบบหลัก ได้แก่ SOAP, REST และ GraphQL

## 2. SOAP (Simple Object Access Protocol)

### 2.1 หลักการทำงาน

SOAP เป็นโพรโทคอลสำหรับแลกเปลี่ยนข้อมูลเชิงโครงสร้างที่ใช้ XML เป็นรูปแบบข้อมูลหลัก ถูกพัฒนาขึ้นในช่วงปลายทศวรรษ 1990 โดยมีจุดเด่นด้านความเป็นมาตรฐานที่เข้มงวดและมีข้อกำหนดที่ชัดเจน SOAP มักทำงานร่วมกับ WSDL (Web Services Description Language) ซึ่งเป็นเอกสาร XML ที่อธิบายว่าเซอร์วิสมีฟังก์ชันใดบ้าง รับพารามิเตอร์อะไร และคืนค่าอะไร

### 2.2 โครงสร้างของ SOAP Message

ข้อความ SOAP ทุกฉบับจะห่อหุ้ม (envelope) ด้วยโครงสร้าง XML ที่มีรูปแบบตายตัว ประกอบด้วยส่วน Header (ข้อมูลเสริม เช่น การยืนยันตัวตน) และส่วน Body (ข้อมูลจริงที่ต้องการส่ง)

```xml
<?xml version="1.0"?>
<soap:Envelope
  xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
  </soap:Header>
  <soap:Body>
    <GetStudentRequest>
      <StudentId>1</StudentId>
    </GetStudentRequest>
  </soap:Body>
</soap:Envelope>
```

### 2.3 ข้อดีและข้อจำกัดของ SOAP

**ข้อดี**

- มีมาตรฐานที่เข้มงวดและชัดเจน เหมาะกับระบบที่ต้องการความน่าเชื่อถือสูง เช่น ระบบธนาคารหรือระบบประกันภัย
- รองรับ WS-Security ซึ่งเป็นมาตรฐานความปลอดภัยระดับสูงสำหรับข้อความ (message-level security)
- ทำงานได้กับหลายโพรโทคอลขนส่ง (transport protocol) ไม่จำกัดเฉพาะ HTTP

**ข้อจำกัด**

- ข้อมูลในรูปแบบ XML มีขนาดใหญ่กว่ารูปแบบอื่น ทำให้สิ้นเปลืองแบนด์วิดท์
- โครงสร้างซับซ้อนและมีขั้นตอนการพัฒนาที่ใช้เวลานานกว่ามาตรฐานอื่น
- ไม่เหมาะกับแอปพลิเคชันสมัยใหม่ที่ต้องการความเร็วและความยืดหยุ่นสูง เช่น แอปพลิเคชันมือถือ

ปัจจุบัน SOAP ยังคงพบเห็นได้ในระบบองค์กรขนาดใหญ่และหน่วยงานภาครัฐบางแห่งที่มีระบบเดิม (legacy system) อยู่แล้ว แต่ไม่เป็นที่นิยมสำหรับการพัฒนาระบบใหม่ในปัจจุบัน

## 3. REST (Representational State Transfer)

### 3.1 หลักการทำงาน

REST ไม่ใช่โพรโทคอล แต่เป็นรูปแบบสถาปัตยกรรม (architectural style) ที่กำหนดแนวทางในการออกแบบเว็บเซอร์วิสโดยอาศัยหลักการของ HTTP ที่มีอยู่แล้ว ถูกเสนอโดย Roy Fielding ในปี ค.ศ. 2000 REST มองทุกสิ่งเป็น "resource" (ทรัพยากร) ที่สามารถเข้าถึงได้ผ่าน URI (Uniform Resource Identifier) และดำเนินการผ่าน HTTP Method มาตรฐาน

รายละเอียดหลักการออกแบบ URI และการเลือกใช้ HTTP Method ตามหลัก RESTful จะกล่าวถึงอย่างละเอียดในสัปดาห์ที่ 3

### 3.2 หลักการสำคัญ 6 ประการของ REST

1. **Client-Server** — แยกส่วนของ client และ server ออกจากกันอย่างชัดเจน ทำให้พัฒนาแต่ละฝั่งได้อย่างอิสระ
2. **Stateless** — แต่ละคำขอต้องมีข้อมูลครบถ้วนในตัวเอง เซิร์ฟเวอร์ไม่จำเป็นต้องจดจำสถานะของคำขอก่อนหน้า
3. **Cacheable** — ผลลัพธ์ต้องระบุได้ว่าสามารถแคช (cache) ได้หรือไม่ เพื่อเพิ่มประสิทธิภาพ
4. **Uniform Interface** — ใช้รูปแบบการเข้าถึงทรัพยากรที่เป็นมาตรฐานเดียวกันทั่วทั้งระบบ
5. **Layered System** — สถาปัตยกรรมสามารถประกอบด้วยหลายชั้น (layer) เช่น load balancer หรือ API Gateway โดยที่ client ไม่จำเป็นต้องทราบ
6. **Code on Demand (ทางเลือก)** — เซิร์ฟเวอร์สามารถส่งโค้ดที่ execute ได้ไปยัง client เพิ่มเติม (พบได้น้อยในทางปฏิบัติ)

### 3.3 ตัวอย่าง REST API

```
GET /api/v1/students          → ดึงรายการนิสิตทั้งหมด
GET /api/v1/students/1        → ดึงข้อมูลนิสิตรหัส 1
POST /api/v1/students         → เพิ่มนิสิตใหม่
PUT /api/v1/students/1        → แก้ไขข้อมูลนิสิตรหัส 1 ทั้งระเบียน
DELETE /api/v1/students/1     → ลบข้อมูลนิสิตรหัส 1
```

ตัวอย่างผลลัพธ์ (response) ในรูปแบบ JSON

```json
{
  "id": 1,
  "name": "สมชาย ใจดี",
  "major": "วิทยาการคอมพิวเตอร์"
}
```

### 3.4 ข้อดีและข้อจำกัดของ REST

**ข้อดี**

- เรียนรู้และใช้งานง่าย เนื่องจากอาศัยหลักการของ HTTP ที่มีอยู่แล้ว
- รองรับรูปแบบข้อมูลที่หลากหลาย เช่น JSON, XML แต่ในทางปฏิบัตินิยมใช้ JSON เนื่องจากมีขนาดเล็กและอ่านง่าย
- มีเครื่องมือสนับสนุนจำนวนมาก เช่น Postman, Swagger

**ข้อจำกัด**

- ปัญหา **over-fetching** คือได้รับข้อมูลมากเกินความจำเป็น เนื่องจาก endpoint หนึ่งคืนค่าทุกฟิลด์ของ resource แม้ client ต้องการเพียงบางฟิลด์
- ปัญหา **under-fetching** คือได้รับข้อมูลไม่เพียงพอ ต้องเรียกหลาย endpoint เพื่อประกอบข้อมูลที่ต้องการ เช่น ต้องเรียก `/students/1` แล้วเรียก `/students/1/courses` ต่อ เพื่อให้ได้ข้อมูลครบ

## 4. GraphQL

### 4.1 หลักการทำงาน

GraphQL เป็นภาษา query (query language) สำหรับ API ที่พัฒนาโดย Facebook (ปัจจุบันคือ Meta) และเปิดเผยเป็นโอเพนซอร์สในปี ค.ศ. 2015 แนวคิดหลักคือให้ client เป็นผู้กำหนดโครงสร้างของข้อมูลที่ต้องการรับกลับได้เอง ผ่าน endpoint เดียว (โดยทั่วไปคือ `/graphql`) แทนที่จะมีหลาย endpoint เหมือน REST

### 4.2 โครงสร้างของ GraphQL

GraphQL มี 3 ส่วนประกอบหลัก

1. **Schema** — นิยามชนิดข้อมูล (type) และความสัมพันธ์ของข้อมูลทั้งหมดในระบบ
2. **Query** — คำขอสำหรับอ่านข้อมูล (คล้ายกับ GET ใน REST)
3. **Mutation** — คำขอสำหรับเปลี่ยนแปลงข้อมูล เช่น การสร้าง แก้ไข หรือลบ (คล้ายกับ POST, PUT, DELETE ใน REST)

### 4.3 ตัวอย่าง GraphQL Schema

```graphql
type Student {
  id: ID!
  name: String!
  major: String!
  courses: [Course!]!
}

type Course {
  id: ID!
  courseName: String!
}

type Query {
  student(id: ID!): Student
  students: [Student!]!
}

type Mutation {
  createStudent(name: String!, major: String!): Student!
}
```

### 4.4 ตัวอย่าง GraphQL Query และผลลัพธ์

คำขอ (Query) ที่ระบุเฉพาะฟิลด์ที่ต้องการ

```graphql
query {
  student(id: 1) {
    name
    courses {
      courseName
    }
  }
}
```

ผลลัพธ์ที่ได้รับกลับมีเฉพาะฟิลด์ที่ระบุไว้ในคำขอเท่านั้น

```json
{
  "data": {
    "student": {
      "name": "สมชาย ใจดี",
      "courses": [
        { "courseName": "การเขียนโปรแกรมเบื้องต้น" },
        { "courseName": "โครงสร้างข้อมูล" }
      ]
    }
  }
}
```

GraphQL แก้ปัญหา over-fetching และ under-fetching ของ REST ได้โดยตรงด้วยวิธีนี้ เพราะ client เป็นผู้กำหนดโครงสร้างข้อมูลที่ต้องการเอง และสามารถรวมข้อมูลจากหลาย resource ไว้ในคำขอเดียวได้

### 4.5 ข้อดีและข้อจำกัดของ GraphQL

**ข้อดี**

- ลดปัญหา over-fetching และ under-fetching เนื่องจาก client ควบคุมโครงสร้างข้อมูลที่ต้องการได้เอง
- ใช้ endpoint เดียวสำหรับทุกการดำเนินการ ลดความซับซ้อนในการจัดการ routing ฝั่ง client
- มีระบบ Schema ที่ชัดเจน ทำให้ตรวจสอบชนิดข้อมูล (type-checking) ได้ตั้งแต่ตอนพัฒนา

**ข้อจำกัด**

- มีความซับซ้อนในการตั้งค่าเริ่มต้นมากกว่า REST โดยเฉพาะการออกแบบ Schema ที่ดี
- การทำแคช (caching) ทำได้ยากกว่า REST เนื่องจาก REST อาศัย URL เป็นตัวระบุ cache key ได้โดยตรง ในขณะที่ GraphQL ใช้ endpoint เดียวกันทุกคำขอ
- หากออกแบบไม่ดี อาจเปิดช่องให้ client ส่ง query ที่ซับซ้อนเกินไปจนกระทบประสิทธิภาพของเซิร์ฟเวอร์

## 5. ตารางเปรียบเทียบ SOAP, REST และ GraphQL

| หัวข้อเปรียบเทียบ     | SOAP                                                          | REST                                    | GraphQL                                                  |
| --------------------- | ------------------------------------------------------------- | --------------------------------------- | -------------------------------------------------------- |
| ประเภท                | โพรโทคอล (Protocol)                                           | รูปแบบสถาปัตยกรรม (Architectural Style) | ภาษา Query (Query Language)                              |
| รูปแบบข้อมูล          | XML เท่านั้น                                                  | นิยม JSON (รองรับ XML ได้)              | JSON                                                     |
| จำนวน Endpoint        | หลาย endpoint ตามฟังก์ชัน                                     | หลาย endpoint ตาม resource              | endpoint เดียว                                           |
| ความยืดหยุ่นของข้อมูล | ต่ำ โครงสร้างตายตัว                                           | ปานกลาง ได้ข้อมูลตามที่ endpoint กำหนด  | สูง client เลือกฟิลด์เองได้                              |
| การทำแคช              | ทำได้ยาก                                                      | ทำได้ง่าย ใช้ HTTP caching มาตรฐาน      | ทำได้ยากกว่า REST                                        |
| ความปลอดภัย           | รองรับ WS-Security ระดับสูง                                   | อาศัยมาตรฐาน HTTPS และ OAuth/JWT        | อาศัยมาตรฐานเดียวกับ REST                                |
| ความเหมาะสม           | ระบบองค์กรที่ต้องการความน่าเชื่อถือสูง เช่น ธุรกรรมทางการเงิน | API ทั่วไปสำหรับเว็บและโมบายแอปพลิเคชัน | แอปพลิเคชันที่มีโครงสร้างข้อมูลซับซ้อนและหลากหลาย client |

## 6. แนวทางการเลือกมาตรฐานให้เหมาะสมกับ Use Case

การเลือกมาตรฐานเว็บเซอร์วิสควรพิจารณาจากปัจจัยต่อไปนี้

1. **ความต้องการด้านความปลอดภัยและความน่าเชื่อถือ** — หากระบบต้องการมาตรฐานความปลอดภัยระดับสูงและมีข้อกำหนดทางกฎหมายที่เข้มงวด เช่น ระบบธนาคารระหว่างองค์กร ควรพิจารณา SOAP
2. **ความหลากหลายของ client** — หากระบบต้องรองรับหลาย client ที่มีความต้องการข้อมูลแตกต่างกันมาก เช่น เว็บแอปพลิเคชัน โมบายแอปพลิเคชัน และสมาร์ตทีวี ควรพิจารณา GraphQL เนื่องจากแต่ละ client สามารถเลือกฟิลด์ข้อมูลที่ต้องการได้เอง
3. **ความเรียบง่ายและความเร็วในการพัฒนา** — หากต้องการพัฒนา API ทั่วไปที่ไม่ซับซ้อนมาก และต้องการเครื่องมือสนับสนุนที่หลากหลาย ควรพิจารณา REST ซึ่งเป็นมาตรฐานที่ได้รับความนิยมสูงสุดในปัจจุบันสำหรับ API สาธารณะ (public API)
4. **ความต้องการด้านการทำแคช** — หากระบบต้องพึ่งพาการทำแคชเพื่อเพิ่มประสิทธิภาพเป็นหลัก REST มีข้อได้เปรียบเนื่องจากใช้กลไก HTTP caching ได้โดยตรง (รายละเอียดเรื่อง Caching จะกล่าวถึงในสัปดาห์ที่ 7)

**ตัวอย่างสถานการณ์และคำแนะนำ**

| สถานการณ์                                                                               | มาตรฐานที่แนะนำ | เหตุผล                                                                               |
| --------------------------------------------------------------------------------------- | --------------- | ------------------------------------------------------------------------------------ |
| ระบบเชื่อมต่อโอนเงินระหว่างธนาคาร                                                       | SOAP            | ต้องการมาตรฐานความปลอดภัยระดับสูงและมีข้อกำหนดทางกฎหมายที่เข้มงวด                    |
| API สาธารณะสำหรับนักพัฒนาภายนอกเรียกใช้ข้อมูลสภาพอากาศ                                  | REST            | ใช้งานง่าย มีเอกสารประกอบชัดเจน และรองรับการทำแคช                                    |
| แอปพลิเคชันโซเชียลมีเดียที่ต้องแสดงข้อมูลผู้ใช้ โพสต์ และความคิดเห็นพร้อมกันในหน้าเดียว | GraphQL         | ลดจำนวนคำขอที่ต้องเรียก และลดปัญหา over-fetching/under-fetching                      |
| ระบบจัดการข้อมูลนิสิตในมหาวิทยาลัย (ตามบริบทของรายวิชานี้)                              | REST            | สมดุลระหว่างความง่ายในการพัฒนา การดูแลรักษา และการรองรับเครื่องมือทดสอบ เช่น Postman |

สำหรับเนื้อหาในรายวิชานี้ จะใช้ REST เป็นมาตรฐานหลักในการพัฒนาโครงงานตลอดภาคการศึกษา เนื่องจากเหมาะสมกับขอบเขตของเนื้อหาและเป็นมาตรฐานที่ใช้งานแพร่หลายที่สุดในอุตสาหกรรมปัจจุบัน

## สรุปเนื้อหาสำคัญ

1. เว็บเซอร์วิสเป็นกลไกที่ช่วยให้ระบบซอฟต์แวร์ต่างแพลตฟอร์มสามารถสื่อสารและแลกเปลี่ยนข้อมูลระหว่างกันได้
2. SOAP เป็นโพรโทคอลที่ใช้ XML มีมาตรฐานเข้มงวดและปลอดภัยสูง แต่มีความซับซ้อนและขนาดข้อมูลใหญ่
3. REST เป็นรูปแบบสถาปัตยกรรมที่อาศัยหลักการของ HTTP เรียนรู้ง่าย ใช้งานแพร่หลาย แต่อาจเกิดปัญหา over-fetching และ under-fetching
4. GraphQL เป็นภาษา query ที่ให้ client กำหนดโครงสร้างข้อมูลที่ต้องการเอง ผ่าน endpoint เดียว ช่วยลดปัญหาการรับข้อมูลที่ไม่ตรงความต้องการ แต่มีความซับซ้อนในการตั้งค่าและการทำแคชมากกว่า
5. การเลือกมาตรฐานที่เหมาะสมขึ้นอยู่กับปัจจัยด้านความปลอดภัย ความหลากหลายของ client ความเรียบง่ายในการพัฒนา และความต้องการด้านการทำแคช

## คำถามท้ายบท

1. จงอธิบายความแตกต่างระหว่างคำว่า "โพรโทคอล" (Protocol) และ "รูปแบบสถาปัตยกรรม" (Architectural Style) พร้อมระบุว่า SOAP และ REST จัดอยู่ในประเภทใด
2. เพราะเหตุใด SOAP จึงยังคงใช้งานอยู่ในระบบธนาคารและหน่วยงานภาครัฐบางแห่ง แม้จะมีความซับซ้อนมากกว่า REST และ GraphQL
3. จงอธิบายปัญหา over-fetching และ under-fetching ที่พบใน REST API พร้อมยกตัวอย่างสถานการณ์ที่เกิดปัญหานี้
4. GraphQL แก้ปัญหาที่กล่าวถึงในข้อ 3 ได้อย่างไร จงอธิบายพร้อมยกตัวอย่างประกอบ
5. จงเขียน GraphQL Query เพื่อดึงข้อมูลนิสิตที่มี `id` เท่ากับ 2 โดยต้องการเฉพาะฟิลด์ `name` และ `major` เท่านั้น
6. หากต้องพัฒนาระบบ API สาธารณะสำหรับให้นักพัฒนาภายนอกเรียกใช้ข้อมูลสภาพอากาศแบบง่าย ควรเลือกใช้มาตรฐานใดระหว่าง SOAP, REST และ GraphQL พร้อมให้เหตุผลประกอบ
7. เพราะเหตุใดการทำแคช (caching) ใน GraphQL จึงทำได้ยากกว่า REST
