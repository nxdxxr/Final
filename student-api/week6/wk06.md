## วัตถุประสงค์การเรียนรู้ประจำสัปดาห์

เมื่อเรียนจบเนื้อหาในสัปดาห์นี้ นิสิตจะสามารถ

1. อธิบายความแตกต่างระหว่าง Authentication และ Authorization ได้
2. อธิบายวงจรชีวิต (lifecycle) ของ JWT (JSON Web Token) ตั้งแต่การออก token จนถึงการตรวจสอบ token ได้
3. ออกและตรวจสอบ JWT ด้วยไลบรารี `jsonwebtoken` ได้อย่างถูกต้อง
4. เข้ารหัสรหัสผ่านด้วย `bcrypt` เพื่อป้องกันการจัดเก็บรหัสผ่านแบบ plain text ได้
5. ออกแบบและ implement ระบบควบคุมสิทธิ์ตามบทบาท (Role-Based Access Control หรือ RBAC) ได้

หัวข้อนี้สอดคล้องกับ CLO1 และ CLO4

ดูคู่มืออ้างอิงคำสั่ง `jsonwebtoken`/`bcrypt` ที่ใช้บ่อย (เปิดดูเวลาเขียนโค้ด ไม่ต้องไล่อ่านเนื้อหาเต็ม) ได้ที่ [ref-jwt-bcrypt.md](ref-jwt-bcrypt.md)

## 1. Authentication และ Authorization

### 1.1 ความแตกต่างระหว่างสองแนวคิด

แม้คำสองคำนี้มักถูกใช้ปนกัน แต่มีความหมายต่างกันอย่างชัดเจน

| แนวคิด                               | คำถามที่ตอบ                   | ตัวอย่าง                                                                              |
| ------------------------------------ | ----------------------------- | ------------------------------------------------------------------------------------- |
| **Authentication** (การพิสูจน์ตัวตน) | "คุณเป็นใคร"                  | ผู้ใช้เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน                                                 |
| **Authorization** (การตรวจสอบสิทธิ์) | "คุณมีสิทธิ์ทำสิ่งนี้หรือไม่" | ตรวจสอบว่าผู้ใช้ที่ล็อกอินแล้วมีบทบาทเป็น "ผู้ดูแลระบบ" หรือไม่ ก่อนอนุญาตให้ลบข้อมูล |

ระบบ API ที่ปลอดภัยต้องมีทั้งสองกลไกทำงานร่วมกัน โดย Authentication เกิดขึ้นก่อนเสมอ เนื่องจากต้องทราบว่า "ใคร" กำลังร้องขอ ก่อนจะตัดสินว่า "อนุญาตหรือไม่" (ตรงกับความเสี่ยงประเภท Authentication Failures หรือ A07 ใน OWASP Top 10:2025)

ในเชิง HTTP มาตรฐาน ความแตกต่างนี้สะท้อนออกมาเป็น Status Code สองรหัสที่มักถูกใช้สลับกันผิด

| สถานการณ์                                                         | Status Code ที่ถูกต้อง | เหตุผล                        |
| ----------------------------------------------------------------- | ---------------------- | ----------------------------- |
| ไม่ได้แนบ token หรือ token ไม่ถูกต้อง/หมดอายุ (ไม่ทราบว่าเป็นใคร) | `401 Unauthorized`     | ล้มเหลวที่ขั้น Authentication |
| แนบ token ถูกต้อง ทราบว่าเป็นใคร แต่ไม่มีสิทธิ์ทำสิ่งที่ร้องขอ    | `403 Forbidden`        | ล้มเหลวที่ขั้น Authorization  |

> **หมายเหตุ**: ชื่อ `401 Unauthorized` ทำให้เข้าใจผิดได้ง่ายว่าเกี่ยวกับสิทธิ์ (authorization) แต่ตามข้อกำหนด RFC 7235 แล้ว `401` หมายถึงปัญหาการพิสูจน์ตัวตนเท่านั้น ส่วน `403` (RFC 9110) จึงเป็นรหัสที่ถูกต้องสำหรับกรณี "รู้ว่าเป็นใครแล้ว แต่ไม่มีสิทธิ์"

### 1.2 แนวทาง Authentication ที่พบบ่อย

| แนวทาง                                  | คำอธิบาย                                                                                                             |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| [Session-based](wk06-session-based.md)  | เซิร์ฟเวอร์เก็บสถานะการล็อกอินไว้ (session) และส่ง session ID กลับให้ client เก็บใน cookie                           |
| Token-based (JWT)                       | เซิร์ฟเวอร์ออก token ที่บรรจุข้อมูลผู้ใช้ไว้ในตัวเอง client แนบ token มากับทุกคำขอ โดยเซิร์ฟเวอร์ไม่ต้องเก็บสถานะไว้ |

รายวิชานี้ใช้แนวทาง Token-based ด้วย JWT เนื่องจากสอดคล้องกับคุณสมบัติ Stateless ของ REST กล่าวคือเซิร์ฟเวอร์ไม่จำเป็นต้องจดจำสถานะของผู้ใช้ไว้ในหน่วยความจำหรือฐานข้อมูล ทำให้ระบบขยายขนาด (scale) ได้ง่ายกว่า (ดูรายละเอียดเชิงลึกของ Session-based Authentication และการเปรียบเทียบกับ JWT ในเอกสารเสริม [wk06-session-based.md](wk06-session-based.md))

## 2. JWT (JSON Web Token)

### 2.0 JWT คืออะไร

#### ความหมายพื้นฐาน

JWT (JSON Web Token) เป็นมาตรฐาน (RFC 7519) สำหรับการแสดงข้อมูลที่ถูกลงนาม (digitally signed) ในรูปแบบ URL-safe string ประกอบด้วยข้อมูลของผู้ใช้ (เช่น id, email, role) ซึ่งเซิร์ฟเวอร์ออกให้หลังจากผู้ใช้พิสูจน์ตัวตนสำเร็จ (เช่น กรอกอีเมลและรหัสผ่านถูก) ผู้ใช้จะแนบ token นี้มากับคำขอต่อมา เซิร์ฟเวอร์ก็สามารถยืนยันว่า request นั้นมาจากใครตามข้อมูลใน token ได้โดยไม่ต้องเก็บสถานะ (stateless)

#### ความแตกต่างจาก Session-based Authentication

ในระบบ Session-based ที่กล่าวถึงในหัวข้อ 1.2:

- เซิร์ฟเวอร์จะจดจำว่า "ผู้ใช้ ID 5 ล็อกอินแล้ว" ไว้ในหน่วยความจำหรือฐานข้อมูล
- ผู้ใช้ได้รับ session ID (เช่น `abc123`) กลับมา
- ผู้ใช้แนบ session ID นั้นมากับคำขอต่อมา (ใน cookie หรือ header)
- เซิร์ฟเวอร์ค้นในรายการ session ว่า session `abc123` เป็นของผู้ใช้คนใด แล้วจึงดำเนินการตามที่ร้องขอ

ส่วน JWT ทำงานแตกต่างออกไปดังนี้

- เซิร์ฟเวอร์ออก token ที่เข้ารหัสแบบ Base64 และเซ็นด้วย secret key ให้
- **ตัว token เอง**เก็บข้อมูล "ผู้ใช้ ID 5 บทบาท student" ไว้ในตัวแล้ว
- เซิร์ฟเวอร์ไม่ต้องเก็บรายชื่อ token ไว้
- เมื่อ token มาถึง เซิร์ฟเวอร์เพียงยืนยันลายเซ็น (signature) แล้วแยกข้อมูลออกมาอ่าน

#### ตัวอย่างการใช้งานจริง

```
1. ผู้ใช้ส่ง POST /api/v1/auth/login { email, password }

                          │
                          ▼
3. ถ้าถูก ออก JWT เช่น: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6NSwicm9sZSI6InN0dWRlbnQifQ.xxxxx
                          │
                          ▼
4. ผู้ใช้เก็บ token ใน localStorage/memory
                          │
                          ▼
5. ผู้ใช้ส่ง GET /api/v1/students/1
   Header: Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpZCI6NSwicm9sZSI6InN0dWRlbnQifQ.xxxxx
                          │
                          ▼
6. เซิร์ฟเวอร์ตรวจสอบ signature ด้วย secret key
   หากถูกต้อง จะดึงข้อมูล id=5, role="student" จาก payload มาใช้ได้ทันที ไม่ต้องค้นในฐานข้อมูลว่า token นี้อยู่ใน valid list หรือไม่
```

#### ลักษณะพิเศษของ JWT

| ลักษณะ             | คำอธิบาย                                                                    |
| ------------------ | --------------------------------------------------------------------------- |
| **Stateless**      | เซิร์ฟเวอร์ไม่ต้องเก็บรายชื่อ token ที่ออกไปแล้ว ทำให้ง่ายต่อการ scale      |
| **Self-contained** | ข้อมูลของผู้ใช้อยู่ในตัว token ไม่ต้องค้นในฐานข้อมูลทุกครั้ง                |
| **URL-safe**       | เป็นสตริงที่สามารถส่ง URL ผ่าน query string หรือ header ได้โดยปลอดภัย       |
| **ถอดรหัสอ่านได้** | Header และ Payload ใช้ Base64URL ถอดรหัสแล้วอ่านได้เสมอ (ไม่ใช่ encryption) |
| **ลงนามได้**       | Signature ยืนยันว่าข้อมูลไม่ถูกดัดแปลง แต่ไม่ได้เป็นความลับ                 |

#### โครงสร้างคร่าว

JWT ประกอบด้วย 3 ส่วนคั่นด้วยจุด (`.`):

```
[Header].[Payload].[Signature]
```

- **Header**: บอกว่าใช้อัลกอริทึมอะไรไปเซ็น (เช่น HS256)
- **Payload**: ข้อมูลที่ต้องการเก็บ (เช่น `{"id": 5, "role": "student"}`)
- **Signature**: ลายเซ็นคำนวณจาก header + payload + secret key เพื่อป้องกันดัดแปลง

หากผู้ไม่หวังดีแก้ไข payload (เช่น เปลี่ยน `role` จาก `student` เป็น `admin`) signature จะไม่ตรงกับ secret key อีกต่อไป เซิร์ฟเวอร์จะปฏิเสธทันที

> **ข้อสำคัญ**: JWT **ไม่ได้ป้องกันความลับ** (confidentiality) เพราะ payload อ่านได้โดยไม่ต้องมี secret key จึงห้ามใส่ข้อมูลอ่อนไหว เช่น รหัสผ่าน บัญชีธนาคาร ลงใน payload อ่านละเอียดในหัวข้อ 2.2

### 2.2 โครงสร้างของ JWT

JWT ประกอบด้วย 3 ส่วน คั่นด้วยจุด (`.`) ในรูปแบบ `header.payload.signature`

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJpZCI6MSwicm9sZSI6InN0dWRlbnQiLCJpYXQiOjE2ODAwMDAwMDB9
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

| ส่วน      | เนื้อหา                                                                            | ตัวอย่าง                                          |
| --------- | ---------------------------------------------------------------------------------- | ------------------------------------------------- |
| Header    | ระบุอัลกอริทึมที่ใช้เข้ารหัสลายเซ็น                                                | `{"alg": "HS256", "typ": "JWT"}`                  |
| Payload   | ข้อมูล (claims) ที่ต้องการฝังไว้ใน token                                           | `{"id": 1, "role": "student", "iat": 1680000000}` |
| Signature | ลายเซ็นที่คำนวณจาก header, payload และ secret key เพื่อยืนยันว่า token ไม่ถูกแก้ไข | (ค่าที่คำนวณได้)                                  |

#### 2.2.1 Standard Claims (Registered Claims)

Payload มักมี claims มาตรฐานตามมาตรฐาน RFC 7519 ดังต่อไปนี้ (นอกจากข้อมูลที่กำหนดเอง เช่น `id`, `role` ฯลฯ)

| Claim | ชื่อเต็ม        | ความหมาย                                 | ตัวอย่าง                            |
| ----- | --------------- | ---------------------------------------- | ----------------------------------- |
| `iss` | Issuer          | เซิร์ฟเวอร์ที่ออก token                  | `"iss": "https://auth.example.com"` |
| `aud` | Audience        | ใครสามารถใช้ token นี้ได้ (อาจมีหลายค่า) | `"aud": "api.example.com"`          |
| `sub` | Subject         | ประเภท/ID ของ entity ที่ token หมายถึง   | `"sub": "5"` (user ID 5)            |
| `exp` | Expiration Time | เวลาหมดอายุ (Unix timestamp)             | `"exp": 1686295142`                 |
| `iat` | Issued At       | เวลาออก token (Unix timestamp)           | `"iat": 1686208742`                 |
| `nbf` | Not Before      | เวลาที่เร็วที่สุดที่ token ถือว่า valid  | `"nbf": 1686208742`                 |
| `jti` | JWT ID          | ID เฉพาะตัวของ token (ใช้ในการเพิกถอน)   | `"jti": "a1b2c3d4e5f6g7h8"`         |

**ความสำคัญ**:

- `exp` ช่วยจำกัดหน้าต่างเวลาที่ token ที่หลุดไปยังใช้งานได้
- `iat` และ `nbf` ช่วยตรวจสอบว่า token ยังไม่เสื่อมเสีย
- `jti` ใช้ในการ revoke token (อ่านหัวข้อ 2.7)

#### 2.2.2 ตัวอย่าง JWT จริงจากเครื่องมือออนไลน์

JWT ที่สร้างจากเครื่องมือ [JWT Generator](https://www.jwt.io/) มักมีรูปแบบซับซ้อนกว่าตัวอย่างธรรมชาติในเนื้อหา ตัวอย่างจริง:

**Header** (ถูกเข้ารหัส Base64URL):

```json
{
  "typ": "at+jwt",
  "alg": "ES256",
  "kid": "a2a4ec577eee2d77a3fc284c1d7054b"
}
```

**Payload** (ถูกเข้ารหัส Base64URL):

```json
{
  "iss": "https://idp.local",
  "aud": "api1",
  "sub": "5be63359073c434ba0dda3932222dabe",
  "client_id": "my_client_app",
  "exp": 1786295142,
  "iat": 1786946542,
  "jti": "701b6887dbdf53f01e209c7466d012b"
}
```

**Signature** (คำนวณจาก header + payload + secret):

```
8c1d3eKf2WxP9Qm4Ln5Rt6Uv7Wx8Yz9Ab0Cd1Ef2Gh3Ij4Kl5Mn6Op7Qr8St9Uv...
```

**สังเกตความแตกต่างจากตัวอย่าง**:

- Header ใช้ `"typ": "at+jwt"` แทน `"typ": "JWT"` (บอกว่าเป็น access token)
- Header ใช้ `"alg": "ES256"` แทน `HS256` (asymmetric key แทน symmetric)
- Header มี `"kid"` (Key ID) — อ้างอิงถึง public key ที่ server ใช้ยืนยัน signature
- Payload มี claims มาตรฐานบางส่วนเท่านั้น (ไม่มี `role` เพราะเป็น access token ไม่ใช่ identity token)
- `exp` มีค่ามากกว่า `iat` ประมาณ 1000 วินาที (ประมาณ 17 นาที)

**วิธีทดลองด้วยตัวเอง**:

1. ไปที่ https://jwt.io หรือ JWT Generator ด้านบน
2. ทดลองแก้ payload (เช่น เปลี่ยน `exp` เป็นค่าอื่น)
3. สังเกตว่า signature เปลี่ยนทันที แสดงว่า signature ขึ้นอยู่กับ payload
4. ทดลองแนบ token นี้ไปยังเซิร์ฟเวอร์ เซิร์ฟเวอร์จะปฏิเสธเพราะ signature ไม่ตรง

> **คำเตือน**: ห้ามนำ JWT ของจริงจากระบบที่ใช้งานจริงไปวางในเครื่องมือออนไลน์เหล่านี้ เพราะ secret key อาจถูกเปิดเผย

#### 2.2.3 อัลกอริทึมที่ใช้เซ็น JWT (Signing Algorithms)

RFC 7518 กำหนดอัลกอริทึมหลายตัวที่สามารถใช้เซ็น JWT ได้ สามารถจำแนกเป็น 2 ประเภทหลัก ตามประเภท key ที่ใช้

| อัลกอริทึม | ประเภท Key                     | ความหมาย                                                             | ข้อดี                                                     | ข้อจำกัด                                                                 | ใช้งานอยู่ที่                                             |
| ---------- | ------------------------------ | -------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------- |
| **HS256**  | Symmetric (HMAC-SHA256)        | Server เก็บ secret key เดียว ใช้เซ็นและตรวจสอบทั้งคู่                | เรียบง่าย ประมวลผลเร็ว                                    | Secret key ต้องเก็บไว้ที่ server เท่านั้น ไม่สามารถให้ client ตรวจสอบได้ | ระบบ single-server หรือ microservices ที่มี shared secret |
| **RS256**  | Asymmetric (RSA-SHA256)        | Server เก็บ private key เซ็น client/verifier เก็บ public key ตรวจสอบ | Public key สามารถแจกจ่ายได้อย่างสาธารณะ ปลอดภัยกว่า HS256 | ประมวลผลช้ากว่า HS256 key size ใหญ่                                      | OAuth 2.0 Authorization Servers, OpenID Connect           |
| **ES256**  | Asymmetric (ECDSA-SHA256)      | ใช้ Elliptic Curve Cryptography แทน RSA                              | Key size เล็กกว่า RS256 ประมวลผลเร็วกว่า                  | อาจไม่รองรับใน library เก่า ๆ บางตัว                                     | Modern API authentication, JWT ที่ต้องประสิทธิภาพสูง      |
| **PS256**  | Asymmetric (RSA-PSS-SHA256)    | Variant ของ RS256 ที่ใช้ PSS padding                                 | ปลอดภัยกว่า RS256 ตามหลักการเข้ารหัส                      | ประมวลผลช้ากว่า RS256                                                    | ระบบที่มีความต้องการความปลอดภัยสูง                        |
| **EdDSA**  | Asymmetric (Edwards-curve DSA) | ใช้ Curve25519 หรือ Curve448                                         | ปลอดภัย ประมวลผลเร็ว key size เล็ก                        | รองรับน้อยกว่า RS256/ES256 ในไลบรารีเก่า                                 | Modern cryptography applications                          |

**การเลือกอัลกอริทึม**:

- **HS256**: ใช้เมื่อระบบเป็น single-server หรือ microservices ที่ share secret key ได้อย่างปลอดภัย (รายวิชานี้ใช้ HS256 สำหรับความเรียบง่าย)
- **RS256 / ES256**: ใช้เมื่อต้องให้ client หรือ external service ตรวจสอบ JWT ด้วย public key โดยไม่ต้องเก็บ secret key (แนวทาง OAuth 2.0, OpenID Connect)
- **PS256 / EdDSA**: ใช้เมื่อระบบต้องการความปลอดภัยที่เข้มงวดหรือประสิทธิภาพสูงมาก (ข้อจำกัด: ไลบรารี JavaScript บางตัวอาจยังไม่รองรับ EdDSA อย่างสมบูรณ์)

**ตัวอย่างการใช้อัลกอริทึมต่าง ๆ ใน Node.js**:

```javascript
const jwt = require("jsonwebtoken");
const fs = require("fs");

// HS256 (Symmetric) — ใช้ string secret เท่านั้น
const hs256Token = jwt.sign({ id: 1, role: "student" }, "my-secret-key-here", {
  algorithm: "HS256",
  expiresIn: "1h",
});

// RS256 (Asymmetric) — ต้องมี private key สำหรับเซ็น
const privateKey = fs.readFileSync("private.pem", "utf8");
const rs256Token = jwt.sign({ id: 1, role: "student" }, privateKey, {
  algorithm: "RS256",
  expiresIn: "1h",
});

// ES256 (Asymmetric ECDSA) — ต้องมี private key ของ EC
const ecPrivateKey = fs.readFileSync("ec-private.pem", "utf8");
const es256Token = jwt.sign({ id: 1, role: "student" }, ecPrivateKey, {
  algorithm: "ES256",
  expiresIn: "1h",
});

// ตรวจสอบ token ด้วย public key (สำหรับ RS256 / ES256)
const publicKey = fs.readFileSync("public.pem", "utf8");
try {
  const decoded = jwt.verify(rs256Token, publicKey, { algorithms: ["RS256"] });
  console.log("Token ถูกต้อง:", decoded);
} catch (err) {
  console.error("Token ไม่ถูกต้อง:", err.message);
}
```

> **หมายเหตุสำหรับ asymmetric algorithms**: เมื่อใช้ RS256, ES256, PS256, หรือ EdDSA ต้องมีไฟล์ key ที่สร้างด้วยคำสั่ง OpenSSL (เช่น `openssl genrsa -out private.pem 2048` สำหรับ RS256) นิสิตไม่ต้องใช้ asymmetric algorithms ในแล็บสัปดาห์นี้ แต่ควรทราบว่ามีอยู่ เพื่อเลือกใช้ได้เมื่อต้องการแชร์ public key กับ external services ต่อไป

> **ข้อควรระวังสำคัญที่สุดของบทนี้**
> Header และ Payload เป็นเพียงการเข้ารหัสแบบ Base64URL (ไม่ใช่การเข้ารหัสลับ/encryption) ซึ่ง **ถอดรหัสอ่านได้โดยไม่ต้องมี secret key** ใครก็ตามที่มี token สามารถนำไปวางที่ https://jwt.io เพื่ออ่าน payload ได้ทันที จึงห้ามใส่ข้อมูลอ่อนไหว เช่น รหัสผ่าน เลขบัตรประชาชน หรือข้อมูลลับทางธุรกิจ ลงใน payload ของ JWT โดยเด็ดขาด สิ่งที่ทำให้ JWT เชื่อถือได้คือ **Signature** ซึ่งใช้ยืนยันว่าข้อมูลใน token ไม่ถูกดัดแปลงเท่านั้น (integrity) ไม่ได้ทำให้ข้อมูลนั้นเป็นความลับ (confidentiality) — นิสิตที่สับสนสองคุณสมบัตินี้มักเข้าใจผิดว่า "เมื่อเซ็นแล้วจะปลอดภัย" ทั้งที่ payload ยังคงอ่านได้

ทดลองพิสูจน์ได้ด้วยตนเองโดยไม่ต้องใช้ secret key

```bash
node -e "console.log(Buffer.from('eyJpZCI6MSwicm9sZSI6InN0dWRlbnQiLCJpYXQiOjE2ODAwMDAwMDB9', 'base64url').toString())"
# ผลลัพธ์: {"id":1,"role":"student","iat":1680000000}
```

```bash
npm install jsonwebtoken bcrypt
```

- `jsonwebtoken` ใช้สำหรับสร้างและตรวจสอบ JWT
- `bcrypt` ใช้สำหรับเข้ารหัส (hash) รหัสผ่านก่อนบันทึกลงฐานข้อมูล

### 2.4 การเข้ารหัสรหัสผ่านด้วย bcrypt

```javascript
const bcrypt = require("bcrypt");

const SALT_ROUNDS = 10;

async function hashPassword(plainPassword) {
  return await bcrypt.hash(plainPassword, SALT_ROUNDS);
}

async function verifyPassword(plainPassword, hashedPassword) {
  return await bcrypt.compare(plainPassword, hashedPassword);
}
```

`bcrypt` ใช้เทคนิค salt เพื่อให้รหัสผ่านที่เหมือนกันของผู้ใช้สองคนได้ค่า hash ที่แตกต่างกัน ป้องกันการโจมตีด้วยตาราง rainbow table ค่า `SALT_ROUNDS` ยิ่งสูงยิ่งปลอดภัยแต่ใช้เวลาประมวลผลนานขึ้น ค่า 10 เป็นค่าที่สมดุลระหว่างความปลอดภัยและประสิทธิภาพสำหรับการใช้งานทั่วไป

### 2.5 การออก JWT (Sign)

```javascript
const jwt = require("jsonwebtoken");

function generateToken(user) {
  return jwt.sign(
    { id: user.id, email: user.email, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: process.env.JWT_EXPIRES_IN }, // เช่น "1h" กำหนดค่าไว้ใน .env
  );
}
```

การกำหนด `expiresIn` เป็นแนวปฏิบัติที่สำคัญ เนื่องจาก JWT ที่ไม่มีวันหมดอายุจะยังใช้งานได้ตลอดไปแม้จะรั่วไหลไปอยู่ในมือผู้ไม่หวังดี การกำหนดอายุที่เหมาะสม (เช่น 1 ชั่วโมงถึง 1 วัน ขึ้นอยู่กับความอ่อนไหวของระบบ) ช่วยจำกัดความเสียหายหากเกิดการรั่วไหล อ่านค่านี้จาก `process.env.JWT_EXPIRES_IN` แทนการ hardcode ในโค้ด เพื่อให้ปรับอายุ token ได้โดยไม่ต้องแก้โค้ดและ deploy ใหม่ (เช่น ปรับชั่วคราวเป็น `5s` เพื่อทดสอบพฤติกรรม token หมดอายุตามแบบฝึกหัดในหัวข้อปฏิบัติการ)

`process.env.JWT_SECRET` และ `process.env.JWT_EXPIRES_IN` ต้องถูกกำหนดไว้ในไฟล์ `.env` (โหลดด้วย `require("dotenv").config()` ตามที่แนะนำไว้ตั้งแต่สัปดาห์ที่ 5) และห้าม commit ไฟล์ `.env` ขึ้น Git โดยเด็ดขาด เนื่องจากผู้ที่ทราบค่า `JWT_SECRET` จะสามารถปลอมแปลง (forge) JWT ที่ผ่านการตรวจสอบ signature ได้ทุกใบ ค่านี้ควรเป็นสตริงสุ่มที่ยาวและคาดเดายาก ไม่ใช่คำศัพท์ทั่วไป

```
# เพิ่มในไฟล์ .env
JWT_SECRET=<ค่าสุ่มความยาว 64 ไบต์ สร้างด้วยคำสั่งด้านล่าง>
JWT_EXPIRES_IN=1h
```

```bash
# สร้างค่าสุ่มความยาว 64 ไบต์สำหรับใช้เป็น JWT_SECRET (รันครั้งเดียวตอนตั้งโปรเจกต์)
node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
```

> **Pitfall ที่พบบ่อย**: หากไฟล์ `.env` ไม่ถูกโหลดสำเร็จ (เช่น ลืมเรียก `require("dotenv").config()` ก่อนใช้ `process.env`) `process.env.JWT_SECRET` จะมีค่าเป็น `undefined` ไลบรารี `jsonwebtoken` ตรวจสอบค่านี้ก่อนเซ็นเสมอ และจะ throw `Error: secretOrPrivateKey must have a value` ทันทีเมื่อเรียก `jwt.sign()` โดยไม่เซ็น token ให้ ทำให้ route `login` ล้มเหลวและตอบกลับ `500` ผ่าน error-handling middleware (สัปดาห์ที่ 4) แม้ error นี้จะช่วยให้ตรวจพบปัญหาได้เร็ว แต่ในการ debug ควรตรวจสอบด้วย `console.log(process.env.JWT_SECRET)` เพื่อยืนยันว่าไฟล์ `.env` ถูกโหลดสำเร็จก่อนใช้งานเสมอ และห้ามแก้ปัญหาด้วยการกำหนดค่า `JWT_SECRET` สำรองแบบ hardcode ไว้ในโค้ด (เช่น `process.env.JWT_SECRET || "some-default"`) เพราะจะทำให้ทุกคนที่อ่านซอร์สโค้ดทราบค่า secret ที่แท้จริงทันที

### 2.6 การตรวจสอบ JWT (Verify) ด้วย Middleware

```javascript
function authenticateToken(req, res, next) {
  const authHeader = req.headers["authorization"];
  const token = authHeader && authHeader.split(" ")[1]; // รูปแบบ "Bearer <token>"

  if (!token) {
    return res.status(401).json({
      error: { code: "NO_TOKEN", message: "กรุณาเข้าสู่ระบบก่อนใช้งาน" },
    });
  }

  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET); // แนบข้อมูลผู้ใช้ที่ถอดรหัสแล้วไปกับ req เพื่อใช้ต่อใน route handler
    next();
  } catch (err) {
    return res.status(401).json({
      error: { code: "INVALID_TOKEN", message: "Token ไม่ถูกต้องหรือหมดอายุ" },
    });
  }
}
```

`jwt.verify(token, secret)` เมื่อเรียกโดยไม่ส่ง callback จะทำงานแบบ synchronous คืนค่า payload ที่ถอดรหัสแล้วหาก token ถูกต้อง หรือ throw exception (เช่น `JsonWebTokenError`, `TokenExpiredError`) หาก token ไม่ถูกต้องหรือหมดอายุ จึงใช้ `try/catch` ดักจับได้เช่นเดียวกับรูปแบบ error handling ที่ใช้กับ `async/await` ตลอดทั้งเอกสารนี้ แทนรูปแบบ callback ของ `jwt.verify` ที่มีให้เลือกใช้เช่นกันแต่ไม่สอดคล้องกับสไตล์โค้ดส่วนที่เหลือ

Middleware นี้ทำงานก่อน route handler และเรียก `next()` เพื่อส่งต่อการประมวลผล หากตรวจสอบไม่ผ่านจะหยุดและตอบกลับ error ทันทีโดยไม่เรียก `next()`

### 2.7 ข้อจำกัดที่พบบ่อยที่สุด: เหตุใดจึง "Logout" JWT ไม่ได้ทันที

หัวข้อนี้เป็นจุดที่นิสิตสับสนบ่อยที่สุดเมื่อเริ่มใช้ JWT เพราะคุ้นเคยกับระบบ session-based ที่ server สามารถลบ session ทิ้งเพื่อบังคับ logout ได้ทันที

**แนวคิด**: เนื่องจาก JWT เป็น Stateless (หัวข้อ 1.2) เซิร์ฟเวอร์ **ไม่ได้เก็บรายชื่อ token ที่ออกไปแล้วไว้ที่ใดเลย** การ "ตรวจสอบ" ในหัวข้อ 2.6 เป็นเพียงการคำนวณ signature ซ้ำแล้วเทียบกันทางคณิตศาสตร์เท่านั้น ไม่ได้ถามฐานข้อมูลว่า "token นี้ยัง valid อยู่ไหม"

**เหตุผล**: ผลที่ตามมาคือ เมื่อผู้ใช้กด "Logout" แล้ว client ลบ token ออกจาก localStorage หรือ memory (ฝั่ง client) — แต่ตัว token เดิมนั้น **ยังคง valid และผ่าน `jwt.verify()` ได้ตามปกติ** จนกว่าจะถึงเวลาหมดอายุตาม `expiresIn` หากมีผู้ไม่หวังดีคัดลอก token นั้นไปก่อนหน้า ก็ยังใช้งานต่อได้แม้เจ้าของบัญชีจะกด logout ไปแล้ว

**ตัวอย่าง**: สมมติ `expiresIn: "1h"` และผู้ใช้ login เวลา 09:00 น. แม้กด logout เวลา 09:05 น. token ที่หลุดไปอยู่ในมือผู้อื่นก่อนหน้านั้นยังใช้เรียก API ได้จนถึง 10:00 น.

**แนวทางบรรเทาปัญหา** (นอกเหนือขอบเขตของแล็บสัปดาห์นี้ แต่ควรทราบหลักการไว้):

| แนวทาง                             | คำอธิบายสั้น                                                                                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| กำหนด `expiresIn` ให้สั้น          | จำกัดหน้าต่างเวลาที่ token ที่หลุดไปยังใช้งานได้ (ตามหัวข้อ 2.5)                                                                                 |
| Token Blocklist ใน Redis/ฐานข้อมูล | เก็บรายการ token (หรือ `jti` claim) ที่ถูก revoke ไว้ แล้วให้ middleware ตรวจสอบเพิ่มก่อนอนุญาต — แต่ทำให้ระบบไม่ Stateless อย่างสมบูรณ์อีกต่อไป |
| Refresh Token Pattern              | ใช้ Access Token อายุสั้นมาก (เช่น 15 นาที) คู่กับ Refresh Token อายุยาวที่เก็บในฐานข้อมูลและเพิกถอนได้                                          |

> **ข้อควรระวัง**: รายวิชานี้ implement เฉพาะ Access Token แบบพื้นฐานตามหัวข้อ 2.5-2.6 เพื่อเน้นความเข้าใจหลักการของ JWT ก่อน แนวทาง Refresh Token และ Token Blocklist เป็นหัวข้อขั้นสูงที่นิสิตควรทราบว่ามีอยู่ แต่ไม่อยู่ในขอบเขตการประเมินผลของแล็บสัปดาห์นี้

## 3. Implement ระบบ Register และ Login

### 3.1 ตาราง Users

```sql
CREATE TABLE users (
  id INT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,
  password_hash VARCHAR(255) NOT NULL,
  role ENUM('student', 'admin') NOT NULL DEFAULT 'student',
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

คอลัมน์ `role` ใช้ชนิดข้อมูล `ENUM` เพื่อจำกัดค่าที่เป็นไปได้ไว้ล่วงหน้าในระดับฐานข้อมูล ป้องกันการกำหนดบทบาทที่ไม่ถูกต้องโดยไม่ตั้งใจ

### 3.2 Route สำหรับ Register

```javascript
app.post("/api/v1/auth/register", async (req, res, next) => {
  const { email, password } = req.body;

  if (!email || !password) {
    return res.status(400).json({
      error: {
        code: "VALIDATION_ERROR",
        message: "กรุณาระบุ email และ password",
      },
    });
  }

  try {
    const passwordHash = await hashPassword(password);
    const [result] = await pool.query(
      "INSERT INTO users (email, password_hash, role) VALUES (?, ?, 'student')",
      [email, passwordHash],
    );

    res.status(201).json({
      message: "สมัครสมาชิกสำเร็จ",
      data: { id: result.insertId, email, role: "student" },
    });
  } catch (err) {
    if (err.code === "ER_DUP_ENTRY") {
      return res.status(409).json({
        error: { code: "DUPLICATE_EMAIL", message: "อีเมลนี้มีอยู่ในระบบแล้ว" },
      });
    }
    next(err);
  }
});
```

> **ข้อควรระวัง — Privilege Escalation ผ่าน Mass Assignment**: ตัวอย่างข้างต้น**จงใจไม่รับค่า `role` จาก `req.body`** และกำหนดให้ผู้สมัครใหม่ทุกคนเป็น `'student'` เสมอ หากเขียนโค้ดรับ `role` จาก client โดยตรง (เช่น `role || "student"` แล้วส่ง `role` เข้า query โดยตรง) ผู้ไม่หวังดีสามารถส่ง `{"email": "...", "password": "...", "role": "admin"}` มาสมัครสมาชิกแล้วได้สิทธิ์ admin ทันทีโดยไม่ต้องผ่านการอนุมัติจากใคร ช่องโหว่ลักษณะนี้เรียกว่า **Mass Assignment** และจัดอยู่ในกลุ่ม Broken Access Control (A01) ตาม OWASP Top 10:2025 หากต้องการให้มีบัญชี admin ควรสร้างผ่านการ seed ข้อมูลโดยตรงในฐานข้อมูล หรือให้ admin ที่มีอยู่แล้วเป็นผู้เพิ่ม admin คนใหม่ผ่าน route ที่ปกป้องด้วย `authorizeRole("admin")` เท่านั้น (ดูหัวข้อ 4.3)

### 3.3 Route สำหรับ Login

```javascript
app.post("/api/v1/auth/login", async (req, res, next) => {
  const { email, password } = req.body;

  if (!email || !password) {
    return res.status(400).json({
      error: {
        code: "VALIDATION_ERROR",
        message: "กรุณาระบุ email และ password",
      },
    });
  }

  try {
    const [rows] = await pool.query("SELECT * FROM users WHERE email = ?", [
      email,
    ]);

    if (rows.length === 0) {
      return res.status(401).json({
        error: {
          code: "INVALID_CREDENTIALS",
          message: "อีเมลหรือรหัสผ่านไม่ถูกต้อง",
        },
      });
    }

    const user = rows[0];
    const isPasswordValid = await verifyPassword(password, user.password_hash);

    if (!isPasswordValid) {
      return res.status(401).json({
        error: {
          code: "INVALID_CREDENTIALS",
          message: "อีเมลหรือรหัสผ่านไม่ถูกต้อง",
        },
      });
    }

    const token = generateToken(user);
    res.status(200).json({ message: "เข้าสู่ระบบสำเร็จ", token });
  } catch (err) {
    next(err);
  }
});
```

**ข้อสังเกตด้านความปลอดภัย:** ทั้งกรณี "ไม่พบอีเมล" และ "รหัสผ่านผิด" ตอบกลับด้วยข้อความเดียวกันคือ "อีเมลหรือรหัสผ่านไม่ถูกต้อง" แทนที่จะระบุแยกว่าอีเมลไม่มีในระบบหรือรหัสผ่านผิด เนื่องจากการแยกข้อความจะเปิดช่องให้ผู้ไม่หวังดีตรวจสอบได้ว่าอีเมลใดมีอยู่ในระบบจริงหรือไม่ (enumeration attack)

## 4. Role-Based Access Control (RBAC)

### 4.1 หลักการของ RBAC

RBAC คือแนวทางการควบคุมสิทธิ์การเข้าถึงโดยกำหนดบทบาท (role) ให้กับผู้ใช้แต่ละคน แล้วอนุญาตหรือปฏิเสธการเข้าถึง resource ตามบทบาทนั้น แทนที่จะกำหนดสิทธิ์เป็นรายบุคคลซึ่งจัดการยากเมื่อระบบมีผู้ใช้จำนวนมาก

### 4.2 การสร้าง Middleware ตรวจสอบ Role

```javascript
function authorizeRole(...allowedRoles) {
  return (req, res, next) => {
    if (!req.user) {
      return res.status(401).json({
        error: { code: "NO_TOKEN", message: "กรุณาเข้าสู่ระบบก่อนใช้งาน" },
      });
    }

    if (!allowedRoles.includes(req.user.role)) {
      return res.status(403).json({
        error: {
          code: "FORBIDDEN",
          message: "คุณไม่มีสิทธิ์เข้าถึงทรัพยากรนี้",
        },
      });
    }

    next();
  };
}
```

ฟังก์ชันนี้ใช้เทคนิค higher-order function คืนค่าเป็น middleware ที่ปรับแต่งได้ตามบทบาทที่อนุญาต ทำให้นำไปใช้ซ้ำกับหลาย route ได้อย่างยืดหยุ่น

### 4.3 การใช้งาน Middleware ร่วมกันเป็นลำดับ (Chaining)

```javascript
// เฉพาะผู้ใช้ที่ login แล้วเท่านั้นที่เข้าถึงได้
app.get("/api/v1/auth/me", authenticateToken, (req, res) => {
  res.status(200).json({ message: "สำเร็จ", data: req.user });
});

// เฉพาะผู้ที่มี role เป็น admin เท่านั้นที่ลบข้อมูลได้
app.delete(
  "/api/v1/students/:id",
  authenticateToken,
  authorizeRole("admin"),
  async (req, res, next) => {
    // ตรวจสอบผ่านทั้งสองชั้นแล้ว จึงจะมาถึงจุดนี้
    try {
      const [result] = await pool.query("DELETE FROM students WHERE id = ?", [
        req.params.id,
      ]);
      if (result.affectedRows === 0) {
        return res.status(404).json({
          error: { code: "NOT_FOUND", message: "ไม่พบข้อมูลนิสิต" },
        });
      }
      res.status(200).json({ message: "ลบข้อมูลสำเร็จ" });
    } catch (err) {
      next(err);
    }
  },
);
```

สังเกตลำดับของ middleware ในตัวอย่างที่สอง: `authenticateToken` ต้องทำงานก่อน `authorizeRole` เสมอ เนื่องจาก `authorizeRole` ต้องอาศัยค่า `req.user` ที่ `authenticateToken` เป็นผู้กำหนดไว้

> **ข้อแนะนำ**: จำลำดับด้วยหลักการ "ต้องทราบก่อนว่าเป็นใคร จึงจะตรวจสอบได้ว่ามีสิทธิ์หรือไม่" (Authenticate ก่อน Authorize เสมอ) หากสลับลำดับเป็น `authorizeRole("admin"), authenticateToken` เมื่อ request ไม่มี token มาถึง `authorizeRole` ก่อน โค้ดจะพยายามอ่าน `req.user.role` ทั้งที่ `req.user` ยังเป็น `undefined` อยู่ ทำให้เกิด `TypeError: Cannot read properties of undefined (reading 'role')` และเซิร์ฟเวอร์ตอบกลับ `500 Internal Server Error` แทนที่จะเป็น `401` ที่ควรจะเป็น — เป็นข้อผิดพลาดที่พบบ่อยเมื่อคัดลอกโค้ดแล้ววาง middleware สลับตำแหน่งกัน

### 4.4 ตารางสรุปสิทธิ์การเข้าถึงตามบทบาท

| Resource / Action                                    | Student | Admin |
| ---------------------------------------------------- | ------- | ----- |
| ดูข้อมูลบัญชีของตนเอง (`GET /auth/me`)               | ได้     | ได้   |
| ดูข้อมูลนิสิต (`GET /students`, `GET /students/:id`) | ได้     | ได้   |
| ลบข้อมูลนิสิต (`DELETE /students/:id`)               | ไม่ได้  | ได้   |
| จัดการรายวิชา                                        | ไม่ได้  | ได้   |

ตารางลักษณะนี้ควรจัดทำไว้ตั้งแต่ขั้นตอนออกแบบระบบ เพื่อให้ทีมพัฒนาเห็นภาพรวมของสิทธิ์การเข้าถึงตรงกันก่อนเริ่มเขียนโค้ด

> **ข้อสังเกตสำคัญ**: ตาราง `users` (บัญชีผู้ใช้สำหรับ login ในหัวข้อ 3.1) และตาราง `students` (ข้อมูลนิสิตในสัปดาห์ที่ 5) เป็นคนละตารางที่**ไม่มี Foreign Key เชื่อมโยงกัน** ในขอบเขตของแล็บสัปดาห์นี้ ดังนั้นแถว "ดูข้อมูลของตนเอง" ในตารางข้างต้นหมายถึงข้อมูลบัญชี `users` ของตนเอง (ผ่าน `req.user` ที่ได้จาก JWT) เท่านั้น **ไม่ได้หมายความว่า role `student` ผูกกับระเบียนใดระเบียนหนึ่งในตาราง `students` โดยอัตโนมัติ** การจะทำให้ "ผู้ใช้แก้ไขได้เฉพาะข้อมูลนิสิตของตนเอง" เป็นจริงในทางเทคนิคต้องเพิ่มคอลัมน์เชื่อมโยง (เช่น `user_id` ใน `students` อ้างอิง `users(id)`) ก่อน ซึ่งเป็นการปรับ schema ที่อยู่นอกเหนือขอบเขตของแล็บสัปดาห์นี้ (ดูหัวข้อ "ส่วนต่อยอด" ของ `wk06-lab.md`)

### 4.5 Workflow รวมของระบบ Authentication และ RBAC

หัวข้อที่ 1-4 ข้างต้นแต่ละหัวข้อสอนกลไกแยกส่วนกัน (Authentication, JWT, Register/Login, RBAC) แผนภาพต่อไปนี้รวมทุกกลไกเข้าด้วยกันเป็น workflow เดียว แสดงเส้นทางของ request ตั้งแต่ยังไม่มี token จนถึงเข้าถึง resource ที่มีการป้องกันด้วย RBAC สำเร็จ

![Workflow รวมของระบบ Authentication และ RBAC](wk06/authen-rbac.png)

**ข้อสังเกตจาก workflow ทั้งภาพ**

1. **Register และ Login เกิดขึ้นเพียงครั้งเดียว** (หรือนาน ๆ ครั้งเมื่อ token หมดอายุ) ส่วนขั้นตอนตั้งแต่ `authenticateToken` ลงไปเกิดขึ้น**ทุกครั้ง**ที่มีคำขอไปยัง route ที่มีการป้องกัน เซิร์ฟเวอร์ไม่ต้องจำว่าใคร login ไว้ก่อนหน้า เพราะทุกคำขอพิสูจน์ตัวตนตัวเองผ่าน token ที่แนบมา
2. **ลำดับ Middleware คือหัวใจของ workflow นี้**: `authenticateToken` ต้องมาก่อน `authorizeRole` เสมอ (ตามหัวข้อ 4.3) เพราะ `authorizeRole` อ่านค่า `req.user.role` ที่ `authenticateToken` เป็นผู้กำหนดไว้เท่านั้น หากไม่มี `req.user` มาก่อน middleware ชั้นที่สองจะทำงานผิดพลาด
3. **ทุกจุดที่ตอบ error (401, 403) จะหยุด workflow ทันทีโดยไม่เรียก `next()`** ไม่ปล่อยให้คำขอไหลต่อไปถึง route handler จริง
4. Diagram นี้แสดงเฉพาะเส้นทางของ `DELETE /students/:id` (ต้องผ่านทั้ง Authentication และ Authorization) หาก route ใดต้องการเพียงการยืนยันตัวตนโดยไม่จำกัด role (เช่น `GET /auth/me` ในหัวข้อ 4.3) จะข้ามขั้นตอน `authorizeRole`

## สรุปเนื้อหาสำคัญ

1. Authentication ตอบคำถามว่า "คุณเป็นใคร" (ล้มเหลว → `401`) ส่วน Authorization ตอบคำถามว่า "คุณมีสิทธิ์ทำสิ่งนี้หรือไม่" (ล้มเหลว → `403`) ทั้งสองต้องทำงานร่วมกันเพื่อความปลอดภัยที่สมบูรณ์
2. JWT ประกอบด้วย Header, Payload และ Signature โดย Payload สามารถถอดรหัสอ่านได้เสมอ (ไม่ใช่การเข้ารหัสลับ) จึงห้ามใส่ข้อมูลอ่อนไหวลงไป
3. รหัสผ่านต้องเข้ารหัสด้วย `bcrypt` ก่อนบันทึกลงฐานข้อมูลเสมอ ห้ามเก็บแบบ plain text และ `role` ของผู้ใช้ต้องไม่รับค่าจาก client โดยตรงตอน register (ป้องกัน Mass Assignment)
4. Middleware `authenticateToken` ใช้ตรวจสอบว่าผู้ใช้ล็อกอินหรือไม่ ส่วน `authorizeRole` ใช้ตรวจสอบว่าผู้ใช้มีบทบาทที่เหมาะสมหรือไม่ และต้องเรียงลำดับให้ authenticate มาก่อน authorize เสมอ
5. RBAC ช่วยจัดการสิทธิ์การเข้าถึงอย่างเป็นระบบผ่านบทบาท แทนที่จะกำหนดสิทธิ์รายบุคคลซึ่งจัดการยากเมื่อระบบขยายขนาด
6. JWT เป็น Stateless จึงไม่มีกลไก "logout ทันที" ในตัว token ที่ออกไปแล้วจะยังใช้งานได้จนกว่าจะหมดอายุตาม `expiresIn` แม้ผู้ใช้จะกด logout ฝั่ง client ไปแล้วก็ตาม

## คำถามท้ายบท

1. จงอธิบายความแตกต่างระหว่าง Authentication และ Authorization พร้อมยกตัวอย่างสถานการณ์ที่แสดงความแตกต่างนี้อย่างชัดเจน
2. เพราะเหตุใดจึงไม่ควรใส่ข้อมูลอ่อนไหว เช่น รหัสผ่าน ลงใน payload ของ JWT
3. `bcrypt` ช่วยป้องกันความเสี่ยงประเภทใดตาม OWASP Top 10:2025 ที่กล่าวถึงในสัปดาห์ที่ 4 และป้องกันได้อย่างไร
4. เพราะเหตุใดการตอบกลับข้อความ error เดียวกันสำหรับกรณี "ไม่พบอีเมล" และ "รหัสผ่านผิด" จึงเป็นแนวปฏิบัติที่ปลอดภัยกว่าการแยกข้อความ
5. จงอธิบายว่าเหตุใด middleware `authenticateToken` จึงต้องถูกเรียกก่อน `authorizeRole` เสมอ หากสลับลำดับจะเกิดผลอย่างไร
6. หากต้องการเพิ่มบทบาทใหม่ชื่อ `instructor` (อาจารย์) ที่สามารถแก้ไขคะแนนของนิสิตได้ แต่ไม่สามารถลบบัญชีผู้ใช้ได้ จงออกแบบตารางสิทธิ์การเข้าถึงในลักษณะเดียวกับหัวข้อที่ 4.4
7. จงอธิบายเหตุผลที่ควรกำหนด `expiresIn` ให้กับ JWT ทุกครั้ง และอธิบายผลกระทบหากไม่กำหนดอายุของ token ไว้เลย
8. เพราะเหตุใดจึงไม่ควรให้ route `POST /api/v1/auth/register` รับค่า `role` จาก `req.body` โดยตรง ช่องโหว่นี้เรียกว่าอะไร และหากต้องการสร้างบัญชี admin คนแรกของระบบควรทำอย่างไร
9. จงอธิบายว่าเพราะเหตุใดการกด "Logout" ในระบบที่ใช้ JWT แบบพื้นฐาน (ตามที่สอนในหัวข้อ 2.5-2.6) จึงไม่ได้ทำให้ token เดิมใช้งานไม่ได้ทันที และมีแนวทางใดบ้างที่ช่วยบรรเทาปัญหานี้
