## 1. ลำดับขั้นตอนการสาธิตระบบสด (Live Demo Script: 3-4 นาที)

> **คำแนะนำ:** ก่อนเริ่มนำเสนอ ให้รันคำสั่ง `npm run dev` ในโฟลเดอร์โปรเจกต์ และเปิดเบราว์เซอร์ไปที่ `http://localhost:3000`

### นาทีที่ 1: แนะนำภาพรวมระบบและเปิดหน้า Frontend Web App
* **คำพูดนำ:** *"สวัสดีครับอาจารย์ วันนี้ผมขอสาธิตระบบบริหารจัดการฟิตเนสและคลาสออกกำลังกาย FitZone ซึ่งพัฒนาตามโจทย์ Pno: 9 ในระยะที่ 3 นี้เราได้ผสานระบบ Backend API, ฐานข้อมูล MySQL, External Weather API และ Frontend Web Client เข้าเป็นระบบเดียวที่ใช้งานได้จริงครับ"*
* **การกระทำในจอ:** 
  1. ชี้ให้เห็น Header ที่มีไฟแสดงสถานะ `API เชื่อมต่อปกติ` สีเขียว
  2. แสดงกล่องสถิติภาพรวม (Hero Stats): สาขา 4 แห่ง, คลาส 4 รายการ, สมาชิกในระบบ

### นาทีที่ 2: สาธิต External API & การค้นหาข้อมูล (Search & Weather)
* **การกระทำในจอ:** 
  1. ชี้ไปที่ Card ของสาขาฟิตเนส จะเห็นกล่อง **"🌤️ สภาพอากาศสด (External API)"** ที่ดึงอุณหภูมิและความชื้นจริงมาจากพิกัดของสาขานั้นผ่าน Open-Meteo
  2. ทดลองพิมพ์ค้นหาในช่องค้นหา เช่น พิมพ์ว่า `"สยาม"` หรือ `"สุขุมวิท"` จะเห็นการกรองสาขาแบบ Interactive ทันที
  3. อธิบายสั้น ๆ ว่า: *"หาก External API มีปัญหา ระบบของเรามีกลไก Retry 2 ครั้งพร้อม Exponential Backoff และส่งมอบข้อมูลสภาพอากาศสำรอง (Fallback) ทันที ทำให้หน้าเว็บไม่ค้างหรือแสดง Error ต่อผู้ใช้ครับ"*

### นาทีที่ 3: สาธิตการทำ Transaction จองคลาส และดู "คลาสของฉัน" (My Bookings)
* **การกระทำในจอ:**
  1. สลับไปแท็บ **"ตารางคลาสออกกำลังกาย"**
  2. ชี้ให้เห็นคลาส เช่น *HIIT Fat Burner* หรือ *Yoga Flow & Flexibility* ซึ่งแสดงจำนวนที่นั่งว่าง เช่น `"เหลือ 9 / 10 ที่นั่ง"`
  3. คลิกปุ่ม **"จองคลาสนี้"** -> Modal จะเด้งขึ้นมา
  4. เลือกสมาชิกจาก Dropdown -> คลิกปุ่ม **"ยืนยันการจอง"** (POST /bookings)
  5. ระบบจะแสดง Toast สีเขียว: `"จองคลาสสำเร็จ! หมายเลขการจอง #X"` และตัดยอดที่นั่งว่างบนหน้าจอทันทีแบบ Real-time
  6. สลับไปแท็บ **"คลาสของฉัน (My Bookings)"** (GET /members/:id/bookings) -> **ชี้ให้อาจารย์ดูว่าคลาสที่เพิ่งกดจอง ปรากฏขึ้นมาในการ์ดของสมาชิกคนนั้นทันที! พร้อมวันเวลาและชื่อเทรนเนอร์**
  7. **กดปุ่ม "❌ ยกเลิกการจอง"** (DELETE /bookings/:id) -> กดยืนยัน -> การ์ดหายไป และยอดที่นั่งว่างในตารางคลาสเพิ่มคืนกลับมา (+1) ทันที!
* **คำพูดนำ:** *"การออกแบบนี้ช่วยตอบโจทย์ความเป็นส่วนตัว (PDPA) ให้สมาชิกเห็นเฉพาะคลาสของตนเอง และยังรองรับครบทั้งการจอง (POST) และการยกเลิก (DELETE) ด้วย Transaction ป้องกัน Race Condition ครับ"*

### นาทีที่ 4: สาธิตฟอร์มสมัครสมาชิก และเปิดเอกสาร Swagger UI
* **การกระทำในจอ:**
  1. สลับไปแท็บ **"สมัครสมาชิก (Staff)"** -> ลองกดปุ่มสมัครโดยไม่กรอกข้อมูล ระบบจะแสดง Error Validation ใต้ช่องแต่ละช่องทันที (ชื่อสั้นไป, อีเมลไม่ถูกต้อง, ยังไม่ได้เลือกสาขา)
  2. กรอกข้อมูลถูกต้อง -> กดสมัคร -> ระบบบันทึกเข้า MySQL และรายชื่ออัปเดตลงตารางด้านขวาทันที
  3. คลิกที่เมนูขวาบน **"Swagger Docs ↗"** (เปิดไปที่ `/api-docs`) โชว์ให้อาจารย์เห็นว่ามีเอกสารสเปก OpenAPI 3.0 ครบทั้ง 10 Endpoints และทดสอบเรียกได้จริง

## 2. แนวคำถามเชิงเทคนิคที่ผู้สอนมักจะถาม พร้อมแนวคำตอบ (Technical Q&A)

### คำถามที่ 1: ทำไมถึงต้องมีหน้า "คลาสของฉัน (My Bookings)" และมีความสำคัญอย่างไรในแง่ Architecture?
* **แนวคำตอบ:**  
  *"ในระบบฟิตเนสจริง ผู้ใช้จำเป็นต้องตรวจสอบตารางเวลาของตนเองได้ว่าลงเรียนคลาสอะไรไว้บ้าง และสามารถยกเลิกได้หากติดธุระเพื่อคืนที่นั่งให้ผู้อื่น นอกจากนี้ยังเป็นการคำนึงถึง Data Privacy / PDPA เพื่อไม่ให้เปิดเผยรายชื่อสมาชิกคนอื่นต่อสาธารณะ และในแง่ API ทำให้ระบบมีฟังก์ชัน RESTful ครบถ้วนทั้ง GET, POST, และ DELETE ครับ"*

### คำถามที่ 2: ทำไมถึงต้องใช้ `SELECT ... FOR UPDATE` ในขั้นตอนการจองคลาสและยกเลิกคลาส?
* **แนวคำตอบ:**  
  *"เนื่องจากระบบจองคลาสและยกเลิกคลาสเป็นจุดที่มีความเสี่ยงต่อปัญหา Concurrency หรือ Race Condition สูง เช่น หากมีที่นั่งเหลือเพียง 1 ที่ แต่มีผู้ใช้ 2 คนกดจองพร้อมกันในเสี้ยววินาที หากอ่านค่าแบบปกติ ทั้งคู่จะเห็นว่าที่นั่งว่างและทำการตัดยอด ทำให้เกิดปัญหาที่นั่งติดลบ (Overbooking)  
  การใช้ `SELECT ... FOR UPDATE` ภายใต้ `START TRANSACTION` จะเป็นการ Lock แถวของคลาสนั้นไว้ที่ระดับฐานข้อมูล จนกว่า Transaction แรกจะ Commit หรือ Rollback ทำให้คำขอที่สองต้องรอคิว และเมื่อเข้ามาตรวจสอบจะพบว่า `available_spots <= 0` ระบบจึงปฏิเสธได้อย่างถูกต้องครับ"*

### คำถามที่ 3: กลไก Resilience สำหรับ External API ออกแบบไว้อย่างไร และทำไมไม่ปล่อยให้พังไปเลย?
* **แนวคำตอบ:**  
  *"เราออกแบบให้ระบบทนทานต่อความล้มเหลว (Fault Tolerance) ตามหลัก 3 ระดับครับ:  
  1. **Timeout Control:** กำหนดเพดานไว้ที่ 3 วินาที หากภายนอกไม่ตอบกลับ จะยกเลิกทันทีเพื่อไม่ให้ Thread ของเราค้าง  
  2. **Automatic Retry with Exponential Backoff:** หากเกิดข้อผิดพลาดประเภท Transient (เช่น เครือข่ายสะดุด หรือ 5xx) ระบบจะลองใหม่ 2 ครั้ง โดยเว้นระยะห่าง 500ms และ 1,000ms เพื่อลดภาระของเซิร์ฟเวอร์ปลายทาง  
  3. **Fallback Data:** หากลองซ้ำครบแล้วยังไม่สำเร็จ ระบบจะดึงข้อมูลสภาพอากาศสำรองในหน่วยความจำ (เช่น 30°C อากาศแจ่มใส) มาแสดงผลแทน ทำให้หน้าเว็บยังแสดงผลได้อย่างต่อเนื่อง และผู้ใช้ยังใช้งานฟังก์ชันหลักอื่น ๆ ได้ตามปกติครับ"*

### คำถามที่ 4: ในการเขียน Integration Test ทำไมต้องแยก `app` ออกจาก `app.listen()`?
* **แนวคำตอบ:**  
  *"ถ้าเราใส่ `app.listen(PORT)` ไว้ในไฟล์เดียวโดยไม่มีเงื่อนไข เมื่อ Jest หรือ Supertest ทำการ `require` ไฟล์นั้นเข้ามาเพื่อรันการทดสอบ ตัว Express จะพยายาม Bind เข้ากับพอร์ตจริง (เช่น 3000) ซึ่งอาจไปชนกับเซิร์ฟเวอร์ที่กำลังรันอยู่จริง หรือหากรันหลาย Test Suite พร้อมกันจะเกิด Error `EADDRINUSE`  
  เราจึงใช้การตรวจสอบ `if (require.main === module)` เพื่อให้ `listen()` ทำงานเฉพาะเมื่อเรารันไฟล์นั้นโดยตรงด้วย `node index.js` ส่วน Supertest จะสามารถสร้าง Ephemeral Port ในหน่วยความจำเพื่อทดสอบได้โดยไม่มีข้อขัดแย้งครับ"*
